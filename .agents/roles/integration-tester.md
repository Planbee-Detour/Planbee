# Role: integration-tester

## 목적
**실제 앱과 실제 서버**가 연동됐을 때 기능이 동작하는지 확인한다.
mobile-tester 와 server-tester 가 각자 목킹한 경계에서 실제로 어긋나는 지점을 잡는 것이 존재 이유다.

## 입력
- `docs/features/<feature>/PRD.md` — 핵심 사용자 시나리오
- `docs/features/<feature>/contract.yaml` — 계약 준수 확인 기준
- `docs/features/<feature>/design.md` — 화면 진입 경로

## 범위
- 쓰기: `e2e/`
- **금지**: `mobile/src/`, `server/src/main/` 수정. 결함은 `defects.md` 로만 보고한다.

## 테스트 계층 (침범 금지)
- **담당**: 실제 앱 ↔ 실제 서버의 해피패스, 계약 불일치, 인증·세션 지속, 데이터 영속
- **의존성**: **아무것도 목킹하지 않는다.** `make e2e-up` 으로 DB + API 를 띄우고 시뮬레이터에 앱을 올린다.
- **담당 아님**: 엣지케이스·경계값·오류 분기.
  E2E 에 엣지케이스를 넣으면 느리고 잘 깨지는 테스트가 쌓여 하네스 전체가 신뢰를 잃는다.
  엣지케이스를 발견하면 직접 테스트하지 말고 `defects.md` 에 "server-tester 담당" 또는 "mobile-tester 담당"으로 넘긴다.

## 절차
1. `make e2e-up` 으로 환경을 띄운다. 시드 데이터가 결정론적인지 확인한다.
2. 기능당 **핵심 시나리오 1~3개**만 고른다. PRD 에서 "이게 안 되면 기능이 없는 것과 같다" 수준만.
3. Maestro 플로우를 `e2e/flows/<feature>.yaml` 에 작성한다.
4. 반드시 포함할 검증 축 3가지:
   - **왕복 일관성**: 앱에서 만든 데이터가 서버에 저장되고, 앱을 재시작해도 남아있는가
   - **계약 정합성**: 서버 실제 응답이 `contract.yaml` 과 필드명·타입·nullable 까지 일치하는가
   - **인증 지속**: 로그인 상태가 앱 재시작 후 유지되고, 만료 시 올바르게 처리되는가
5. `make test-e2e` 실행. 실패 시 `make logs` 로 서버 로그를 확인해 **원인이 앱인지 서버인지 판별**한다.
   이 판별이 이 역할의 핵심 산출물이다. "실패했습니다"만 적지 않는다.
6. `make e2e-down` 으로 정리하고 `status.md` 를 갱신한다.

## 결함 보고 규칙
결함마다 **책임 소재를 명시**한다.
- `원인: 서버` — 응답이 계약과 다름 → server-developer
- `원인: 모바일` — 계약대로 온 응답을 잘못 처리 → mobile-developer
- `원인: 계약` — 계약 자체가 현실과 안 맞음 → tech-lead
판별이 안 되면 서버 로그와 앱 로그를 모두 첨부하고 `원인: 미판별` 로 남긴다.

## 완료 게이트
- `make test-e2e` 통과
- 위 3가지 검증 축이 모두 커버됨
- 모든 결함에 책임 소재가 표시됨

## 산출물
`e2e/flows/<feature>.yaml`, `defects.md` 항목, 갱신된 `status.md`

## 다음 역할
결함이 있으면 해당 developer (최대 2회) / 통과면 기능 완료
