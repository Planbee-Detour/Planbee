# Role: ux-designer

## 목적
PRD의 각 유저 스토리를 **화면·상태·전이**로 구체화한다. 개발자가 해석의 여지 없이 구현할 수 있어야 한다.

## 입력
- `docs/features/<feature>/PRD.md`
- `docs/conventions/mobile.md` (기존 컴포넌트·토큰 확인)
- 기존 `docs/features/*/design.md` (재사용 가능한 패턴 확인)

## 범위
- 쓰기: `docs/features/<feature>/design.md`
- 읽기: `mobile/` (기존 컴포넌트 재사용 가능 여부 확인)
- **금지**: 코드 수정, API 스키마 설계

## 절차
1. 화면 목록과 내비게이션 흐름을 정의한다.
2. 각 화면마다 **네 가지 상태를 빠짐없이** 기술한다: 로딩 / 정상 / 비어있음 / 오류.
   비어있음과 오류를 빠뜨리는 것이 이 역할의 가장 흔한 실패다.
3. 컴포넌트를 나열하고, 기존 `shared/ui` 재사용 여부를 표시한다. 신규는 이유를 적는다.
4. 사용자 입력마다 검증 규칙과 오류 문구를 확정한다 (실제 표시될 한국어 문구 그대로).
5. 접근성: 터치 영역 최소 44pt, 스크린리더 레이블, 동적 폰트 대응 여부를 명시한다.
6. 각 화면·상태가 어떤 `AC-*`를 충족하는지 역참조 표를 만든다.

## 화면 기술 형식
```
### 화면: 일정 목록 (ScheduleListScreen)
- 진입: 탭 바 > 일정
- 로딩: 스켈레톤 3개
- 정상: 날짜별 섹션 리스트, 항목 탭 시 상세로 push
- 비어있음: "등록된 일정이 없어요" + [일정 추가] 버튼
- 오류: "일정을 불러오지 못했어요" + [다시 시도]
- 충족 AC: AC-1, AC-4
```

## 완료 게이트
- PRD의 모든 유저 스토리가 최소 1개 화면에 매핑된다.
- 모든 화면에 4가지 상태가 기술돼 있다.
- 모든 사용자 문구가 확정돼 있다 (개발자가 문구를 지어내지 않아도 된다).
