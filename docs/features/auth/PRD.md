# PRD: 이메일 가입과 로그인

- 기능 슬러그: `auth`
- 작성일: 2026-08-23

## 배경 / 문제

Planbee 는 사용자별로 추천 이력과 이용 한도를 관리해야 하는데, 지금은 사용자를 식별할 수단이
전혀 없다. 서버에 `SecurityConfig`, `JwtEncoder/JwtDecoder`, `PasswordEncoder` 인프라는 있지만
`/api/v1/auth/**` 는 공개 경로로 열려만 있고 엔드포인트가 없어 404 다
(`docs/private/TODO.md` 항목 4). 사용자 데이터를 다루는 어떤 기능도 이것 없이는 시작할 수 없다.

또한 Planbee 는 당분간 **초대·승인제 클로즈드 베타**로 운영한다. 즉 계정이 생겼다고 바로
서비스를 쓸 수 있는 것이 아니라, 관리자가 승인한 계정만 로그인이 성립한다. 이 기능은 그 전제인
**계정 생성 · 상태 판정 · 세션 유지**까지를 담당하고, 승인 처리 자체는 `admin-user-approval` 이 맡는다.

## 목표

- 방문자가 이메일과 비밀번호만으로 가입을 신청할 수 있다.
- 승인된 사용자가 로그인해 앱을 이용할 수 있고, 앱을 껐다 켜도 다시 로그인하지 않아도 된다.
- 승인되지 않은 사용자가 자기 계정이 지금 어떤 상태인지(검토 중 / 거절 / 정지) 앱에서 확인할 수 있다.
- 사용자가 앱 안에서 스스로 계정을 삭제할 수 있다. (App Store 심사지침 5.1.1(v) 요건)
- 로그인이 막힌 사용자(거절·정지·잠금)가 앱 안에서 문의할 곳을 찾을 수 있다.
- 개인정보 수집·이용 동의를 법정 고지 사항과 함께 받고, 그 이력을 남긴다.

## Out of scope

- **이메일 인증(가입 시 링크·코드 확인)** — 관리자 승인 게이트가 같은 역할을 하므로 두지 않는다.
  승인 대기열이 스팸으로 오염되기 시작하면 그때 도입한다. (2026-08-23 결정)
- **비밀번호 재설정과 비밀번호 변경** — 메일 발송 인프라를 두지 않기로 했으므로 재설정 링크를
  보낼 수단이 없다. 베타 기간에는 관리자가 수동 처리한다.
- **이메일 / 푸시 발송 인프라 일체** — 사용자 알림은 "다시 로그인하면 상태를 보여주는" 방식으로 대체한다.
- **승인 · 거절 · 정지 처리와 관리자 화면** — `admin-user-approval` 로 분리.
- **일일 추천 횟수 제한** — `recommendation-quota` 로 분리.
- 소셜 로그인 (Sign in with Apple / Google). `docs/conventions/server.md` S-17 상 범위 밖.
- 프로필 편집, 닉네임 변경, 프로필 이미지.
- 다중 기기 세션 목록 조회 및 개별 기기 로그아웃.
- 위치정보 이용 동의 — 추천 기능이 위치를 사용하기 시작할 때 별도로 다룬다 (위치정보법상 별도 동의 대상).

## 유저 스토리와 인수조건

> **AC-46~50 은 2026-08-25 에 추가되었다.** 기존 번호는 재사용·이동하지 않고 각 US 표의 끝에 이어 붙였다.

### US-1. 방문자로서 Planbee 를 이용하기 위해 이메일과 비밀번호로 가입을 신청하고 싶다

| ID | 인수조건 |
|---|---|
| AC-1 | Given 가입 화면에서 미등록 이메일·정책을 만족하는 비밀번호·필수 동의 3건을 모두 채웠을 때 When 신청을 제출하면 Then 계정이 `PENDING` 상태로 생성되고 "가입 신청을 검토하고 있어요" 안내 화면으로 이동한다 |
| AC-2 | Given 이미 가입 신청된 이메일을 입력했을 때 When 제출하면 Then 이메일 입력란 아래에 "이미 가입 신청된 이메일입니다" 가 표시되고 화면은 이동하지 않는다 |
| AC-3 | Given 비밀번호가 8자 미만이거나 영문·숫자 중 하나를 포함하지 않을 때 When 입력을 마치면 Then 제출 버튼이 비활성 상태이고 비밀번호 입력란 아래에 "영문과 숫자를 포함해 8자 이상" 이 표시된다 |
| AC-4 | Given 앱 검증을 우회한 요청이 서버에 도달했을 때 When 비밀번호가 AC-3 정책을 만족하지 않으면 Then 서버가 `password` 필드를 지목한 검증 실패로 거부한다 |
| AC-5 | Given 이메일이 `local@domain` 형식이 아닐 때 When 입력을 마치면 Then 제출 버튼이 비활성 상태이고 이메일 입력란 아래에 형식 오류 문구가 표시된다 |
| AC-6 | Given 필수 동의 3건(이용약관 · 개인정보 수집·이용 · 만 14세 이상) 중 하나라도 체크되지 않았을 때 When 제출을 시도하면 Then 제출 버튼이 비활성 상태다 |
| AC-7 | Given 선택 동의(마케팅·알림 수신)를 체크하지 않았을 때 When 나머지 필수 항목을 채우고 제출하면 Then 가입 신청이 정상 접수된다 |
| AC-8 | Given 가입이 접수되었을 때 When 저장된 동의 이력을 조회하면 Then 동의한 항목별로 동의 여부·약관 버전·동의 시각이 남아 있다 |
| AC-9 | Given 가입 사유 입력란에 100자를 입력한 상태에서 When 한 글자를 더 입력하면 Then 입력이 되지 않고 글자 수 표시가 `100/100` 을 유지한다 |
| AC-10 | Given 네트워크가 끊긴 상태에서 When 가입을 제출하면 Then "연결을 확인해 주세요" 안내가 표시되고 입력한 값이 그대로 남아 다시 제출할 수 있다 |
| AC-46 | Given 가입 신청이 접수되었을 때 When 검토 중 화면이 표시되면 Then 제목·본문·행동 지시 문구·신청 이메일·신청일·문의 주소가 **가입 신청 응답 하나**에 모두 담겨 있다 (별도 조회를 하지 않으며, 로그인 차단 응답과 같은 구조를 쓴다) |

### US-2. 승인된 사용자로서 내 계정으로 앱에 들어가고 싶다

| ID | 인수조건 |
|---|---|
| AC-11 | Given 상태가 `APPROVED` 인 계정일 때 When 올바른 이메일과 비밀번호로 로그인하면 Then 홈 화면으로 이동한다 |
| AC-12 | Given 등록된 이메일에 잘못된 비밀번호를 입력했을 때 When 로그인하면 Then "이메일 또는 비밀번호를 확인해 주세요" 가 표시된다 |
| AC-13 | Given 등록되지 않은 이메일을 입력했을 때 When 로그인하면 Then AC-12 와 **동일한** 문구와 동일한 응답을 받는다 (계정 존재 여부를 노출하지 않는다) |
| AC-14 | Given 상태가 `PENDING` 인 계정일 때 When 올바른 비밀번호로 로그인하면 Then 홈으로 가지 않고 "가입 신청을 검토하고 있어요" 화면이 표시된다 |
| AC-15 | Given 상태가 `REJECTED` 인 계정일 때 When 올바른 비밀번호로 로그인하면 Then "가입이 승인되지 않았어요" 화면이 표시된다 |
| AC-16 | Given 상태가 `SUSPENDED` 인 계정일 때 When 올바른 비밀번호로 로그인하면 Then "이용이 정지된 계정이에요" 화면이 표시된다 |
| AC-17 | Given 같은 계정으로 10분 안에 5회 연속 로그인에 실패했을 때 When 6번째로 **올바른** 비밀번호를 입력하면 Then 로그인이 거부되고 남은 잠금 시간이 분 단위로 안내된다 |
| AC-18 | Given 로그인에 성공했을 때 When 기기의 저장소를 확인하면 Then 액세스·리프레시 토큰이 Keychain(iOS) / Keystore(Android) 에만 있고 MMKV·AsyncStorage 에는 없다 |
| AC-19 | Given 서버가 500 을 반환하는 상황에서 When 로그인을 시도하면 Then "잠시 후 다시 시도해 주세요" 와 재시도 버튼이 표시된다 |
| AC-47 | Given 등록되지 않은 이메일로 10분 안에 5회 연속 로그인에 실패했을 때 When 6번째로 로그인을 시도하면 Then 등록된 계정이 잠겼을 때(AC-17)와 **동일한** 응답을 받는다 (잠금 여부로 계정 존재를 구분할 수 없다) |
| AC-48 | Given 잠금이 걸린 상태일 때 When 잠금이 풀리기 전에 로그인을 여러 번 더 시도하면 Then 잠금 시간이 늘어나지 않고 남은 시간이 계속 줄어든다 |

### US-3. 사용자로서 앱을 다시 열 때마다 로그인하지 않고 이어서 쓰고 싶다

| ID | 인수조건 |
|---|---|
| AC-20 | Given 유효한 리프레시 토큰이 저장되어 있을 때 When 앱을 실행하면 Then 로그인 화면을 거치지 않고 홈 화면이 표시된다 |
| AC-21 | Given 저장된 토큰이 하나도 없을 때 When 앱을 실행하면 Then 로그인 화면이 표시된다 |
| AC-22 | Given 액세스 토큰이 만료된 상태에서 When 인증이 필요한 API 를 호출하면 Then 리프레시로 1회 갱신한 뒤 원래 요청이 재시도되어 성공하고, 사용자에게 로그인 화면은 나타나지 않는다 |
| AC-23 | Given 리프레시 토큰으로 갱신에 성공했을 때 When **유예 창(10초)이 지난 뒤** 갱신에 사용한 직전 리프레시 토큰으로 다시 갱신을 시도하면 Then 거부된다 |
| AC-24 | Given AC-23 의 재사용(유예 창 밖)이 감지되었을 때 When 같은 계정의 다른 기기에서 갱신을 시도하면 Then 그 기기도 거부되고 로그인 화면으로 이동한다 (해당 계정의 모든 리프레시 토큰이 폐기된다) |
| AC-25 | Given 마지막 **사용**(로그인 또는 토큰 갱신)으로부터 14일이 지났을 때 When 앱을 실행하면 Then 로그인 화면과 함께 "다시 로그인해 주세요" 가 표시된다 |
| AC-49 | Given 리프레시 갱신에 성공한 직후 10초 안에 When 같은(직전) 리프레시 토큰으로 갱신을 다시 시도하면 Then 재사용으로 처리되지 않고 직전에 발급한 것과 **같은** 토큰 쌍을 다시 받는다 (AC-24 의 전 기기 폐기가 일어나지 않는다) |

### US-4. 사용자로서 이 기기에서 로그아웃하고 싶다

### US-5. 사용자로서 서비스를 그만 쓰기 위해 앱 안에서 계정을 삭제하고 싶다

| ID | 인수조건 |
|---|---|
| AC-28 | Given 로그인된 상태일 때 When 설정 화면을 열면 Then "계정 삭제" 진입점이 보인다 |
| AC-29 | Given 계정 삭제를 선택했을 때 When 비밀번호를 다시 입력하지 않으면 Then 삭제가 실행되지 않는다 |
| AC-30 | Given 계정 삭제 확인 단계일 때 When 확인 화면을 보면 Then "삭제하면 되돌릴 수 없습니다" 문구가 표시된다 |
| AC-31 | Given 계정 삭제가 완료되었을 때 When 삭제 전에 쓰던 이메일과 비밀번호로 로그인을 시도하면 Then 등록되지 않은 계정으로 처리된다 (AC-13 과 동일 응답) |
| AC-32 | Given 계정 삭제가 완료되었을 때 When 같은 이메일로 다시 가입을 신청하면 Then 정상적으로 접수된다 |
| AC-50 | Given 상태가 `REJECTED` 인 계정으로 로그인해 상태 안내 화면에 있을 때 When "계정 삭제" 를 선택하고 비밀번호를 다시 입력하면 Then 계정이 삭제되고 이후 로그인은 AC-31 과 같은 응답을 받는다 |

### US-6. 사용자로서 내 정보가 어떻게 쓰이는지 언제든 확인하고 싶다

| ID | 인수조건 |
|---|---|
| AC-33 | Given 가입 화면일 때 When 각 동의 항목의 "보기" 를 누르면 Then 해당 약관 전문을 읽을 수 있는 화면이 열린다 |
| AC-34 | Given 개인정보 수집·이용 동의 전문을 열었을 때 When 내용을 확인하면 Then 수집 항목 · 이용 목적 · 보유 기간 · 동의 거부 권리와 그에 따른 불이익 네 가지가 모두 표시된다 |
| AC-35 | Given 로그인된 상태일 때 When 설정 화면을 열면 Then 이용약관과 개인정보 처리방침 전문으로 가는 항목이 보인다 (App Store 심사지침 5.1.1(i)) |
| AC-36 | Given 약관 전문 화면을 열었을 때 When 문서 상단을 보면 Then 버전과 시행일이 표시된다 (AC-8 이 저장하는 버전과 같은 값) |
| AC-37 | Given 네트워크가 끊긴 상태일 때 When 약관 전문을 열면 Then 전문이 정상적으로 표시된다 (본문이 앱에 포함되어 있다) |

### US-7. 로그인할 수 없는 사용자로서 앱 안에서 문의할 곳을 찾고 싶다

`REJECTED`·`SUSPENDED` 계정은 로그인이 막혀 AC-28 의 계정 삭제 화면에 도달할 수 없고,
로그인 잠금(AC-17)은 비밀번호 재설정이 범위 밖이라 시간 경과 외의 해제 수단이 없다.
사람에게 닿는 경로가 화면에 없으면 이 사용자들에게는 출구가 없다.

| ID | 인수조건 |
|---|---|
| AC-38 | Given 상태가 `REJECTED` 인 계정으로 로그인했을 때 When 상태 안내 화면을 보면 Then 문의용 이메일 주소가 화면에 표시된다 |
| AC-39 | Given 상태가 `SUSPENDED` 인 계정으로 로그인했을 때 When 상태 안내 화면을 보면 Then 문의용 이메일 주소가 화면에 표시된다 |
| AC-40 | Given 상태가 `PENDING` 인 계정으로 로그인했을 때 When 상태 안내 화면을 보면 Then 문의용 이메일 주소가 화면에 표시된다 |
| AC-41 | Given 로그인 잠금(AC-17)이 걸린 상태에서 When 잠금 안내를 보면 Then 문의용 이메일 주소가 함께 표시된다 |
| AC-42 | Given AC-38~41 의 화면이 표시되었을 때 When 표시된 주소의 출처를 확인하면 Then 서버 응답에 담겨 온 값이고 앱에 하드코딩된 문자열이 아니다 (`docs/conventions/common.md` C-8) |
| AC-43 | Given 서버의 문의 주소 설정값이 비어 있거나 가져올 수 없을 때 When AC-38~41 의 화면이 표시되면 Then 이메일 주소와 "문의하기" 동작이 나타나지 않고 그 자리에 "문의 창구를 준비하고 있어요" 취지의 대체 안내가 표시된다 |
| AC-44 | Given AC-43 의 상황일 때 When 화면의 나머지를 조작하면 Then 제목·본문·주 버튼이 정상 표시되어 로그인 화면으로 돌아갈 수 있다 (화면이 막히거나 오류로 처리되지 않는다) |
| AC-45 | Given 문의 주소가 응답에 실려 왔을 때 When AC-38~41 의 화면을 보면 Then 주소는 **단수 문자열 하나**로 표시된다 (앱이 여러 주소를 나열하는 UI 를 갖지 않는다) |

## 제약

- **계정 상태는 4가지다**: `PENDING`(신청 접수, 검토 중) / `APPROVED`(이용 가능) /
  `REJECTED`(승인 거절) / `SUSPENDED`(이용 정지). 신규 가입은 항상 `PENDING` 으로 시작한다.
- **역할은 2가지다**: `USER` / `ADMIN`. 앱에서 역할을 바꾸는 경로는 만들지 않는다.
  초기 관리자 계정은 시드로 생성한다 (열린 질문 2).
- 비밀번호 정책: 영문과 숫자를 포함해 8자 이상. 저장은 `PasswordEncoder`(bcrypt) 로만 한다
  (`docs/conventions/server.md` S-17).
- 토큰 수명: 액세스 30분 / 리프레시 14일 (S-17). 리프레시는 **해시해서 저장하고 사용 시 회전**한다.
- **리프레시 14일은 절대 만료가 아니라 유휴 만료(sliding)다** (2026-08-25 확정). 회전할 때마다
  새 토큰에 새 14일이 부여되고, 별도의 절대 만료 상한은 두지 않는다. AC-25 가 말하는 14일의
  기준점은 마지막 **로그인**이 아니라 마지막 **사용**(갱신 포함)이다. 절대 만료를 두면 매일 쓰는
  사용자도 2주마다 재로그인해야 해서 계획 앱의 사용 맥락에 맞지 않는다.
- **리프레시 회전에는 10초의 유예 창을 둔다** (2026-08-25 확정). 회전 직후 10초 안에 직전 토큰이
  다시 오면 재사용으로 보지 않고 **그때 발급한 것과 같은 토큰 쌍을 다시 돌려준다**(AC-49).
  10초를 넘긴 재사용만 AC-23 의 거부와 AC-24 의 전 기기 폐기로 이어진다. 유예 창이 없으면
  네트워크 타임아웃이나 앱 강제 종료만으로 정상 사용자가 모든 기기에서 로그아웃된다.
- **로그인 실패 잠금: 10분 창 안에 5회 연속 실패하면 10분간 잠근다** (2026-08-23 확정).
  AC-17 이 이 수치를 그대로 검증한다. 비밀번호 재설정이 범위 밖이므로 해제 수단은 시간 경과뿐이다.
- **실패 카운터의 키는 계정이 아니라 입력된 이메일 문자열이다** (2026-08-25 확정). 계정이 존재하지
  않아도 같은 규칙으로 세고 같은 잠금 응답을 낸다(AC-47). 계정 단위로만 세면 등록된 이메일은
  잠금 응답을, 미등록 이메일은 자격 증명 오류를 받아 **AC-13 이 막으려던 계정 존재 여부가
  잠금 응답으로 새어 나간다.** 정규화(소문자·공백 제거)한 이메일을 키로 TTL 캐시에 센다.
- **잠금 상태 확인은 비밀번호 검증보다 먼저 한다** (2026-08-25 확정). 잠겨 있으면 남은 시간과
  함께 즉시 반환하고 비밀번호를 검증하지 않는다. 그 시도는 카운터에 넣지 않으므로 잠금이
  연장되지 않는다(AC-48). 이 순서는 bcrypt 연산을 아끼고 응답 시간 차이로 정보가 새는 것도 막는다.
  카운터는 로그인 성공 시와 잠금 만료 시 초기화한다.
- 남은 잠금 시간은 **올림(ceil)하고 최소 1분**으로 내린다 (2026-08-25 확정). 30초가 남았을 때
  "약 0분" 은 "지금 되는데 안 되네" 가 된다. 실제보다 짧게 말하지 않는다.
- **만 14세 미만은 자기신고 체크박스로 차단한다** (2026-08-23 확정). 법정대리인 동의 절차
  (「개인정보 보호법」 제22조의2)를 만들지 않는 대신 만 14세 미만의 가입 자체를 막는다.
- **가입 사유는 선택 항목이다. 비어 있어도 가입 신청이 접수된다** (2026-08-23 확정).
  제출 버튼의 활성 조건은 이메일 · 비밀번호 · 필수 동의 3건뿐이고(AC-1·AC-6) 가입 사유는 그 조건이 아니다.
  `docs/legal/privacy-policy.md` 1항도 가입 사유를 **선택 항목** 표에 두고 있다 — 두 문서는 일치한다.
  가입 사유를 소비하는 쪽(`admin-user-approval` 의 대기 목록)은 값이 없는 신청을 정상 케이스로 다뤄야 한다.
- **앱 안의 문의 연락처는 서버가 설정값(`SUPPORT_CONTACT_EMAIL`)을 응답에 담아 내려준다**
  (2026-08-25 확정 — 2026-08-23 의 "`ADMIN` 계정 이메일" 결정을 대체한다).
  앱이 주소를 하드코딩하거나 조합하지 않는다 (C-8, AC-42). 값의 출처만 사용자 레코드에서
  환경 변수로 옮긴 것이고 앱 쪽 요건은 그대로다.
  **왜 바꿨나.** C-8 이 요구하는 것은 "앱이 하드코딩하지 않는다" 뿐이고 설정값도 이를 똑같이
  만족한다. 반면 `ADMIN` 계정 이메일을 쓰면 ① 문의 창구가 관리자 계정의 존재 여부에 묶이고,
  ② 담당자가 바뀌면 대외 연락처가 함께 바뀌며, ③ 잠금 응답(AC-41)은 비밀번호를 틀린
  누구에게나 가므로 **직원 개인 이메일이 사실상 공개**된다.
  이 주소는 `docs/legal/privacy-policy.md` 11항의 개인정보 보호책임자 연락처, 이용약관
  제8조 2항의 이의 제기 연락처와 **같은 값**이어야 한다. 개인 계정이 아니라 문의 전용
  별칭(`support@` 등)을 쓴다.
  설정값이 비어 있을 때는 화면이 실패하지 않고 대체 안내로 성립한다(AC-43·AC-44).
  변수 정의는 `.env.example` 에 추가한다 — 값은 채우지 않는다 (절대 규칙 7).
- **동의 이력에 남는 것은 동의 3건이고, 만 14세 확인은 동의가 아니다** (2026-08-25 확정).
  `TERMS` · `PRIVACY` · `MARKETING` 은 동의 이력에 항목별로 동의 여부·약관 버전·동의 시각을
  남긴다(AC-8). `MARKETING` 은 대응 문서가 아직 없으므로 **버전이 비어 있을 수 있다**(nullable).
  반면 **만 14세 이상 확인은 자기 확인(attestation)이지 약관 동의가 아니다** — 대응 문서가
  존재하지 않아 버전이라는 개념이 성립하지 않는다. 동의 이력이 아니라 사용자 레코드의
  확인 시각 필드로 남긴다. 정보통신망법상 광고성 정보 발송 증빙이 필요한 `MARKETING` 은
  거부한 경우에도 "거부함" 으로 이력을 남긴다.
- 사용자에게 가는 어떤 종류의 알림도 발송하지 않는다. 상태 전달은 전적으로 "다시 로그인" 시점에 이뤄진다.
  따라서 승인 안내 화면(AC-14)에 "승인되면 다시 로그인해 주세요" 라는 행동 지시가 반드시 있어야 한다.
- **가입 화면의 이메일 중복 노출(AC-2)은 인수된 위험이다** (2026-08-25 확정). 로그인은 계정
  존재 여부를 숨기지만(AC-13·AC-47) 가입은 "이미 가입 신청된 이메일입니다" 로 그대로 알린다.
  둘을 모두 숨기려면 해당 주소로 메일을 보내 분기하는 수밖에 없는데 **메일 발송 인프라가
  범위 밖**이라 그 선택지가 없다. 대신 가입 엔드포인트에 IP 단위 레이트 리밋을 걸어 대량
  자동 열거를 막는다. 이 비대칭은 의도된 것이며, 로그인 쪽 보호를 약화시키는 근거로 쓰지 않는다.
- API 상의 모든 시각은 ISO 8601 UTC (`docs/conventions/common.md` C-2), 필드 이름은 `snake_case` (C-7).
- 화면에 필요한 값은 서버가 한 번의 응답으로 완성해서 내린다 (C-8). 앱이 상태 문구를 조합하지 않는다.
- **계정 삭제 시 즉시 파기한다** (2026-08-23 결정). 이메일·비밀번호 해시·동의 이력을 유예 기간 없이
  지운다 (개인정보보호법 제21조). 결제 이력이 없어 법령상 보존 의무 대상이 없다.
  되돌릴 수 없으므로 AC-29 의 비밀번호 재확인과 AC-30 의 경고 문구가 유일한 안전장치다.
- **`REJECTED` 계정은 상태 안내 화면에서 직접 삭제할 수 있다** (2026-08-25 확정, AC-50).
  App Store 심사지침 5.1.1(v) 는 앱 안에서 삭제를 **개시**할 수 있을 것을 요구하는데,
  거절된 계정은 로그인이 막혀 설정 화면(AC-28)에 도달하지 못하므로 문의 메일 외에 경로가 없었다.
  비밀번호는 이미 맞은 상태(상태 때문에 막힌 것)이므로 AC-29 의 비밀번호 재확인 흐름을 그대로
  재사용한다. `docs/legal/privacy-policy.md` 6항이 약속한 "로그인 불가 상태의 삭제" 도 이걸로
  자기 처리된다.
  **`SUSPENDED` 는 제외한다** — 즉시 파기(위 항목) + AC-32(같은 이메일 재가입 가능)와 합쳐지면
  정지된 사용자가 계정을 지우고 곧바로 재가입해 정지를 무력화할 수 있다. 정지 회피 차단은
  `admin-user-approval` 에서 다룬다. `SUSPENDED` 의 삭제 경로는 문의(AC-39)로 남는다.
  **부수 효과:** `REJECTED` 사용자는 삭제 후 같은 이메일로 재신청할 수 있게 된다(AC-32).
  "다시 검토받고 싶다" 는 `design.md` §7.3.1 이 이미 예상한 요구지만, 승인 대기열이 반복
  재신청으로 오염되면 `admin-user-approval` 에서 재신청 제한을 검토한다.
- **약관 본문의 원본은 저장소에 둔다** (`docs/legal/terms.md`, `docs/legal/privacy-policy.md`).
  각 문서 상단에 버전과 시행일을 적고, 그 값이 AC-8 의 동의 이력과 AC-36 의 화면 표시에 함께 쓰인다.
  앱은 이 원본을 **빌드에 포함**해 오프라인에서도 열리게 하고(AC-37), 같은 원본을 웹에 게시해
  App Store Connect / Google Play Console 의 개인정보 처리방침 URL 입력값으로 쓴다.
  앱 내 화면과 공개 URL 은 서로를 대체하지 못한다 — 둘 다 필수다.
- iOS 우선이되 구현은 Android 에서도 성립해야 한다 (`docs/conventions/mobile.md` M-19·M-20).
  토큰 저장소가 플랫폼마다 다르므로 AC-18 은 양쪽 모두에서 검증한다.

## 열린 질문

1. **약관 본문의 게시 위치.** 본문 자체는 작성되었다 — `docs/legal/terms.md` (v1.0),
   `docs/legal/privacy-policy.md` (v1.0). 남은 것은 두 가지다.
   - (가) **공개 URL** — 같은 내용을 웹에 게시하고 그 주소를 App Store Connect / Google Play
     Console 의 개인정보 처리방침 URL 로 입력해야 한다. GitHub Pages 등 수단 미정.
   - (나) **문서 안의 `{{ }}` 미확정 값** — 운영자명, 개인정보 보호책임자 성명·연락처,
     시행일, 거절 계정 보유 기간. → **사람 판단 (절대 규칙 8)**
     처리 위탁 현황(5항)은 알림에서 개인정보를 뺀 결정으로 확정되었다 — 위탁·국외 이전 없음.
     연락처(11항)는 **앱 안에서 보여주는 문의 주소와 같은 값**이어야 한다. 앱 쪽은 서버가
     `ADMIN` 계정 이메일로 내려주므로(AC-42) 해소되었지만, 이 문서는 정적 파일이라 실제 값이 여전히 필요하다.

   두 문서 모두 **법률 전문가 검토를 받지 않은 초안**이다. 배포 전 검토가 필요하다.
   화면 설계와 구현은 이 값들 없이도 진행할 수 있다 — 본문 구조가 확정되었기 때문이다.
2. **초기 관리자 계정을 어떻게 만드는가.** E2E 는 시드 마이그레이션(V900)으로 해결되지만
   운영 환경의 첫 관리자 생성 경로가 정해지지 않았다. → tech-lead
   *(2026-08-25 축소)* 문의 연락처를 설정값으로 분리하면서 **문의 창구가 관리자 계정에서
   떨어져 나갔다.** "`ADMIN` 이 여럿일 때 어느 이메일을 내릴지" 라는 하위 질문은 사라졌고,
   관리자 계정이 없어도 문의 창구는 정상 동작한다. 남은 것은 순수하게 첫 관리자 생성 경로뿐이며,
   이 항목은 더 이상 `auth` 의 화면 동작을 막지 않는다 (`admin-user-approval` 의 선행 조건이다).
3. **오류 코드 확정** (`docs/api/error-codes.md` 등록은 tech-lead 소유). AC 가 구분을 요구하는 상황은
   다음과 같다: 이메일 중복(AC-2), 자격 증명 불일치(AC-12·AC-13 은 서로 구분 불가해야 함),
   상태별 로그인 차단 3종(AC-14·15·16 은 서로 구분 가능해야 함), 로그인 시도 초과(AC-17),
   리프레시 무효(AC-23), 리프레시 재사용(AC-24). → tech-lead
