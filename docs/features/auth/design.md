# UI/UX 명세: 이메일 가입과 로그인 (`auth`)

- 기능 슬러그: `auth`
- 작성일: 2026-08-23
- 작성 역할: ux-designer
- 근거 문서: `docs/features/auth/PRD.md` (US 7 / AC 50), `docs/features/auth/status.md`,
  `docs/legal/terms.md` (v1.0), `docs/legal/privacy-policy.md` (v1.0),
  `docs/design/planbee.pen` (`Screen 01 — Design System`), `docs/design/planbee-design-prompt.md`
- 이 문서가 `auth` 의 **유일한** UI/UX 명세다. 화면 문구는 여기 적힌 것을 그대로 쓴다 (`mobile.md` M-7).

---

## 0. 읽는 방법

- **문구는 확정안이다.** 큰따옴표 안의 한국어는 그대로 화면에 넣는다. 개발자가 바꾸거나 지어내지 않는다.
- **`{{ }}` 로 감싼 값은 미확정이다.** `status.md` 의 `ASK` 와 연결된다. 화면 구조는 이 값 없이도 구현할 수 있고,
  구현 시에는 상수 한 곳(`shared/config`)에서 읽어 쓴다. 배포 전 사람이 채운다.
  이 문서에 남아 있는 `{{ }}` 는 **약관 문서 안의 값(`{{시행일}}`, `{{운영자명}}` 등)뿐**이다.
- **서버가 문구를 내리는 자리**는 그렇게 명시했다. 앱이 조건문으로 문구를 조합하지 않는다 (`common.md` C-8 / `mobile.md` M-18).
  **문의 이메일 주소도 여기 해당한다** — 앱 상수가 아니라 응답 값이다 (§2.7.1 / AC-42).
- 각 화면 끝의 `충족 AC` 는 그 화면이 책임지는 인수조건이다. 전체 대조표는 §13.

## 1. 정보 구조와 내비게이션

### 1.1 내비게이터 구성

```
RootNavigator (세션 상태에 따라 스택 하나만 마운트)
│
├─ SplashScreen                        ← 앱 실행 시 항상 첫 화면 (§3)
│
├─ AuthStack        (세션 없음)
│   ├─ LoginScreen                     (§4)
│   ├─ SignUpScreen                    (§5)
│   └─ LegalDocumentScreen  [모달]      (§6)
│
├─ AccountStatusStack (세션은 발급되지 않았고 계정 상태만 확인된 경우)
│   ├─ AccountStatusScreen             (§7 — PENDING / REJECTED / SUSPENDED 세 변형)
│   ├─ AccountDeleteScreen             (§9 — REJECTED 변형에서만 도달, AC-50)
│   └─ LegalDocumentScreen  [모달]      (§6)
│
└─ MainStack        (세션 있음 · APPROVED)
    ├─ HomeScreen ... (auth 범위 밖, 기존 Screen 02)
    ├─ SettingsScreen                  (§8)
    ├─ AccountDeleteScreen             (§9)
    └─ LegalDocumentScreen  [모달]      (§6)
```

`AccountStatusStack` 을 `AuthStack` 과 분리하는 이유: `PENDING` / `REJECTED` / `SUSPENDED` 는
"로그인 화면 위에 뜬 오류"가 아니라 **사용자가 머물러 읽어야 하는 목적지**다. AC-14 의 행동 지시
("승인되면 다시 로그인해 주세요")를 토스트로 흘리면 사용자가 다음에 뭘 해야 할지 알 수 없다.

### 2.2 화면 골격

- 폭 390 기준, 배경은 `background`, 좌우 여백 20.
- 상단 안전영역 아래에 화면별 헤더, 하단 안전영역 위에 주 버튼.
- 폼 화면은 스크롤 가능. 주 버튼은 **콘텐츠 흐름 안**에 두고, 키보드가 올라오면 함께 밀린다.
  (하단 고정 버튼은 안드로이드에서 키보드와 겹치는 사례가 많아 쓰지 않는다 — M-20)
- 키보드 회피: `KeyboardAvoidingView` 의 `behavior` 를 iOS `padding` / Android `height` 로 분기한다 (M-20).
- 상태바: 밝은 배경이므로 `dark-content`(iOS) / `dark` 아이콘(Android).

### 2.3 텍스트 입력 공통 동작

- 검증 시점: **blur 이후부터** 필드별 오류를 표시한다. 입력 중(타이핑 중)에는 이미 표시된 오류만 실시간으로 해제한다.
  타이핑 도중에 빨간 글씨가 먼저 뜨는 패턴은 쓰지 않는다.
- 제출 버튼 활성 조건은 각 화면에 명시한다. 비활성 버튼은 눌러도 아무 일도 일어나지 않지만
  **숨기지 않는다** — 무엇이 남았는지 화면에서 보이게 한다.
- 서버가 `VALIDATION_FAILED` 로 필드를 지목하면 해당 필드 아래에 서버 `detail` 을 표시한다 (M-13).
  AC-4 가 서버 검증을 요구하는 경우가 여기 해당한다.
- 자동완성: 이메일 iOS `textContentType="username"` / Android `autoComplete="email"`.
  비밀번호는 로그인 `password` / `password`, 가입 `newPassword` / `new-password`.
  삭제 확인은 `password` / `password`.
- 모든 비밀번호 필드는 `secureTextEntry`. 우측에 눈 아이콘 토글을 둔다 (44×44).

### 2.4 오류 표현의 3단계

| 단계 | 형태 | 언제 |
|---|---|---|
| 필드 오류 | 입력란 아래 `BodySmall` `danger` + 입력란 테두리 `danger` | 그 필드 하나가 원인일 때 (AC-2·3·5) |
| 인라인 배너 | 폼 위쪽, `surface` 배경 + `danger` 1px 테두리 + `alert-circle` 아이콘 | 화면 전체에 해당 (AC-10·12·13·17·19) |
| 확인 다이얼로그 | 시스템 모달 | 되돌릴 수 없는 행동 직전 (§8.4, §9.5) |

토스트는 **완료 알림에만** 쓴다 (로그아웃, 계정 삭제). 오류에는 토스트를 쓰지 않는다.

### 2.5 접근성 (모든 화면 공통)

- 모든 터치 대상 **최소 44×44pt**. 시각적으로 작은 요소(체크박스 22×22, "보기" 링크)는 `hitSlop` 으로 확장한다.
- 아이콘 전용 버튼에는 `accessibilityLabel` 을 붙인다: 뒤로가기 "뒤로", 닫기 "닫기",
  비밀번호 표시 토글 "비밀번호 표시" / "비밀번호 숨기기".
- 입력란은 `accessibilityLabel` = 라벨 텍스트, 오류가 있으면 `accessibilityHint` 에 오류 문구를 넣는다.
- 체크박스는 `accessibilityRole="checkbox"` + `accessibilityState={{checked}}`.
  레이블에 필수/선택을 포함해 읽히게 한다 — 예: "필수, 이용약관에 동의합니다, 선택 안 됨".
- 비활성 버튼은 `accessibilityState={{disabled:true}}` 와 함께 남은 조건을 `accessibilityHint` 로 알린다:
  "필수 동의 항목을 모두 선택하면 신청할 수 있어요".
- 오류 배너가 나타나면 `accessibilityLiveRegion="polite"`(Android) / `AccessibilityInfo.announceForAccessibility`(iOS)
  로 읽어준다 (M-20 분기).
- 동적 폰트: 모든 텍스트는 시스템 배율을 따른다. 버튼·입력란·리스트 행의 `height` 는 **최소 높이**로 두고
  내용에 따라 늘어나게 한다. 한 줄 고정 높이를 쓰지 않는다.
- 색만으로 상태를 구분하지 않는다. 오류에는 항상 아이콘 또는 문구가 함께 있다.

### 2.7 문의 블록 — 네 화면이 공유하는 패턴 (AC-38~45)

로그인이 막힌 사용자에게 사람으로 가는 길을 주는 요소다. **네 곳에 같은 형태로 들어간다.**

| 들어가는 곳 | 절 | AC |
|---|---|---|
| 로그인 잠금 배너 | §4.7 | AC-41 |
| `PENDING` 검토 중 | §7.2.2 | AC-40 |
| `REJECTED` 승인 안 됨 | §7.3.1 | AC-38 |
| `SUSPENDED` 이용 정지 | §7.4.1 | AC-39 |

#### 2.7.1 주소의 출처

- 문의 주소는 **서버 응답에 담겨 오는 값**이다. 앱이 하드코딩하거나 조합하지 않는다 (AC-42 / C-8 / M-18).
- 서버는 이 값을 **설정값(`SUPPORT_CONTACT_EMAIL`)에서 읽는다.** 사용자 레코드(`ADMIN` 계정 이메일)에서
  가져오지 않는다 (2026-08-25 확정 — PRD 제약 참조). **앱 쪽 요건은 이 변경과 무관하게 그대로다** —
  앱은 어느 쪽이든 응답에 실려 온 문자열 하나를 렌더할 뿐이다.
- 앱은 이 값을 **단수 문자열 하나**로 다룬다. 여러 주소를 나열하는 UI 를 만들지 않는다 (AC-45).
  응답이 배열로 오는 일은 없다 — 어떤 주소를 쓸지는 전적으로 서버가 정한다.
- 주소 문자열을 앱에서 가공하지 않는다 — 도메인만 잘라 보여주거나 마스킹하지 않는다.
- 어떤 화면에도 `{{ }}` 자리표시자를 남기지 않는다. 값이 없으면 §2.7.3 으로 떨어진다.

#### 2.7.2 값이 있을 때의 구성

문구에 주소를 **문장 안으로 넣지 않는다.** 주소를 자기 줄에 두면 값이 없을 때 그 줄만 통째로
바꿔 끼울 수 있고, 사용자가 주소를 눈으로 찾기도 쉽다.

```
제목                                    ← Title / ink (화면마다 다름)
본문                                    ← BodySmall / ink-body (주소를 포함하지 않는다)

┌ Layout/ContactRow ──────────────────────────┐
│ ✉  admin@planbee.app              문의하기 › │   ← surface + border 1px, 라운드 12, 최소 높이 44
└──────────────────────────────────────────────┘
[ 문의하기 ]                            ← §7.3.1 · §7.4.1 만. Button/Secondary
```

주소 행은 `Layout/ContactRow` 컴포넌트다 (§10.3). 아이콘 `mail` 16 / `ink-muted`,
주소 BodySmall / `ink` · 600, 우측 슬롯에 "문의하기" 텍스트 버튼.

행의 배경은 **놓이는 자리에 따라 뒤집는다** — 행이 배경에서 떠 보여야 하기 때문이다.

| 놓이는 곳 | 행 배경 |
|---|---|
| 화면 배경 위 (§7.2.2 `PENDING`) | `surface` + `border` 1px |
| `surface` 카드 안 (§7.3.1, §7.4.1, §4.7 잠금 배너) | `background` + `border` 1px |
`REJECTED`·`SUSPENDED` 는 카드 안에 `Button/Secondary` "문의하기" 를 한 번 더 두어
액션의 무게를 높이고, `PENDING`(§7.2.2)과 잠금 배너(§4.7)는 행 안의 텍스트 버튼만 쓴다.

- 주소 텍스트는 **선택·복사 가능**하게 둔다 (메일 앱이 없는 기기의 최후 수단 — §7.5).
- "문의하기" 는 메일 작성기를 연다. 받는 사람은 서버가 준 주소, 제목은 화면별로 다르다.
- 주소 행은 최소 높이 44, 탭하면 "문의하기" 와 같은 동작을 한다.
- `accessibilityLabel` 은 "문의 이메일 주소, {주소}". 주소를 한 글자씩 읽지 않도록
  스크린리더에는 원문 그대로 넘긴다.

#### 2.7.3 값이 없을 때 — AC-43 · AC-44

서버가 문의 주소를 내리지 못한 경우다 (설정값 미입력, 조회 실패 등).

- **주소 행과 "문의하기" 를 렌더하지 않는다.** 빈 줄이나 회색 자리표시자를 남기지 않는다.
- 그 자리에 대체 안내 한 줄을 넣는다 (Caption / `ink-muted`):
  **"문의 창구를 준비하고 있어요. 조금 뒤에 다시 확인해 주세요."**
- **화면의 나머지는 전부 그대로다** (AC-44). 제목·본문·정보 카드·주 버튼("로그인 화면으로")이
  정상 표시되고 사용자는 로그인 화면으로 나갈 수 있다.
- 이 상황을 **오류로 처리하지 않는다.** 오류 배너·토스트·재시도 버튼을 띄우지 않고,
  화면을 오류 화면으로 대체하지 않으며, 로딩 상태로 붙잡아 두지 않는다.
  사용자 입장에서는 "문의 창구가 아직 없는 정상 화면"이다.
- 잠금 배너(§4.7)에서도 같다 — 남은 시간 안내는 그대로 표시되고 문의 줄만 대체 안내로 바뀐다.

## 3. 화면: 스플래시 / 세션 복원 (`SplashScreen`)

### 3.1 진입

앱 콜드 스타트 시 항상. 사용자가 직접 이동할 수 없다.

### 3.2 구성

세로 중앙 정렬, 배경 `background`.

```
        [ AI/Identity 마크 44×44 ]
                 (16)
              Planbee                 ← H1 / ink
                 (8)
   계획이 바뀌어도 괜찮아요.              ← BodySmall / ink-muted, 2줄 중앙 정렬
   Planbee가 다음 계획을 찾아드릴게요.
                 (32)
        [ 로딩 인디케이터 ]
```

로딩 인디케이터는 `AI/Identity` 육각형 마크의 은은한 펄스(투명도 0.4↔1.0, 1.2초)로 표현한다.
새 애니메이션 라이브러리는 도입하지 않는다 — `Animated` 의 opacity 루프면 충분하다
(`mobile.md` 미확정 항목: reanimated 미도입).

### 3.3 상태

| 상태 | 화면 | 다음 |
|---|---|---|
| **로딩** (기본) | 위 구성 그대로. 문구 변화 없음 | 판정 완료까지 |
| **정상** | 화면 유지, 즉시 전환 | Home (AC-20) |
| **비어있음** — 저장된 토큰 없음 | 화면 유지, 즉시 전환. 배너 없음 | Login (AC-21) |
| **오류 A** — 갱신 거부(만료·재사용·로그아웃된 기기) | 화면 유지, 즉시 전환. 저장된 토큰을 지운다 | Login + 배너 (AC-23·24·25) |
| **오류 B** — 네트워크 오류 | 아래 §3.4 | Splash 유지 |

전환은 300ms 페이드. 인위적인 최소 노출 시간을 두지 않는다 — 빠르면 빠른 대로 넘어간다.

### 3.4 오류 B — 네트워크 끊김

로딩 인디케이터를 아래 블록으로 교체한다. **저장된 토큰을 지우지 않는다.**
연결이 불안정하다는 이유로 사용자를 로그아웃시키지 않는다.

```
        [ wifi-off 아이콘 24, ink-muted ]
                 (12)
       "연결을 확인해 주세요"              ← Title / ink
                 (4)
  "네트워크에 연결되면 이어서 진행할게요."     ← BodySmall / ink-muted
                 (24)
        [ Button/Primary  "다시 시도" ]
                 (12)
        [ 텍스트 버튼  "로그인 화면으로" ]     ← BodySmall / ink-muted, 밑줄 없음
```

"다시 시도" 는 세션 복원을 재시도한다. "로그인 화면으로" 는 토큰을 **지우지 않은 채** 로그인 화면으로
보낸다 (사용자가 다른 계정으로 들어가려는 경우). 이후 로그인에 성공하면 기존 토큰은 새 토큰으로 대체된다.

> 이 상태는 PRD 의 AC 가 명시하지 않은 경로다. AC-20 과 AC-21 사이에 "토큰은 있는데 확인할 수 없는"
> 구간이 실재하므로 설계에 포함했다. §14 에 기록해 둔다.

### 3.5 접근성

- 화면 진입 시 `accessibilityLiveRegion` 으로 "Planbee 를 준비하고 있어요" 를 한 번 읽는다.
- 로딩 인디케이터에는 `accessibilityLabel="불러오는 중"`.
- 애니메이션은 "동작 줄이기"(Reduce Motion) 설정이 켜져 있으면 정지 상태로 표시한다.

**충족 AC**: AC-20, AC-21, AC-23, AC-24, AC-25

## 4. 화면: 로그인 (`LoginScreen`)

### 4.1 진입

Splash 판정 결과 / 로그아웃 / 계정 삭제 완료 / 상태 안내 화면의 "로그인 화면으로" / 세션 강제 종료.

### 4.2 구성

```
[ 상단 안전영역 ]
   (40)
Planbee                                  ← Brand/Logo (마크 + 워드마크)
   (8)
"계획이 바뀌어도 괜찮아요."                  ← Body / ink-muted
   (32)

[ 세션 배너 자리 — §4.3, 해당 시에만 ]
[ 오류 배너 자리 — §4.6, 해당 시에만 ]

[ 입력: 이메일 ]                          ← Input/TextField
   (16)
[ 입력: 비밀번호 ]                        ← Input/TextField (secure + 표시 토글)
   (24)
[ Button/Primary  "로그인" ]
   (20)
──────────────  또는  ──────────────      ← 구분선 + Caption / ink-muted
   (20)
[ Button/Secondary  "가입 신청하기" ]       ← 좌측 아이콘 없음
   (16)
"Planbee는 승인제로 운영돼요.
 가입을 신청하면 관리자가 확인한 뒤 알려드려요."   ← Caption / ink-muted, 중앙 정렬
[ 하단 안전영역 ]
```

"승인제로 운영돼요" 안내를 로그인 화면에 두는 이유: 승인 대기 상태를 처음 만나는 시점이 가입 직후이므로,
그 전에 기대를 맞춰 둔다. (이용약관 제4조 1항과 같은 사실)

### 4.3 세션 배너 (화면 상단, 폼 위)

| 사유 | 아이콘 | 문구 | AC |
|---|---|---|---|
| 리프레시 만료(14일) | `clock` / `ink-muted` | **"다시 로그인해 주세요"** / 부연 "오랫동안 앱을 열지 않아 자동으로 로그아웃됐어요." | AC-25 |
| 리프레시 재사용·강제 폐기 | `shield-alert` / `danger` | **"보안을 위해 모든 기기에서 로그아웃했어요. 다시 로그인해 주세요."** | AC-24 |

배너는 `cream` 배경 + `border` 1px + 라운드 16 + 패딩 16. 보안 배너만 테두리를 `danger` 로 한다.
배너에는 닫기(×) 버튼을 두고, 사용자가 로그인 입력을 시작하면 자동으로 사라진다.

토스트로 보여주는 경우: 로그아웃 완료 "로그아웃했어요" (§8.4), 계정 삭제 완료 "계정이 삭제되었어요" (§9.6).
토스트는 2초 후 자동으로 사라지고 배너와 동시에 뜨지 않는다.

### 4.4 입력 필드

| 필드 | 라벨 | 플레이스홀더 | 키보드 | 검증 |
|---|---|---|---|---|
| 이메일 | "이메일" | "name@example.com" | `email-address`, 자동 대문자 끄기, 자동 수정 끄기 | 비어있지 않을 것 |
| 비밀번호 | "비밀번호" | "비밀번호" | 기본, `secureTextEntry` | 비어있지 않을 것 |

로그인 화면에서는 **형식·정책 검증을 하지 않는다.** 형식이 틀린 이메일도 그대로 서버에 보내고
AC-12/13 과 같은 응답을 받는다. 앱이 "이 이메일은 형식이 틀렸으니 가입도 안 돼 있겠네" 를
추론해 다른 문구를 보여주면 계정 존재 여부 노출과 같은 결과가 된다.

- 필드가 비었을 때만: blur 시 "이메일을 입력해 주세요" / "비밀번호를 입력해 주세요"
- 이메일 필드 리턴 키 → 비밀번호 필드로 포커스. 비밀번호 필드 리턴 키(`done`) → 제출.

### 4.5 "로그인" 버튼 상태

| 상태 | 표현 |
|---|---|
| 비활성 | 두 필드 중 하나라도 비었을 때. 배경 `border`, 라벨 `ink-muted` |
| 활성 | 배경 `ink`, 라벨 `on-dark` |
| 제출 중 | 배경 `ink` 유지, 라벨 **"로그인 중…"**, 좌측에 24px 스피너(`on-dark`), 버튼과 두 입력란 모두 비활성. 중복 제출 차단 |

### 4.6 오류 상태 — 전부 인라인 배너

배너는 폼 위에 나타나고, 사용자가 어느 필드든 수정하기 시작하면 사라진다.
**어떤 경우에도 입력한 이메일은 지우지 않는다.** 비밀번호는 지운다.

| # | 상황 | 아이콘 | 배너 문구 | 부연 | AC |
|---|---|---|---|---|---|
| 1 | 잘못된 비밀번호 | `alert-circle` / `danger` | **"이메일 또는 비밀번호를 확인해 주세요"** | 없음 | AC-12 |
| 2 | 등록되지 않은 이메일 | `alert-circle` / `danger` | **"이메일 또는 비밀번호를 확인해 주세요"** | 없음 | AC-13 |
| 3 | 삭제된 계정으로 로그인 | `alert-circle` / `danger` | **"이메일 또는 비밀번호를 확인해 주세요"** | 없음 | AC-31 |
| 4 | 로그인 시도 초과 (잠금) | `lock` / `danger` | §4.7 | §4.7 | AC-17 |
| 5 | 서버 500 | `alert-circle` / `danger` | **"잠시 후 다시 시도해 주세요"** | 배너 우측에 텍스트 버튼 **"다시 시도"** | AC-19 |
| 6 | 네트워크 끊김 | `wifi-off` / `ink-muted` | **"연결을 확인해 주세요"** | 배너 우측에 텍스트 버튼 **"다시 시도"** | AC-10 계열 |

**1·2·3 은 문구·아이콘·레이아웃·표시 시간이 완전히 동일해야 한다.** 응답 시간 차이도 노출 요소이므로
앱은 로딩 표시를 응답 도착 즉시가 아니라 **최소 400ms 유지 후** 해제한다. 세 경우 모두 같은 규칙을 적용한다.
개발자는 이 세 가지를 분기하지 말고 하나의 코드 경로로 처리한다 (서버 `code` 도 동일해야 한다 — tech-lead).

배너 5·6 의 "다시 시도" 는 직전 요청을 같은 입력으로 재전송한다. 비밀번호 필드를 비웠으므로
5·6 의 경우에 한해 비밀번호를 **유지**한다 (자격 증명 오류가 아니므로 지울 이유가 없다).

### 4.7 잠금 상태 (AC-17) — 막다른 길이 되지 않게

잠금 응답을 받으면 다음 배너를 표시한다. 남은 시간(분)은 **서버가 내려준 값을 그대로 렌더**한다.
앱에서 카운트다운을 계산하거나 타이머를 돌리지 않는다 (M-18).

```
┌────────────────────────────────────────────┐
│ 🔒  로그인을 잠시 제한했어요                    │
│                                             │
│  비밀번호를 여러 번 잘못 입력해서 잠시 동안       │
│  로그인을 막아 뒀어요. 남은 시간이 지나면        │
│  다시 시도할 수 있어요.                        │
│                                             │
│  남은 시간 약 {서버가 내려준 분}분              │
│                                             │
│  비밀번호가 기억나지 않으면 지금은 앱에서         │
│  직접 바꿀 수 없어요. 아래로 알려주시면          │
│  확인 후 도와드릴게요.                          │
│                                             │
│  ✉ {서버가 내려준 문의 주소}      [ 문의하기 ]  │
└────────────────────────────────────────────┘
```

- 제목: **"로그인을 잠시 제한했어요"** (Title / `ink`)
- 본문: **"비밀번호를 여러 번 잘못 입력해서 잠시 동안 로그인을 막아 뒀어요. 남은 시간이 지나면 다시 시도할 수 있어요."**
  — **정책 수치(10분)를 문구에 넣지 않는다.** 잠금 시간이 바뀌어도 문구를 고칠 필요가 없어야 하고,
  구체적인 시간은 아래 "남은 시간" 줄이 서버 값으로 이미 말하고 있다 (C-8 / M-18).
- 남은 시간: **"남은 시간 약 N분"** (Title / `danger`) — `N` 은 서버가 내려준 정수.
  서버가 **올림하고 최소 1분**을 보장하므로 "약 0분" 은 나오지 않는다 (PRD 제약).
- 안내: **"비밀번호가 기억나지 않으면 지금은 앱에서 직접 바꿀 수 없어요. 아래로 알려주시면 확인 후 도와드릴게요."**
- 문의 블록: §2.7 형식. 주소 행(mail 아이콘 + 서버가 준 주소)과 우측 텍스트 버튼
  **"문의하기"** → 메일 작성기 (제목 `[Planbee] 로그인 문의`). AC-41.
- 주소를 받지 못했으면(AC-43) 주소 행과 "문의하기" 대신
  **"문의 창구를 준비하고 있어요. 조금 뒤에 다시 확인해 주세요."** 한 줄. 배너의 제목·본문·남은 시간은
  그대로 남고 로그인 폼도 계속 조작할 수 있다 (AC-44).

설계 의도:
1. **"5회" 라는 정확한 횟수를 문구에 쓰지 않는다.** 공격자에게 임계값을 알려줄 이유가 없고,
   실패한 사용자에게도 도움이 되지 않는다. "여러 번" 으로 적는다.
2. **끝이 있다는 것을 먼저 말한다.** "잠시 동안" 과 "남은 시간 약 N분" 을 함께 두어
   기다리면 풀린다는 사실이 문장 첫머리에서 읽히게 한다. 수치는 서버가 내린 남은 시간
   하나로만 말한다 — 문구에 박은 "10분" 과 서버 값이 어긋나는 일을 만들지 않는다.
3. **재설정이 없다는 사실을 숨기지 않고, 그 자리에서 대안을 준다.** 비밀번호 재설정이 범위 밖이라
   시간 경과 외의 해제 수단이 없으므로, 사람에게 닿는 경로(문의하기)를 배너 안에 둔다.
   "고객센터에 문의하세요" 같은 지시만 남기고 경로를 안 주면 그게 막다른 길이다.
4. 입력란과 "로그인" 버튼을 **비활성화하지 않는다.** 잠금이 이미 풀렸을 수 있으므로 사용자가
   다시 눌러 확인할 수 있어야 한다. 다시 눌러 아직 잠겨 있으면 배너의 남은 시간이 갱신된다.
   **이 재시도는 잠금을 연장하지 않는다** (AC-48) — 서버가 잠금을 먼저 확인하고 비밀번호를
   검증하지 않으므로 실패 카운터가 늘지 않는다. 이 보장이 없으면 3번의 "기다리면 풀린다" 가
   거짓말이 되고, 확인하려고 누를수록 잠금이 길어진다.

문의 주소는 서버가 잠금 응답에 담아 내려주는 값이다 (§2.7.1 / AC-42). 앱이 상수로 갖고 있지 않다.

잠금 응답은 **계정이 존재하지 않는 이메일에도 똑같이 온다** (AC-47). 앱은 이 둘을 구분할 수
없고 구분하려 해서도 안 된다 — §4.6 의 1·2·3 을 하나의 코드 경로로 처리하는 것과 같은 이유다.

### 5.3 입력 필드 상세

#### 이메일

| 항목 | 값 |
|---|---|
| 라벨 | "이메일" |
| 플레이스홀더 | "name@example.com" |
| 도움말 (기본 표시) | "로그인할 때 쓰는 주소예요." — Caption / `ink-muted` |
| 키보드 | `email-address`, 자동 대문자·자동 수정 끄기 |
| 검증 | `local@domain` 형식 (`@` 앞뒤 비어있지 않음, 도메인에 `.` 포함) |
| 비었을 때 (blur) | "이메일을 입력해 주세요" |
| 형식 오류 (blur) | **"이메일 형식이 올바르지 않아요"** (AC-5) |
| 중복 (서버 응답) | **"이미 가입 신청된 이메일입니다"** (AC-2) |

AC-2 는 서버 응답으로만 알 수 있으므로 제출 시점에 판정된다. 이 오류는 **화면을 이동시키지 않고**
이메일 필드 아래에 표시하며, 이메일 필드로 포커스를 옮기고 스크롤한다.
다른 입력값(비밀번호·가입 사유·동의)은 **그대로 유지한다.**

AC-32 (삭제한 이메일로 재신청)에서는 이 오류가 나오지 않고 정상 접수된다 — 앱 쪽 분기는 없다.

#### 비밀번호

| 항목 | 값 |
|---|---|
| 라벨 | "비밀번호" |
| 플레이스홀더 | "비밀번호" |
| 도움말 (기본 표시, 회색) | **"영문과 숫자를 포함해 8자 이상"** — Caption / `ink-muted` |
| 검증 | 길이 ≥ 8 **그리고** 영문 1자 이상 **그리고** 숫자 1자 이상 |
| 정책 미충족 (blur) | 같은 문구 **"영문과 숫자를 포함해 8자 이상"** 이 Caption / `danger` 로 바뀌고 입력란 테두리가 `danger` |
| 서버 검증 실패 (AC-4) | 서버 `errors[]` 의 `password` 항목 `detail` 을 같은 자리에 표시 |
| 표시 토글 | 우측 눈 아이콘 (44×44) |

문구를 도움말과 오류에서 **같게** 유지하는 이유: AC-3 이 요구하는 문구는 하나뿐이고,
정책을 먼저 알려준 뒤 같은 문장이 빨갛게 변하는 편이 "무엇이 틀렸는지" 를 다시 읽게 하지 않는다.

비밀번호 확인 필드는 **두지 않는다.** 표시 토글이 있고, 재설정 수단이 없는 상황에서 확인 필드는
오타를 잡아주지 못하면서(같은 오타를 두 번 치는 경우가 흔하다) 이탈만 늘린다.

#### 가입 사유

| 항목 | 값 |
|---|---|
| 라벨 | "가입 사유" + 우측에 "선택" 배지 |
| 플레이스홀더 | "어떤 상황에서 Planbee를 쓰고 싶은지 알려주세요." |
| 입력 형태 | 멀티라인, 최소 3줄 높이(약 96), 내용에 따라 최대 6줄까지 확장 후 내부 스크롤 |
| 최대 길이 | **100자.** `maxLength=100` 으로 101번째 글자 입력을 차단한다 (AC-9) |
| 카운터 | 입력란 우측 아래 `0/100` → `100/100`. Caption / `ink-muted`, 100 도달 시 `brand-dark` |
| 도움말 | "승인 심사에 참고해요. 100자까지 쓸 수 있어요." — Caption / `ink-muted` |

AC-9 동작: 100자 상태에서 한 글자를 더 입력하면 **입력이 반영되지 않고 카운터는 `100/100` 을 유지**한다.
오류 문구를 띄우지 않는다 (차단 자체가 피드백이다). 붙여넣기로 100자를 초과하면 앞에서부터 100자만 반영한다.
한글 조합 중(IME)에도 100자를 넘기지 않도록 조합 완료 문자열 기준으로 자른다 — iOS·Android 양쪽에서 확인한다 (M-20).

> **가입 사유는 제출 버튼 활성 조건이 아니다.** AC-1 과 AC-6 이 활성 조건으로 지목한 것은
> 이메일·비밀번호·필수 동의 3건뿐이다. `docs/legal/privacy-policy.md` 1항도 가입 사유를
> **선택 항목**으로 두고 있어 두 문서가 일치한다 (2026-08-23 확정 — §14 항목 1 해소).

### 5.4 동의 블록 (AC-6 · AC-7 · AC-8 · AC-33)

필수와 선택의 구분이 **한눈에** 보여야 한다. 세 가지 신호를 겹쳐 쓴다.

1. **배지** — 라벨 앞에 `[필수]` / `[선택]` 칩. 필수는 `brand-light` 배경 + `brand-dark` 텍스트,
   선택은 투명 배경 + `border` 1px + `ink-muted` 텍스트. 둘 다 Caption 크기, 라운드 999.
2. **순서** — 필수 3건이 위, 선택이 아래. 필수 그룹과 선택 항목 사이에 8px 추가 여백.
3. **하단 안내 문구** — "필수 항목에 동의해야 가입을 신청할 수 있어요."

#### 전체 동의 행

```
[ ☑ ]  전체 동의                                       ← Title / ink
       선택 항목을 포함해 모두 동의합니다.                  ← Caption / ink-muted
```

- 체크박스 22×22, 행 전체 높이 최소 56, 행 전체가 터치 영역.
- 체크 시 4개 항목 모두 체크. 해제 시 4개 모두 해제.
- 개별 항목을 하나라도 해제하면 "전체 동의" 는 자동으로 해제된다.
- 4개 모두 개별 체크되면 "전체 동의" 는 자동으로 체크된다.
- 전체 동의 행과 개별 항목 사이에 1px `border` 구분선.

#### 개별 항목

| # | 배지 | 레이블 | 버전 표기 | "보기" | AC |
|---|---|---|---|---|---|
| 1 | 필수 | **"이용약관에 동의합니다"** | "v1.0" (레이블 뒤, Caption / `ink-muted`) | 있음 → `terms` (§6) | AC-6, AC-8, AC-33 |
| 2 | 필수 | **"개인정보 수집·이용에 동의합니다"** | "v1.0" | 있음 → `privacy` (§6) | AC-6, AC-8, AC-33, AC-34 |
| 3 | 필수 | **"만 14세 이상입니다"** | 없음 | 없음 | AC-6 |
| 4 | 선택 | **"마케팅·알림 수신에 동의합니다"** | 없음 | 없음 | AC-7 |

- 레이블이 한 줄에 들어가지 않으면 **두 줄로 줄바꿈**하고, 버전 표기와 "보기" 는 제자리를 지킨다.
  레이블을 줄여 쓰거나 말줄임으로 자르지 않는다 — 동의 대상이 무엇인지가 잘려서는 안 된다.
- 항목 3 부연(Caption / `ink-muted`): "만 14세 미만은 가입할 수 없어요."
- 항목 4 부연(Caption / `ink-muted`): "동의하지 않아도 서비스를 이용할 수 있어요."
  (개인정보 처리방침 7항과 같은 내용)
- 버전 문자열 `v1.0` 은 **번들된 문서에서 읽어온 값**을 표시한다. 하드코딩하지 않는다.
  AC-8 이 저장하는 버전, AC-36 이 표시하는 버전과 같은 출처여야 한다.
- "보기" 는 우측 정렬, `chevron-right` 아이콘 포함, 최소 44×44 터치 영역.
  **"보기" 탭은 체크 상태를 바꾸지 않는다.** 체크박스와 링크의 터치 영역이 겹치지 않게 분리한다.
- 항목 4 에 "보기" 가 없는 이유: 마케팅·알림 수신에 대응하는 별도 문서가 저장소에 없다.
  알림 발송 인프라 자체가 범위 밖이므로 지금은 문서를 만들지 않고 부연 한 줄로 대신한다.

#### 동의 이력 (AC-8)

화면의 체크박스는 4개지만 **저장되는 형태는 두 종류로 갈린다** (2026-08-25 확정).

| 화면 항목 | 저장 형태 | 약관 버전 |
|---|---|---|
| 이용약관 | 동의 이력 `TERMS` | `v1.0` (번들 문서에서 읽음) |
| 개인정보 수집·이용 | 동의 이력 `PRIVACY` | `v1.0` (번들 문서에서 읽음) |
| 마케팅·알림 수신 | 동의 이력 `MARKETING` | **비어 있음** — 대응 문서가 아직 없다 (§14 항목 5) |
| 만 14세 이상 | **동의 이력이 아니다.** 자기 확인(attestation) — 확인 시각만 남긴다 | 해당 없음 |

만 14세 항목을 동의 이력에서 빼는 이유: 이건 약관에 대한 동의가 아니라 사용자가 자기 나이를
신고하는 행위다. 대응하는 문서가 존재하지 않으므로 "동의한 약관의 버전" 이라는 값이 성립하지 않는다.
동의 이력에 억지로 넣으면 버전이 빈 행이 생기고, `docs/legal/privacy-policy.md` 1항이 "동의 이력" 을
설명하는 문장도 부정확해진다.

동의 이력 3종은 **체크하지 않은 경우에도 "동의하지 않음" 으로 함께 보낸다** — 나중에 "동의를 받은
적이 없다" 와 "거부했다" 를 구분할 수 있어야 한다. 특히 `MARKETING` 은 정보통신망법상 광고성 정보를
보낼 때 동의 여부와 시각을 증빙해야 하므로 거부 이력도 남아야 한다.

**화면 동작은 이 구분에 영향받지 않는다** — 사용자에게는 여전히 체크박스 4개이고 §5.4 의
전체 동의·개별 체크 규칙도 그대로다. 필드 이름과 형태는 tech-lead 가 정한다.

### 5.5 "가입 신청하기" 버튼

| 상태 | 조건 | 표현 |
|---|---|---|
| 비활성 | 이메일 형식 오류 / 비밀번호 정책 미충족 / 필수 동의 3건 중 하나라도 미체크 (AC-3·5·6) | 배경 `border`, 라벨 `ink-muted`. `accessibilityHint` 로 남은 조건 안내 |
| 활성 | 위 조건 모두 충족. **선택 동의와 가입 사유는 조건이 아니다** (AC-7) | 배경 `ink`, 라벨 `on-dark` |
| 제출 중 | — | 라벨 **"신청 중…"** + 스피너, 모든 입력·체크박스 비활성 |

비활성 사유가 여러 개일 때 `accessibilityHint` 는 위에서부터 첫 번째 미충족 항목 하나만 읽는다:
"이메일 형식을 확인해 주세요" / "비밀번호 조건을 확인해 주세요" / "필수 동의 항목을 모두 선택해 주세요".

### 5.6 오류 상태

| 상황 | 표현 | 입력값 | AC |
|---|---|---|---|
| 이메일 중복 | 이메일 필드 오류 "이미 가입 신청된 이메일입니다" + 해당 필드로 스크롤·포커스 | 전부 유지 | AC-2 |
| 서버 필드 검증 실패 | 서버 `errors[]` 를 필드별로 매핑해 표시 | 전부 유지 | AC-4 |
| 네트워크 끊김 | 폼 위 배너, `wifi-off` / `ink-muted`, **"연결을 확인해 주세요"** + 부연 "입력한 내용은 그대로 있어요. 연결 후 다시 신청해 주세요." + 텍스트 버튼 "다시 시도" | **전부 유지 — 이메일·비밀번호·가입 사유·체크 상태 모두** | AC-10 |
| 서버 500 | 폼 위 배너, `alert-circle` / `danger`, **"잠시 후 다시 시도해 주세요"** + 텍스트 버튼 "다시 시도" | 전부 유지 | AC-19 계열 |

AC-10 이 요구하는 "입력한 값이 그대로 남는다" 는 **비밀번호와 체크박스를 포함한다.** 폼 상태를
화면 컴포넌트 안에 유지하고, 오류 처리 과정에서 초기화하지 않는다. 화면을 리마운트하는 처리를 쓰지 않는다.

### 5.7 이탈 확인

입력이 하나라도 있는 상태에서 뒤로가기(또는 안드로이드 하드웨어 백)를 하면 시스템 다이얼로그:

- 제목: **"작성 중인 내용을 지울까요?"**
- 본문: **"지금 나가면 입력한 내용이 사라져요."**
- 버튼: **"나가기"**(destructive) / **"계속 작성"**(cancel)

"보기" 로 약관 모달을 열었다 닫는 경우에는 이 다이얼로그를 띄우지 않는다.

### 5.8 네 가지 상태 요약

| 상태 | 내용 |
|---|---|
| 로딩 | §5.5 제출 중 — "신청 중…" + 스피너, 폼 전체 비활성 |
| 정상 | §5.2 폼. 유효한 입력, 오류 없음 |
| 비어있음 | 화면 진입 직후 = 모든 입력이 비고 체크가 전부 해제된 상태. 버튼 비활성. 오류 문구는 **하나도 표시하지 않는다** (아직 blur 전) |
| 오류 | §5.6 배너 2종 + 필드 오류 4종 |

**충족 AC**: AC-1, AC-2, AC-3, AC-4, AC-5, AC-6, AC-7, AC-8, AC-9, AC-10, AC-32, AC-33, AC-46

## 6. 화면: 약관 전문 뷰어 (`LegalDocumentScreen`)

### 6.1 진입

- 가입 화면 동의 항목의 "보기" (AC-33) — 모달 present
- 설정 → "이용약관" / "개인정보 처리방침" (AC-35) — 모달 present
- 계정 상태 안내 화면의 하단 링크 — 모달 present

파라미터는 문서 종류 하나(`terms` | `privacy`)와 진입 출처(`signup` | `settings` | `status`)다.

### 6.2 본문의 출처 (AC-37)

- 본문은 `docs/legal/terms.md` · `docs/legal/privacy-policy.md` 를 **빌드에 포함한 자산**에서 읽는다.
- **네트워크를 타지 않는다.** 따라서 이 화면에는 로딩 스피너도, 재시도 버튼도, 오프라인 배너도 없다.
  비행기 모드에서 열어도 §6.4 "정상" 과 완전히 같은 화면이 나온다.
- 원격 URL 을 열지 않는다. WebView 로 외부 주소를 로드하는 구현은 AC-37 위반이다.
- 문서의 버전·시행일도 같은 자산에서 읽는다. 화면·동의 이력·문서가 한 값을 공유한다 (AC-8 · AC-36).

### 6.3 구성

```
[ NavBar ]  ✕ 닫기        이용약관
────────────────────────────────────  ← 1px border
   (20)
이용약관                                ← H1 / ink
   (8)
[ v1.0 ]  시행일 {{시행일}}              ← 칩(brand-light/brand-dark, Caption) + Caption / ink-muted
   (20)

[ 개인정보 처리방침일 때만: 요약 카드 — §6.5 ]

──────────────────────────────────── (구분선)
   (20)
   ... 본문 ...                        ← §6.6
   (40)
"이 문서는 앱에 함께 담겨 있어 인터넷 연결 없이도
 볼 수 있어요."                          ← Caption / ink-muted, 중앙 정렬
[ 하단 안전영역 ]

[ 출처가 signup 일 때만 하단 액션 바 — §6.7 ]
```

- 헤더 타이틀: 문서에 따라 "이용약관" / "개인정보 처리방침".
- 스크롤 위치가 최상단이 아니면 NavBar 아래에 1px `border` 구분선을 표시한다.

### 6.4 버전·시행일 표시 (AC-36)

문서 제목 바로 아래, 본문보다 **위**에 둔다.

- 버전 칩: `v1.0` — `brand-light` 배경, `brand-dark` 텍스트, Caption, 라운드 999, 패딩 `[4, 10]`
- 시행일: **"시행일 {{시행일}}"** — Caption / `ink-muted`, 날짜는 `YYYY. M. D.` 로 표기 (`common.md` C-2 로컬 포맷)

`{{시행일}}` 이 아직 비어 있는 동안(ASK 1)에는 **"시행일 준비 중"** 으로 표시한다.
버전 칩은 항상 표시한다 — `v1.0` 은 이미 확정값이다.

### 6.5 개인정보 처리방침 요약 카드 (AC-34)

AC-34 는 네 가지가 **모두 표시**될 것을 요구한다. 긴 본문 안에 흩어져 있으면 "표시되었다" 고 보기 어려우므로,
본문 위에 4행 요약 카드를 둔다. 내용은 `docs/legal/privacy-policy.md` 에서 그대로 가져온 것이고
새로 쓴 문장이 아니다.

카드: `cream` 배경, 라운드 16, `border` 1px, 패딩 16, 행 간격 16.

| 행 제목 (Title / `ink`) | 본문 (BodySmall / `ink-body`) | 출처 |
|---|---|---|
| **"수집 항목"** | "이메일 주소, 비밀번호(암호화 저장), 가입 사유, 동의 이력, 접속 일시, 로그인 실패 횟수" | 처리방침 1항 |

번들된 마크다운을 아래 규칙으로 렌더한다. 원문을 요약하거나 재작성하지 않는다.

선택 가능한 텍스트로만 둔다.

### 6.7 하단 액션 바 — 가입 화면에서 진입한 경우에만

`surface` 배경 + 상단 1px `border`, 패딩 `[12, 20]`, 하단 안전영역 포함.

- `Button/Primary` — **"동의하고 닫기"**
  누르면 이 문서에 대응하는 동의 항목을 체크한 상태로 가입 화면에 돌아간다.
- 상단 NavBar 의 `✕` 는 **체크 상태를 바꾸지 않고** 닫는다.

설정·상태 화면에서 진입하면 하단 액션 바가 없고 `✕` 만 있다 (읽기 전용).

### 6.8 네 가지 상태 요약

| 상태 | 내용 |
|---|---|
| 로딩 | **해당 없음.** 본문이 로컬 자산이라 화면 표시 전에 이미 준비되어 있다. 스피너를 넣지 않는다 (AC-37) |

| 비어있음 | **해당 없음.** 문서는 항상 존재한다. 다만 자산 로드에 실패하는 경우는 아래 오류로 처리 |

- 본문 글자 크기는 시스템 배율을 그대로 따른다. 법정 고지 문서에서 배율을 제한하지 않는다.

## 7. 화면: 계정 상태 안내 (`AccountStatusScreen`)

한 화면 컴포넌트의 **세 변형**이다. 레이아웃은 공유하고 아이콘·색·문구·액션이 다르다.
AC-14·15·16 은 서로 구분 가능해야 하므로 **아이콘 모양 · 아이콘 색 · 제목 문장 · 액션 구성**
네 가지를 모두 다르게 한다.

### 7.1 공통 레이아웃

```
[ 상단 안전영역 ]  (뒤로가기 없음 — 되돌아갈 곳이 없다)
   (48)
        [ Feedback/StatusIcon  72×72 ]     ← 중앙
             (24)
          제목                             ← H1 / ink, 중앙 정렬
             (12)
          본문                             ← Body / ink-body, 중앙 정렬, 2~3줄
             (28)
   ┌─ 강조 카드 (변형에 따라 있음/없음) ─┐
   └────────────────────────────────┘
             (24)
   [ 정보 행 (변형에 따라) ]
             (16)
   [ 문의 줄 — PENDING 만, §7.2.2 ]
             ↓ 남는 공간
   [ 주 버튼 ]
             (12)
   [ 보조 버튼 / 링크 (변형에 따라) ]
[ 하단 안전영역 ]
```

- 제목·본문·강조 카드 본문은 **서버 응답의 문자열을 그대로 렌더**한다 (`common.md` C-8 / M-18).
  앱이 상태 코드로 `switch` 해서 문구를 만들지 않는다. 아래 표는 **서버가 내려야 할 확정 문구**다.
  아이콘·색·버튼 구성은 앱이 상태 값으로 결정한다 (표현 계층).
- **문의 주소도 같은 응답에 담겨 온다** (§2.7.1 / AC-42). 값이 없으면 §2.7.3 의 대체 안내로 바뀌고
  화면의 나머지는 그대로다 (AC-43·AC-44). 세 변형 모두 같은 규칙이다.
- 뒤로가기 제스처·하드웨어 백은 "로그인 화면으로" 와 같은 동작 (§1.3).

### 7.2 변형 A — `PENDING` "검토 중" (AC-1 · AC-14)

| 요소 | 내용 |
|---|---|
| 아이콘 | `hourglass` / 72×72 원형, 배경 `brand-light`, 아이콘 `brand-dark` |
| 제목 | **"가입 신청을 검토하고 있어요"** |
| 본문 | **"관리자가 신청 내용을 확인하고 있어요. 확인에는 시간이 조금 걸릴 수 있어요."** |
| 강조 카드 | 아래 §7.2.1 — **필수** |
| 정보 행 | "신청한 이메일" + 이메일 주소 / "신청일" + `YYYY. M. D.` — `surface` 카드, 라벨 `ink-muted`, 값 `ink` |
| 문의 줄 | 아래 §7.2.2 — 강조 카드보다 **낮은 위계** |
| 주 버튼 | `Button/Primary` **"로그인 화면으로"** |
| 보조 | 없음 |

#### 7.2.1 행동 지시 카드 (AC-14 필수 요건)

사용자에게 가는 알림이 **일절 없으므로**, 다음에 무엇을 해야 하는지가 이 화면에서 가장 눈에 띄어야 한다.
본문보다 시각적 위계를 높인다: `cream` 배경 + `brand` 1px 테두리 + 라운드 16 + 패딩 20.

```
┌──────────────────────────────────────────┐
│  🔔  승인되면 다시 로그인해 주세요            │   ← Title / ink
│                                           │
│  따로 알림을 보내드리지 않아요.               │   ← BodySmall / ink-body
│  나중에 앱을 열어 다시 로그인하면              │
│  승인 여부를 확인할 수 있어요.                │
└──────────────────────────────────────────┘
```

- 제목: **"승인되면 다시 로그인해 주세요"** (아이콘 `bell` / `brand-dark` 20px)
- 본문: **"따로 알림을 보내드리지 않아요. 나중에 앱을 열어 다시 로그인하면 승인 여부를 확인할 수 있어요."**

이 카드는 세 변형 중 `PENDING` 에만 있다. 스크린리더에서는 제목·본문을 한 그룹으로 묶어 읽는다.
**이 카드가 `PENDING` 화면의 주 행동 지시다** — §7.2.2 의 문의 줄이 이 자리를 넘겨받지 않는다.

#### 7.2.2 문의 줄 (AC-40) — 강조 카드보다 한 단계 낮게

`PENDING` 은 `REJECTED`·`SUSPENDED` 와 성격이 다르다. 저 둘은 문의가 **유일한 출구**지만,
`PENDING` 은 기다리면 풀리는 정상 상태다. 그래서 문의 경로를 제공하되(AC-40)
"지금 뭔가 잘못됐으니 연락하라"고 읽히지 않게 위계를 낮춘다.

| | §7.2.2 `PENDING` 문의 줄 | §7.3.1 · §7.4.1 문의 카드 |
|---|---|---|
| 담는 그릇 | 카드 없음. 정보 카드 아래 여백에 놓인 텍스트 줄 | `surface` + `border` 카드, 패딩 20 |
| 제목 | 없음 | 있음 (Title / `ink`) |
| 액션 | 텍스트 버튼 "문의하기" | `Button/Secondary` "문의하기" |
| 배치 | 강조 카드 → 정보 카드 **다음**, 화면 하단 | 본문 바로 아래, 화면 중앙부 |
| 글자 | Caption / `ink-muted` | BodySmall / `ink-body` |

구성 (정보 카드 아래 16, 중앙 정렬):

```
승인이 너무 오래 걸리거나 궁금한 점이 있으면 문의해 주세요.     ← Caption / ink-muted
        ✉ {서버가 내려준 문의 주소}        문의하기            ← §2.7.2 주소 행 + 텍스트 버튼
```

- 안내 문구: **"승인이 너무 오래 걸리거나 궁금한 점이 있으면 문의해 주세요."**
- 주소 행과 "문의하기" 는 §2.7.2 형식. 메일 제목은 `[Planbee] 가입 신청 문의`.
- 주소가 없으면(AC-43) 이 줄 전체가
  **"문의 창구를 준비하고 있어요. 조금 뒤에 다시 확인해 주세요."** 한 줄로 바뀐다.
  강조 카드·정보 카드·주 버튼은 그대로다 (AC-44).
- 화면 진입 시 스크린리더 낭독 순서는 제목 → 본문 → 강조 카드 → 정보 카드 → 문의 줄이다.
  문의 줄을 강조 카드보다 먼저 읽지 않는다.

### 7.3 변형 B — `REJECTED` "승인 안 됨" (AC-15)

| 요소 | 내용 |
|---|---|
| 아이콘 | `user-x` / 72×72 원형, 배경 `surface`, 테두리 `border` 1px, 아이콘 `ink-muted` |
| 제목 | **"가입이 승인되지 않았어요"** |
| 본문 | **"신청 내용을 확인했지만 이번에는 승인되지 않았어요. 이 계정으로는 로그인할 수 없어요."** |
| 강조 카드 | §7.3.1 문의 카드 |
| 정보 행 | 없음 |
| 주 버튼 | `Button/Primary` **"로그인 화면으로"** |
| 보조 | 텍스트 버튼 **"계정 삭제"**(`danger`) → §9 (AC-50) / 텍스트 링크 **"개인정보 처리방침 보기"** → §6 (`privacy`) |

`brand` 계열을 쓰지 않고 중립색(회색 아이콘)으로 처리한다. `danger` 빨강도 쓰지 않는다 —
거절은 사용자의 잘못이 아닐 수 있고, 경고로 읽힐 필요도 없다.

#### 7.3.1 문의 카드 — 거절 계정의 유일한 출구

거절된 계정은 로그인이 막히므로 §9 의 계정 삭제 화면에 **영원히 도달할 수 없다.**
자기 정보를 지우려면 사람에게 연락하는 길밖에 없다. 그 길을 이 화면에 명시한다.
(개인정보 처리방침 6항이 "로그인이 불가능한 상태에서 삭제를 원하는 경우 연락처로 요청" 이라고 이미 약속하고 있다.)

`surface` 배경 + `border` 1px + 라운드 16 + 패딩 20:

- 제목: **"다시 검토받고 싶거나 정보를 지우고 싶다면"** (Title / `ink`)
- 본문: **"가입할 때 쓴 이메일 주소와 함께 아래로 알려주시면 확인 후 도와드릴게요."**
  (BodySmall / `ink-body`)
- 주소 행: §2.7.2 형식 — mail 아이콘 + 서버가 내려준 문의 주소 (AC-38 / AC-42)
- 버튼: `Button/Secondary` **"문의하기"** — 메일 작성기 열기, 제목 `[Planbee] 가입 문의`

주소를 받지 못했으면(AC-43) 주소 행과 버튼을 렌더하지 않고 본문 아래에
**"문의 창구를 준비하고 있어요. 조금 뒤에 다시 확인해 주세요."** 한 줄만 둔다 (Caption / `ink-muted`).
카드 자체는 남긴다 — 제목이 "무엇을 요청할 수 있는지"를 알려주는 정보이기 때문이다.
제목·본문·주 버튼("로그인 화면으로")·보조 링크는 모두 정상 동작한다 (AC-44).

#### 7.3.2 계정 삭제 경로 (AC-50) — 문의에 기대지 않는 출구

거절된 사용자가 자기 정보를 지우는 유일한 길이 "메일을 보내고 답을 기다리는 것" 이면,
App Store 심사지침 5.1.1(v) 가 요구하는 **앱 안에서 삭제를 개시하는 경로**가 없는 셈이다.
AC-43 으로 문의 주소마저 없는 상태에서는 출구가 아예 사라진다.

이 사용자는 **비밀번호를 이미 맞힌 상태**다 — 자격 증명이 아니라 계정 상태 때문에 막혔을 뿐이다.
그래서 §9 의 비밀번호 재확인 흐름을 그대로 재사용할 수 있다.

- 배치: §7.3 의 주 버튼("로그인 화면으로") **아래**, 보조 링크 줄에 함께 둔다.
- 형태: 텍스트 버튼 **"계정 삭제"** (BodySmall / `danger`). `Button/Danger` 를 쓰지 않는다 —
  이 화면의 주 행동은 어디까지나 "로그인 화면으로" 이고, 삭제가 시각적으로 더 무거우면
  거절 통보를 받은 사용자에게 삭제를 권하는 화면처럼 읽힌다.
- 동작: §9 `AccountDeleteScreen` 으로 push. 화면 구성·문구·경고·최종 확인 다이얼로그는
  §9 와 **완전히 같다.** 별도 변형을 만들지 않는다.
- 삭제 완료 후 이동 지점도 §9.6 과 같다 — 로그인 화면으로 스택 교체 + 토스트.
- `accessibilityHint`: "계정을 삭제하는 화면으로 이동합니다. 삭제하면 되돌릴 수 없습니다."

**`SUSPENDED`(§7.4)에는 이 경로를 두지 않는다.** 즉시 파기 + AC-32(같은 이메일 재가입 가능)와
겹치면 정지된 사용자가 계정을 지우고 곧바로 재가입해 정지를 무력화할 수 있다 (PRD 제약).
`SUSPENDED` 의 삭제 요청은 §7.4.1 의 문의 경로로 남는다.

### 7.4 변형 C — `SUSPENDED` "이용 정지" (AC-16)

| 요소 | 내용 |
|---|---|
| 아이콘 | `shield-off` / 72×72 원형, 배경 `surface`, 테두리 `danger` 1px, 아이콘 `danger` |
| 제목 | **"이용이 정지된 계정이에요"** |
| 본문 | **"서비스 운영 정책에 따라 이 계정의 이용이 정지되었어요. 정지 중에는 로그인할 수 없어요."** |
| 강조 카드 | §7.4.1 이의 제기 카드 |
| 정보 행 | 없음 |
| 주 버튼 | `Button/Primary` **"로그인 화면으로"** |
| 보조 | 텍스트 링크 **"이용약관 보기"** → §6 (`terms`) |

세 변형 중 유일하게 `danger` 를 쓴다. `REJECTED`(회색) 와 `SUSPENDED`(빨강) 가
색·아이콘·보조 링크에서 모두 갈린다.

#### 7.4.1 이의 제기 카드

이용약관 제8조 2항이 이의 제기 권리를 명시하고 있으므로 그 경로를 화면에 둔다.

- 제목: **"정지에 이의가 있다면"** (Title / `ink`)
- 본문: **"아래로 알려주시면 확인해 드릴게요. 자세한 기준은 이용약관 제8조에서 볼 수 있어요."**
- 주소 행: §2.7.2 형식 — mail 아이콘 + 서버가 내려준 문의 주소 (AC-39 / AC-42)
- 버튼: `Button/Secondary` **"문의하기"** — 제목 `[Planbee] 이용 정지 문의`

주소를 받지 못했을 때의 처리는 §7.3.1 과 같다 (AC-43·AC-44).

### 7.5 네 가지 상태 요약

| 상태 | 내용 |
|---|---|
| 로딩 | 이 화면 자체는 로그인 응답의 결과로 도달하므로 자체 로딩이 없다. **단** 가입 직후(AC-1) 진입 시에도 이미 응답을 받은 뒤다. "로그인 화면으로" 를 누른 직후 전환 시간에만 버튼이 비활성된다 |
| 정상 | §7.2 / §7.3 / §7.4 세 변형 |
| 비어있음 | 두 경우다. ① **문의 주소가 없는 상태** (AC-43) — §2.7.3 대로 문의 요소만 대체 안내로 바뀌고 화면의 나머지는 정상 (AC-44). 세 변형 모두 같다. ② 서버가 **알 수 없는 상태 값**을 내린 경우 — 제목 **"계정 상태를 확인해 주세요"** / 본문 **"지금은 로그인할 수 없어요. 잠시 후 다시 시도해 주세요."** + 아이콘 `help-circle` / `ink-muted` + "로그인 화면으로" (M-13: 카탈로그에 없는 `code` 는 일반 처리, 앱이 죽지 않는다) |
| 오류 | "문의하기" 를 눌렀는데 메일 앱이 없는 기기: 시스템 다이얼로그 **"메일 앱을 열 수 없어요"** / **"아래 주소로 직접 보내주세요."** + 서버가 준 주소를 본문에 한 줄로 표시 / 버튼 "주소 복사", "확인". iOS·Android 모두 `canOpenURL` 로 먼저 확인한다 (M-20). 주소가 없으면 "문의하기" 자체가 없으므로 이 경로도 발생하지 않는다 |

### 7.6 접근성

- 화면 진입 시 제목을 자동으로 읽는다 (`accessibilityAutoFocus` / `announceForAccessibility`).
- 강조 카드는 하나의 그룹으로 묶어 제목→본문 순으로 읽는다.
- 상태 아이콘에는 `accessibilityLabel` 을 붙이지 않는다 (제목이 같은 정보를 준다 — 중복 낭독 방지).
- 문의 주소 행은 §2.7.2 의 낭독 규칙을 따른다. 주소가 없을 때의 대체 안내도 그대로 읽는다 —
  아무 말 없이 사라지면 스크린리더 사용자는 문의 경로가 있는지조차 알 수 없다.

**충족 AC**: AC-1, AC-14, AC-15, AC-16, AC-38, AC-39, AC-40, AC-42, AC-43, AC-44, AC-45, AC-46, AC-50

## 8. 화면: 설정 (`SettingsScreen`)

### 8.1 진입

Home 하단 탭 "MY" → 우상단 톱니 아이콘, 또는 MY 화면 리스트의 "설정".
(`auth` 는 설정 화면 자체와 그 안의 항목만 정의한다. MY 탭 구성은 범위 밖이다.)

### 8.2 구성

`Layout/NavBar` (뒤로 + 타이틀 "설정") 아래 스크롤 리스트. 섹션 사이 간격 32.

```
[ NavBar ]  ‹ 뒤로          설정
   (24)

계정                                     ← 섹션 헤더 Caption / ink-muted
┌────────────────────────────────────┐
│  이메일                 name@ex.com   │   ← 값 표시 행 (탭 불가)
└────────────────────────────────────┘
   (32)

약관·정책                                 ← 섹션 헤더
┌────────────────────────────────────┐
│  이용약관                      v1.0 › │
│  ──────────────────────────────────  │
│  개인정보 처리방침              v1.0 › │
└────────────────────────────────────┘
   (32)

앱 정보                                  ← 섹션 헤더
┌────────────────────────────────────┐
│  버전                        1.0.0   │
└────────────────────────────────────┘
   (32)

┌────────────────────────────────────┐
│  로그아웃                            │   ← ink, 중앙 정렬 아님(좌측)
└────────────────────────────────────┘
   (12)
┌────────────────────────────────────┐
│  계정 삭제                        ›  │   ← danger
└────────────────────────────────────┘
   (12)
"계정을 삭제하면 되돌릴 수 없어요."          ← Caption / ink-muted
[ 하단 안전영역 ]
```

리스트 카드: `surface` 배경, 라운드 16, `border` 1px. 행 최소 높이 **56**, 좌우 패딩 16,
행 사이 1px `border` 구분선(카드 좌우 끝까지 닿지 않게 좌측 16 들여쓰기).

### 8.3 항목 정의

| 섹션 | 라벨 | 우측 | 동작 | AC |
|---|---|---|---|---|
| 계정 | **"이메일"** | 로그인한 계정의 이메일 (`ink-muted`) | 없음 (탭 불가) | — |
| 약관·정책 | **"이용약관"** | "v1.0" + `chevron-right` | §6 모달 (`terms`, 출처 `settings`) | AC-35 |
| 약관·정책 | **"개인정보 처리방침"** | "v1.0" + `chevron-right` | §6 모달 (`privacy`, 출처 `settings`) | AC-35 |
| 앱 정보 | **"버전"** | 앱 버전 문자열 (`ink-muted`) | 없음 | — |
| — | **"로그아웃"** | 없음 | §8.4 | AC-26, AC-27 |
| — | **"계정 삭제"** | `chevron-right` (`danger`) | §9 로 push | AC-28 |

- "이용약관" / "개인정보 처리방침" 은 App Store 심사지침 5.1.1(i) 대응이므로 **로그인 상태에서
  항상 도달 가능**해야 한다. 다른 화면 뒤에 숨기지 않는다 (AC-35).
- 두 항목의 버전 문자열은 §6.4 와 같은 출처에서 읽는다.
- "계정 삭제" 행은 라벨을 `danger` 로 하고 별도 카드로 분리한다. 다른 항목과 같은 카드에 넣지 않는다.
- "로그아웃" 은 `danger` 가 아니다 — 되돌릴 수 있는 행동이다. 두 행의 위험도가 색으로 구분되어야 한다.

### 8.4 로그아웃 (AC-26 · AC-27)

시스템 확인 다이얼로그:

- 제목: **"로그아웃할까요?"**
- 본문: **"다시 이용하려면 로그인해야 해요."**
- 버튼: **"로그아웃"**(destructive) / **"취소"**(cancel)

"로그아웃" 확인 후:

1. 서버에 로그아웃(그 기기의 리프레시 토큰 폐기)을 요청한다.
2. **응답을 기다리지 않고** 기기의 Keychain/Keystore 토큰을 즉시 삭제한다.
3. react-query 캐시를 전부 비운다.
4. 로그인 화면으로 스택을 교체하고 토스트 **"로그아웃했어요"** 를 2초간 표시한다.

서버가 응답하지 않거나 오류를 내도 **화면 동작과 문구가 완전히 같다** (AC-27).
사용자에게 실패를 알리지 않는다 — 이 기기에서는 실제로 로그아웃되었고, 알려봐야 할 수 있는 일이 없다.
(서버 측 토큰은 14일 뒤 만료된다.)

로그아웃 처리 중(1~3 사이)에는 "로그아웃" 행을 비활성하고 우측에 16px 스피너를 표시한다.
이 구간은 대개 눈에 보이지 않을 만큼 짧다.

### 8.5 네 가지 상태 요약

| 상태 | 내용 |
|---|---|
| 로딩 | 계정 정보(이메일) 조회 중 — "계정" 카드의 값 자리에 폭 140 / 높이 16 의 스켈레톤 바 1개. 나머지 섹션은 즉시 렌더한다 (로컬 값이라 기다릴 이유가 없다) |
| 정상 | §8.2 전체 |
| 비어있음 | **해당 없음.** 항목이 고정되어 있어 비는 경우가 없다 |
| 오류 | 계정 정보 조회 실패 — "이메일" 행의 값 자리에 **"불러오지 못했어요"**(`ink-muted`) + 우측 텍스트 버튼 **"다시 시도"**. **다른 섹션은 정상 동작한다.** 특히 "약관·정책"(AC-35)과 "계정 삭제"(AC-28)는 계정 정보 조회 실패와 무관하게 항상 눌려야 한다. 화면 전체를 오류 화면으로 대체하지 않는다 |

### 8.6 접근성

- 값 표시 행("이메일", "버전")은 `accessibilityRole="text"` 로 두고 버튼으로 읽히지 않게 한다.
- 이동 행은 `accessibilityRole="button"`, 레이블은 "이용약관, 버전 1.0" 처럼 우측 값까지 포함해 읽는다.
- "계정 삭제" 행의 `accessibilityHint`: "계정을 삭제하는 화면으로 이동합니다. 삭제하면 되돌릴 수 없습니다."

**충족 AC**: AC-26, AC-27, AC-28, AC-35

## 9. 화면: 계정 삭제 확인 (`AccountDeleteScreen`)

### 9.1 진입

두 경로가 있고 **화면은 완전히 같다.**

| 출처 | 경로 | AC |
|---|---|---|
| 로그인된 사용자 | 설정 → "계정 삭제" | AC-28 |
| 거절된 사용자 | 계정 상태 안내(`REJECTED`) → "계정 삭제" (§7.3.2) | AC-50 |

두 번째 경로는 **세션(액세스 토큰)이 없는 상태**다. 삭제 요청이 무엇으로 인증되는지는
계약이 정한다 (§14.1). 화면 쪽에서 달라지는 것은 취소·완료 시 돌아가는 곳뿐이고,
구성·문구·경고·최종 확인은 §9.3~§9.6 을 그대로 쓴다.

### 9.2 설계 원칙

즉시 파기이고 유예가 없다. AC-29 의 비밀번호 재확인과 AC-30 의 경고 문구가 **유일한 안전장치**다.
따라서 이 화면은 다음을 지킨다.

- 경고를 화면 **맨 위**에 둔다. 스크롤해야 보이면 안전장치가 아니다.
- 무엇이 지워지는지 항목으로 나열한다. "모든 데이터" 같은 뭉뚱그린 표현을 쓰지 않는다.
- 삭제 버튼은 비밀번호를 입력하기 전까지 **활성되지 않는다.**
- 마지막에 확인 다이얼로그를 한 번 더 둔다.
- 삭제 버튼이 취소 버튼보다 누르기 쉬운 자리에 있지 않게 한다.

### 9.3 구성

```
[ NavBar ]  ‹ 뒤로        계정 삭제
   (24)

┌─ 경고 카드 ────────────────────────────┐   ← surface, danger 1px, 라운드 16, 패딩 20
│  ⚠  삭제하면 되돌릴 수 없습니다            │   ← Title / danger + alert-triangle 20
│                                        │
│  계정을 삭제하면 아래 정보가 즉시 지워져요.   │   ← BodySmall / ink-body
│                                        │
│   ·  이메일 주소                         │   ← BodySmall / ink-body, 항목 간격 8
│   ·  비밀번호                            │
│   ·  가입 사유                           │
│   ·  약관 동의 이력                       │
│   ·  Planbee 이용 기록                   │
│                                        │
│  지운 정보는 복구할 수 없어요.              │   ← BodySmall / ink-body
└────────────────────────────────────────┘
   (20)
"같은 이메일로 다시 가입을 신청할 수는 있어요.
 다만 이전 기록은 되돌아오지 않아요."            ← BodySmall / ink-muted
   (32)

"계속하려면 비밀번호를 입력해 주세요"             ← Title / ink
   (12)
[ 입력: 비밀번호 ]                             ← Input/TextField (secure + 표시 토글)
   (28)
[ Button/Danger  "계정 삭제" ]
   (12)
[ Button/Secondary  "취소" ]
[ 하단 안전영역 ]
```

- **"삭제하면 되돌릴 수 없습니다"** 는 AC-30 이 지정한 문구다. 토씨 그대로 쓴다 (경어체가 아닌 점 포함).
- 삭제 항목 목록은 `docs/legal/privacy-policy.md` 3항·9항이 파기 대상으로 적은 것과 일치시킨다.
- "같은 이메일로 다시 가입을 신청할 수는 있어요" 는 AC-32 가 보장하는 사실을 미리 알려
  불필요한 망설임을 줄인다.
- "취소" 를 삭제 버튼 **아래**에 두되 `Button/Secondary` 로 시각 위계를 낮춘다.
  둘 다 최소 높이 52, 사이 간격 12 로 오탭을 막는다.

### 9.4 비밀번호 필드 (AC-29)

| 항목 | 값 |
|---|---|
| 라벨 | "비밀번호" |
| 플레이스홀더 | "현재 비밀번호" |
| 도움말 | "본인 확인을 위해 한 번 더 입력해 주세요." — Caption / `ink-muted` |
| 자동완성 | iOS `password` / Android `password` |
| 검증 | 비어있지 않을 것. **형식·정책 검증은 하지 않는다** (기존 비밀번호이므로) |
| 비었을 때 | 삭제 버튼 비활성. blur 시 필드 오류를 띄우지 않는다 (버튼 비활성이 이미 신호다) |
| 틀렸을 때 (서버) | 필드 아래 **"비밀번호를 확인해 주세요"** (`danger`). 필드를 비우고 포커스를 유지 |

비밀번호가 비어 있으면 삭제 요청이 **전송조차 되지 않는다** — AC-29 의 "삭제가 실행되지 않는다" 를
클라이언트와 서버 양쪽에서 보장한다.

### 9.5 최종 확인 다이얼로그

"계정 삭제" 를 누르면 요청 전에 시스템 다이얼로그를 한 번 띄운다.

- 제목: **"정말 삭제할까요?"**
- 본문: **"삭제하면 되돌릴 수 없습니다."** (AC-30 문구 재확인)
- 버튼: **"삭제"**(destructive) / **"취소"**(cancel, 기본 포커스)

"취소" 를 누르면 화면에 그대로 머문다. 비밀번호 입력값은 유지한다.

### 9.6 완료

1. 토큰을 Keychain/Keystore 에서 삭제한다.
2. react-query 캐시를 전부 비운다.
3. 로그인 화면으로 스택을 교체하고 토스트 **"계정이 삭제되었어요"** 를 2초간 표시한다.

이후 같은 이메일·비밀번호로 로그인하면 §4.6 의 1·2·3 과 **완전히 같은** 배너를 받는다 (AC-31).
같은 이메일로 가입 신청하면 §5 가 정상 접수한다 (AC-32) — 앱 쪽에 별도 분기가 없다.

### 9.7 네 가지 상태 요약

| 상태 | 내용 |
|---|---|
| 로딩 | 삭제 요청 중 — "계정 삭제" 버튼 라벨 **"삭제 중…"** + 스피너, 버튼·"취소"·입력란 전부 비활성. 이 구간에서는 뒤로가기와 하드웨어 백도 막는다 (중복 요청·중간 이탈 방지) |
| 정상 | §9.3 — 비밀번호 입력 전에는 "계정 삭제" 비활성, 입력 후 활성 |
| 비어있음 | 화면 진입 직후 = 비밀번호가 빈 상태. 경고 카드와 안내는 그대로 보이고 삭제 버튼만 비활성 |
| 오류 | ① 비밀번호 불일치 → §9.4 필드 오류 ② 네트워크 끊김 → 경고 카드 아래 배너 **"연결을 확인해 주세요"** + 부연 "계정은 삭제되지 않았어요. 연결 후 다시 시도해 주세요." ③ 서버 500 → 배너 **"잠시 후 다시 시도해 주세요"** + 부연 "계정은 삭제되지 않았어요." 두 배너 모두 텍스트 버튼 "다시 시도" 를 포함하고, 비밀번호는 **비운다**(재입력 요구) |

②·③ 에서 "계정은 삭제되지 않았어요" 를 반드시 붙인다. 되돌릴 수 없는 행동에서
"실패한 건지 성공한 건지 모르는 상태" 가 가장 나쁘다.

### 9.8 접근성

- 화면 진입 시 경고 카드 제목("삭제하면 되돌릴 수 없습니다")을 먼저 읽는다.
- 삭제 항목 목록은 `accessibilityRole="list"` 로 묶고 항목 수를 함께 읽는다.
- "계정 삭제" 버튼의 `accessibilityLabel` 은 "계정 삭제, 되돌릴 수 없습니다".
- 확인 다이얼로그는 시스템 컴포넌트를 써서 플랫폼 기본 포커스·낭독 동작을 그대로 얻는다.

### 11.5 표기 규칙

- 기본은 "~해요" 체. **예외는 AC-30 의 "삭제하면 되돌릴 수 없습니다" 하나**다.
  PRD 가 지정한 문구이고, 문체가 튀는 것이 오히려 경고로 읽혀 유리하다.
- 느낌표를 쓰지 않는다. 사용자가 실패한 순간에 밝은 척하지 않는다.
- 오류 문구는 원인 → 다음 행동 순서로 쓴다. 원인만 적고 끝내지 않는다.
- "계정이 없습니다", "비밀번호가 틀렸습니다" 처럼 **어느 쪽이 틀렸는지 특정하는 표현을 쓰지 않는다** (AC-13).
- 숫자 단위: 시간은 "분", 글자 수는 "자". 잠금 시간은 항상 "약 N분" (초 단위로 표시하지 않는다).

### 14.1 tech-lead 로 넘기는 사항 (계약 설계 시 참고)

API 스펙은 이 문서가 정하지 않는다. 다만 화면이 성립하려면 다음이 응답에 있어야 한다.

**1. 상태 안내 화면을 완성하는 스키마 하나 (AC-46)**

`PENDING`·`REJECTED`·`SUSPENDED` 화면을 그리는 데 필요한 값을 **재사용 가능한 컴포넌트 하나**로
정의하고, **가입 신청 응답과 로그인 차단 응답이 그것을 함께 참조**한다. 담기는 것:
제목 · 본문 · 강조 카드 제목·본문 · 문의 주소 · 신청 이메일 · 신청일.

가입 직후(AC-1)와 로그인 차단(AC-14·15·16)은 **같은 화면**이므로 스키마가 갈리면 안 된다.
엔드포인트마다 비슷한 필드를 따로 정의하면 §7.1 의 "앱이 문구를 조합하지 않는다" 가 두 곳에서
따로 관리된다. 상태 확인만을 위한 별도 왕복은 만들지 않는다.

**2. 오류 코드의 구분과 동일성**

- 계정 상태 3종은 **서로 구분 가능한** `code` (AC-14·15·16)
- 자격 증명 오류는 **하나의 동일한** `code` (AC-12·13·31)
- **잠금은 계정 존재와 무관하게 동일한 응답** (AC-47) — 미등록 이메일도 같은 `code`·같은 본문
- 검증 실패 시 `errors[]` 의 필드 지목 (`email` / `password`) — AC-4, §2.3

**3. 잠금 응답 (AC-17·41·47·48)**

- **남은 시간(분, 정수)** — 앱이 계산하지 않는다 (§4.7, M-18). 서버가 **올림, 최소 1분**으로 낸다
- 상태 코드는 429 를 권장한다. RFC 표준인 `Retry-After` 헤더(초)를 함께 내릴지 tech-lead 가 정한다
- `docs/api/error-codes.md` 에 429 를 쓰는 코드가 아직 없다 — 공통 표에 없는 상태 코드이므로
  auth 도메인 코드를 등록할 때 함께 정리한다

**4. 문의 이메일 주소 (AC-38~43, §2.7.1)**

상태 안내 3종의 응답과 **로그인 잠금 응답**에 함께 실려야 한다. 요구사항은 세 가지다.

① 앱이 하드코딩하지 않으므로 **응답에 있어야 한다**,
② **단수 값**이어야 한다 — 배열이면 앱이 "하나만 고르는" 규칙을 갖게 되고 그건 AC-45 를
   앱으로 떠넘기는 것이다,
③ **없을 수 있는 값**이다 — 값이 없는 응답도 정상 응답이어야 한다. 설정값이 비었다는 이유로
   상태 안내나 잠금 응답 자체가 오류가 되면 AC-44 가 깨진다.

값의 출처는 **서버 설정값 `SUPPORT_CONTACT_EMAIL`** 이다 (2026-08-25 확정, PRD 제약).
`ADMIN` 계정 이메일을 조회하지 않는다 — 문의 창구가 관리자 계정 존재 여부에 묶이지 않아야 하고,
잠금 응답은 인증되지 않은 사용자에게도 가므로 직원 개인 이메일이 실려서는 안 된다.
필드 이름과 배치는 tech-lead 가 정한다.

**5. 토큰 수명과 회전 (AC-23·24·25·49)**

- 리프레시 14일은 **유휴 만료(sliding)** — 회전할 때마다 새 14일. 절대 만료 상한은 없다
- 회전에 **10초 유예 창** — 그 안의 직전 토큰 재사용은 재사용 감지로 처리하지 않고
  **직전에 발급한 것과 같은 토큰 쌍을 다시 돌려준다** (AC-49). 응답을 캐시해 두는 방식이 된다
- 유예 창을 넘긴 재사용만 AC-23 의 거부와 AC-24 의 **계정 전체 리프레시 폐기**로 이어진다

**6. 동의 이력의 구조 (AC-8, §5.4)**

- 동의 이력은 3종: `TERMS` · `PRIVACY` · `MARKETING`. 항목별로 동의 여부 · 약관 버전 · 동의 시각
- **약관 버전은 nullable** — `MARKETING` 은 대응 문서가 없어 값이 비어 있다
- **만 14세 확인은 동의 이력이 아니다** — 사용자 레코드의 확인 시각 필드

**7. 계정 삭제 (AC-29·50)**

- 로그인된 사용자의 삭제(AC-28·29)와 **`REJECTED` 사용자의 삭제**(AC-50)가 모두 성립해야 한다
- 후자는 **세션(액세스 토큰)이 없는 상태**다. 이메일+비밀번호로 받을지, 로그인 차단 응답에
  단기 스코프 토큰을 실어 그것으로 받을지 tech-lead 가 정한다
- 어느 쪽이든 **비밀번호 재확인 없이는 삭제되지 않아야 한다** (AC-29 를 서버에서도 보장)
- `SUSPENDED` 에는 이 경로를 열지 않는다 (PRD 제약 — 정지 회피)

**8. 가입 엔드포인트 레이트 리밋**

AC-2 가 이메일 중복을 그대로 알려주므로 가입 화면은 계정 열거에 쓰일 수 있다. 메일 인프라가
없어 이 노출 자체는 인수했고(PRD 제약), 대량 자동 열거는 **IP 단위 레이트 리밋**으로 막는다.
구체적인 임계값은 tech-lead 가 정한다.

### 15.3 AC-43 대체 안내 상태를 아트보드 하나로만 그린 이유

`Screen 15a` 는 문의 주소를 받지 못한 상태(AC-43)의 **대표 화면**이다.
`REJECTED`·`SUSPENDED`·로그인 잠금 세 화면도 **같은 형태**로 동작한다 —
주소 행(`Layout/ContactRow`)과 "문의하기" 가 사라지고 그 자리에
**"문의 창구를 준비하고 있어요. 조금 뒤에 다시 확인해 주세요."** 한 줄이 들어가며,
제목·본문·정보 카드·주 버튼은 그대로다 (AC-44).
같은 교체가 네 번 반복될 뿐이라 아트보드를 네 개 그리면 차이 없는 그림이 늘어난다.
Design System 의 `Layout/ContactRow` 에 "주소 있음 / 없음" 두 상태를 함께 두어
교체 지점이 한 곳임을 보이게 했다.

### 15.4 자리표시자 표기

- 약관 전문 뷰어(11a·11b)의 본문은 `docs/legal/` 원본에서 발췌한 일부만 시각화했다 —
  아트보드의 목적은 §6.6 의 **렌더링 규칙**(조 제목 / 단락 / 표 / `{{ }}` 미확정 값 표기)을
  보여주는 것이고, 실제 앱은 번들된 원본 전문을 그대로 렌더한다.
- `{{시행일}}` 이 미확정이라 아트보드에는 §6.4 의 대체 표기인 **"시행일 준비 중"** 으로 그렸다.
- **문의 주소에는 `{{ }}` 자리표시자가 없다.** 서버가 내려주는 값이므로 아트보드에는
  예시 주소 `admin@planbee.app` 을 넣었다. 이 문자열은 문구가 아니라 **더미 데이터**이며
  구현에서 상수로 옮기지 않는다 (AC-42, §2.7.1).
