# PRD: 일일 추천 횟수 제한

- 기능 슬러그: `recommendation-quota`
- 작성일: 2026-08-23

## 배경 / 문제

Planbee 의 추천은 AI 서버 호출을 동반하므로 호출 한 번마다 비용이 든다. 베타 기간에는 사용량이
예측되지 않은 상태에서 비용이 무제한으로 늘어나는 것을 막아야 한다. 동시에, 남은 횟수를 사용자가
모르면 갑자기 막히는 경험이 된다 — 한도 자체보다 **한도가 보이지 않는 것**이 더 나쁘다.

제한 단위는 계정이어야 하므로 이 기능은 `auth` 의 로그인 위에서만 성립한다. 기기나 IP 단위로
세면 앱을 지우거나 네트워크를 바꾸는 것으로 우회된다.

관리자는 서비스 점검과 시연을 위해 한도 없이 사용할 수 있어야 한다.

## 목표

- 일반 사용자가 하루에 받을 수 있는 추천 횟수를 10회로 제한한다.
- 사용자가 요청하기 전에 오늘 남은 횟수를 알 수 있다.
- 한도에 도달했을 때 언제 다시 쓸 수 있는지 알 수 있다.
- 관리자는 제한 없이 사용할 수 있다.
- 서버 오류로 추천을 받지 못한 요청은 횟수를 깎지 않는다.

## Out of scope

- **추천 기능 자체의 구현** — 이 PRD 는 이미 존재하는 추천 요청 경로에 한도를 얹는 것만 다룬다.
  추천 엔드포인트가 없으면 이 기능은 착수할 수 없다 (제약 참조).
- **유료 플랜, 횟수 구매, 광고 시청 보상** — 한도를 늘리는 어떤 수단도 이번 범위가 아니다.
- **사용자별로 다른 한도를 관리자가 지정하는 기능** — 한도는 전역 상수 10회로 고정한다.
- **월간·주간 한도**, 시간당 속도 제한(rate limiting).
- **사용량 통계·차트**, 관리자용 사용량 조회 화면.
- 한도 소진 시 보내는 알림 — 이 앱은 사용자에게 알림을 보내지 않는다 (`auth` PRD 참조).

## 유저 스토리와 인수조건

### US-1. 사용자로서 오늘 추천을 몇 번 더 받을 수 있는지 알고 싶다

| ID | 인수조건 |
|---|---|
| AC-1 | Given 오늘 추천을 한 번도 받지 않은 사용자일 때 When 홈 화면을 열면 Then "오늘 남은 추천 10회" 가 표시된다 |
| AC-2 | Given 오늘 추천을 3회 받은 사용자일 때 When 홈 화면을 열면 Then "오늘 남은 추천 7회" 가 표시된다 |
| AC-3 | Given 추천을 1회 받았을 때 When 응답이 도착하면 Then 별도의 화면 이동이나 새로고침 없이 남은 횟수 표시가 1 줄어든다 |
| AC-4 | Given 역할이 `ADMIN` 인 계정일 때 When 홈 화면을 열면 Then 남은 횟수 대신 제한 없음을 뜻하는 표시가 나타난다 |
| AC-5 | Given 남은 횟수를 불러오는 중일 때 When 화면을 보면 Then 숫자 자리에 로딩 상태가 표시되고 잘못된 숫자(예: 0)가 잠깐 보이지 않는다 |
| AC-6 | Given 남은 횟수 조회가 실패했을 때 When 화면을 보면 Then 남은 횟수 영역에 오류 표시와 재시도 수단이 나타나되 다른 화면 요소는 정상 동작한다 |

### US-2. 사용자로서 한도에 도달했을 때 이유와 재개 시점을 알고 싶다

| ID | 인수조건 |
|---|---|
| AC-7 | Given 오늘 추천을 10회 받은 사용자일 때 When 홈 화면을 열면 Then 추천 요청 입력 수단이 비활성 상태이고 "오늘 추천을 모두 사용했어요" 가 표시된다 |
| AC-8 | Given AC-7 상태일 때 When 안내 문구를 보면 Then 다시 사용할 수 있는 시점이 표시된다 |
| AC-9 | Given 오늘 10회를 사용한 뒤 앱 검증을 우회한 11번째 요청이 서버에 도달했을 때 When 서버가 처리하면 Then 추천을 수행하지 않고 한도 초과로 거부한다 |
| AC-10 | Given AC-9 로 거부되었을 때 When 앱이 응답을 받으면 Then 일반 오류 문구가 아니라 AC-7 과 같은 한도 초과 안내 화면으로 전환된다 |
| AC-11 | Given 어제 10회를 모두 사용한 사용자일 때 When `Asia/Seoul` 기준으로 날짜가 바뀐 뒤 홈 화면을 열면 Then "오늘 남은 추천 10회" 가 표시되고 추천을 요청할 수 있다 |

### US-3. 사용자로서 실패한 요청 때문에 횟수를 손해 보고 싶지 않다

| ID | 인수조건 |
|---|---|
| AC-12 | Given 남은 횟수가 5회일 때 When 추천 요청이 서버 오류로 실패하면 Then 남은 횟수가 5회로 유지된다 |
| AC-13 | Given 남은 횟수가 5회일 때 When 추천 요청이 네트워크 오류로 실패하면 Then 남은 횟수가 5회로 유지된다 |
| AC-14 | Given 남은 횟수가 5회일 때 When 잘못된 입력으로 추천 요청이 검증에서 거부되면 Then 남은 횟수가 5회로 유지된다 |
| AC-15 | Given 남은 횟수가 1회일 때 When 두 기기에서 동시에 추천을 요청하면 Then 정확히 한 건만 성공하고 다른 한 건은 한도 초과로 거부된다 |

### US-4. 관리자로서 한도 없이 서비스를 점검하고 싶다

| ID | 인수조건 |
|---|---|
| AC-16 | Given 역할이 `ADMIN` 인 계정일 때 When 하루에 추천을 11회 요청하면 Then 11번째 요청도 정상 처리된다 |
| AC-17 | Given 역할이 `ADMIN` 인 계정일 때 When 추천을 요청하면 Then 그 사용자의 사용 횟수 기록이 증가하지 않는다 |

### US-5. 인증되지 않은 요청은 한도 이전에 차단된다

| ID | 인수조건 |
|---|---|
| AC-18 | Given 로그인하지 않은 상태일 때 When 추천을 요청하면 Then 한도 판정에 도달하기 전에 인증 필요로 거부된다 |
| AC-19 | Given 로그인하지 않은 상태일 때 When 남은 횟수 조회를 요청하면 Then 인증 필요로 거부된다 |

## 필수 포함 인수조건

| 유형 | AC ID |
|---|---|
| 정상 흐름 | AC-2, AC-3, AC-16 |
| 입력 검증 실패 | AC-14 |
| 서버/네트워크 오류 | AC-6, AC-12, AC-13 |
| 데이터가 없는 상태 | AC-1 (오늘 사용 기록이 없는 상태), AC-5 |
| 권한 없음 | AC-18, AC-19 |

## 제약

- **선행 조건**: 이 기능은 `auth` 의 로그인과 **추천 요청 엔드포인트**가 모두 존재해야 착수할 수 있다.
  추천 엔드포인트는 아직 없다. 파이프라인 순서상 `auth` → `admin-user-approval` → 추천 기능 →
  이 기능 순으로 진행한다.
- 한도는 **10회 / 일 / 계정**. 값은 서버 설정으로 두되 사용자별 개별 지정은 하지 않는다.
- **집계 단위는 계정이다.** 기기·IP·세션 단위로 세지 않는다.
- **초기화 기준 시각은 `Asia/Seoul` 자정으로 고정한다** (2026-08-23 확정). 국내 사용자를 대상으로 하는
  앱이므로 기기 시간대를 따르지 않는다 — 기기 시간대를 따르면 시간대를 바꾸는 것으로 한도를
  초기화할 수 있다. 저장·연산은 UTC 로 하고 (`docs/conventions/common.md` C-2), 어느 날짜에
  속하는지 판정할 때만 KST 로 환산한다. 해외에서 사용할 때 현지 자정과 어긋나는 것은 감수한다.
- **남은 횟수는 서버가 계산해서 내린다.** 앱이 사용 횟수를 세거나 `10 - 사용 횟수` 를 계산하지 않는다 (C-8).
  재개 시점 문구(AC-8)도 서버가 만든 값을 표시한다.
- 차감은 **추천이 성공했을 때만** 일어난다. 차감과 추천 수행이 서로 다른 결과로 갈라지지 않아야 한다
  (AC-12·AC-15).
- 동시 요청에서 한도가 초과되지 않도록 카운터 증가는 원자적이어야 한다 (AC-15).
  애플리케이션 메모리에 카운터를 두지 않는다 — 인스턴스가 늘면 깨진다.
- 별도의 속도 제한 라이브러리를 도입하지 않는다. 일일 고정 한도에는 DB 카운터로 충분하다.
- 시각은 ISO 8601 UTC, 필드 이름은 `snake_case` (C-2, C-7).

## 열린 질문

1. **한도 초과 응답의 HTTP 상태 코드.** 표준은 `429 Too Many Requests` 인데
   `docs/conventions/common.md` C-1 이 허용 상태를 `400/401/403/404/405/409/500` 으로 제한하고 있어
   429 가 없다. 둘 중 하나가 필요하다 — (가) C-1 에 429 를 추가한다, (나) `403` 에 한도 초과를
   구분하는 오류 코드를 붙인다. **C-1 개정은 tech-lead 소유이므로 여기서 결정하지 않는다.** → tech-lead
2. **한도 초과 상태에서 사용자가 접근할 수 있는 대안이 있어야 하는가.** 추천은 막히지만 이전 추천
   결과를 다시 볼 수 있어야 하는지 등, AC-7 의 화면이 완전한 막다른 길이 되지 않게 할 방법.
   → ux-designer 와 함께 결정
3. **10회라는 숫자를 언제 재검토하는가.** 베타 사용 데이터가 쌓이면 조정할 값이다.
   설정으로 빼두면 배포 없이 바꿀 수 있다.
4. **오류 코드 확정.** AC-9 의 한도 초과를 구분할 코드가 필요하다. → tech-lead
