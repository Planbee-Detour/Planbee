# UI/UX 명세: 관리자 가입 승인 (`admin-user-approval`)

- 기능 슬러그: `admin-user-approval`
- 작성일: 2026-09-07
- 작성 역할: ux-designer
- 근거 문서: `docs/features/admin-user-approval/PRD.md` (US 6 / AC 34),
  `docs/features/admin-user-approval/status.md`,
  `docs/features/auth/design.md` (§2 공통 규칙 · §8 설정 화면 · §10 컴포넌트 · §12 플랫폼 분기),
  `docs/design/planbee.pen` (`Screen 01 — Design System`), `docs/design/planbee-design-prompt.md`
- 이 문서가 `admin-user-approval` 의 **유일한** UI/UX 명세다. 화면 문구는 여기 적힌 것을 그대로 쓴다 (`mobile.md` M-7).

---

## 0. 읽는 방법

- **문구는 확정안이다.** 큰따옴표 안의 한국어는 그대로 화면에 넣는다. 개발자가 바꾸거나 지어내지 않는다.
- **`auth` design.md 를 상속한다.** 디자인 토큰(§2.1), 화면 골격(§2.2), 텍스트 입력 공통 동작(§2.3),
  오류 표현의 3단계(§2.4), 접근성 공통(§2.5), 플랫폼 분기(§12)는 `auth` design.md 의 해당 절을
  그대로 따른다. 이 문서는 **거기서 달라지는 것과 새로 생기는 것만** 적는다.
  이 문서에서 `auth §2.1` 처럼 적으면 `docs/features/auth/design.md` 의 절 번호다.
- **서버가 문구를 내리는 자리**는 그렇게 명시했다. 앱이 조건문으로 문구를 조합하지 않는다
  (`common.md` C-8 / `mobile.md` M-18). 이 기능에서 그 자리는 **가입 사유의 대체 문구(AC-33)** 와
  **계정 상태 배지 라벨** 두 곳이다.
- 각 화면 끝의 `충족 AC` 는 그 화면이 책임지는 인수조건이다. 전체 대조표는 §11.
- **미확정 항목은 §12 `열린 질문` 에 닫힌 질문으로 올렸다.** 추측으로 메우지 않았다.

## 1. 이 문서가 딛고 선 결정

### 1.1 사람이 확정한 결정 (2026-09-07)

| # | 항목 | 결정 |
|---|---|---|
| 1 | 진입점 (AC-1 · AC-2) | 하단 탭바를 건드리지 않는다. **마이 탭 → 설정 화면에 `관리자` 섹션을 추가**하고 역할이 `ADMIN` 일 때만 렌더한다. 행은 "가입 신청 관리", 우측에 대기 건수 |
| 2 | 목록 구조 (AC-5 · AC-20) | **한 화면 + 상단 세그먼트 2개.** 화면 제목은 "가입 신청 관리". 두 번째 세그먼트 라벨은 처음 "승인됨" 이었고 **2026-09-07 에 "처리 완료" 로 개정되었다** (§1.1.1 Q1) |
| 3 | 조작 위치 (AC-10 · AC-15 · AC-21) | 목록 행을 탭하면 **상세 바텀시트**가 올라오고 거기에 승인/거절(또는 정지/해제) 버튼을 둔다. **목록 행에는 버튼을 노출하지 않는다.** 거절 사유 200자 입력(AC-16)과 확인 단계(AC-15)도 이 시트 흐름 안에 있다 |
| 4 | 계정 삭제 (`status.md` ASK 2) | **이번 범위 밖.** 관리자가 앱 안에서 계정을 지우는 수단을 만들지 않는다. 파기 요청은 `auth` AC-38 의 문의 연락처로 받아 DB 에서 직접 처리한다 |

| # | 질문 | 답 | 이 문서에 반영된 곳 |
|---|---|---|---|
| Q1 | 거절된(`REJECTED`) 사용자를 어디서 보는가 (AC-19) | **세그먼트는 2개 유지. 두 번째 라벨을 "승인됨" → "처리 완료" 로 바꾸고**, 그 목록에 `APPROVED` · `SUSPENDED` · `REJECTED` 를 상태 배지와 함께 담는다. 거기서 `Screen 21d`(거절됨 시트)로 들어가 AC-19 를 완성한다. **표기는 "처리됨" 이 아니라 "처리 완료" 다** | §2.1 아트보드명, §2.3 전이, §3.5·§3.6, §5.2, §5.4, §5.8, §5.11, §7, §9, §11, §15 |

### 1.2 이 문서가 정한 것 (근거 포함)

| # | 항목 | 결정과 근거 |
|---|---|---|
| a | `관리자` 섹션의 위치 | **`계정` 섹션 다음, `약관·정책` 앞.** ⑴ 관리자 업무는 계정 성격의 기능이라 계정 블록에 붙는 것이 의미상 맞고, ⑵ 매일 여는 행동이므로 스크롤 없이 닿아야 하며, ⑶ 약관·정책과 앱 정보는 참조용이라 아래에 남는다. **맨 위(계정 위)에 두지 않는 이유**: `계정` 은 모든 사용자에게 동일한 기준점이다. 역할에 따라 화면의 첫 섹션이 달라지면 `ADMIN` 과 `USER` 의 설정 화면 구조가 갈리고, 사람에게 설명할 때 "위에서 두 번째" 같은 조건부 안내가 생긴다 |
| b | `처리 완료` 세그먼트가 담는 상태 | **`APPROVED` · `SUSPENDED` · `REJECTED` 셋 전부** (2026-09-07 Q1 확정). AC-24(정지 해제)와 AC-19(거절 취소)가 각각 정지된 계정과 거절된 계정에 도달할 것을 요구하는데, 세그먼트는 둘뿐이고 `검토 대기` 는 `PENDING` 전용이다. 따라서 처리가 끝난 계정은 전부 이 세그먼트에 남아야 하고, 그러면 행에 **상태 배지가 필수**가 된다 (§3.4) |
| c | 세그먼트 라벨을 "처리 완료" 로 한 이유 | 두 번째 목록이 `APPROVED` 만 담지 않으므로 "승인됨" 은 내용보다 좁은 이름이다. 세그먼트 **수**(결정 2)는 그대로 두고 이름만 내용에 맞췄다. **"처리됨" 이 아니라 "처리 완료" 로 표기한다** — 2026-09-07 사람 확정. 문구·아트보드명·a11y 라벨 어디에도 "처리됨" 을 쓰지 않는다 |
| d | 승인에는 확인 단계를 두지 않는다 | AC-15 는 **거절에만** 확인 단계를 요구한다. 승인은 되돌릴 수 있고(정지 — AC-21) 이 화면의 주 행동이다. 매 건 확인 다이얼로그를 띄우면 20건을 처리할 때 40번 탭하게 된다 |
| e | 거절의 확인 단계는 시트 2단계로 한다 | AC-15 의 "확인 단계 한 번" 은 §6.4 의 거절 사유 입력 단계가 담당한다. 그 위에 시스템 다이얼로그를 **또** 띄우지 않는다 — 사유를 200자 쓰고 나서 "정말요?" 를 다시 묻는 것은 확인이 아니라 마찰이다 |
| f | 상대 시각 표기를 쓰지 않는다 | "3분 전" 은 앱이 현재 시각과 응답 값으로 **계산**하는 값이다 (M-18 금지). 서버가 내린 ISO 8601 UTC 를 로컬 `YYYY. M. D. HH:mm` 으로 **포맷팅만** 한다 (C-2 허용 범위) |
| g | 건수 상한 표기를 두지 않는다 | "99+" 같은 절삭을 쓰지 않고 서버가 내린 정수를 그대로 표기한다. 클로즈드 베타 규모에서 자릿수가 레이아웃을 깨지 않고, 절삭은 AC-32(알림 건수와 화면 건수가 같아야 함)의 대조를 어렵게 만든다 |

### 2.2 내비게이터 구성

`auth` design.md §1.1 의 `MainStack` 에 화면 하나를 더한다. **하단 탭은 건드리지 않는다** (결정 1).

```
MainStack (세션 있음 · APPROVED)
├─ MainTabs (홈 · 탐색 · 저장 · 마이)
├─ Settings                       ← auth §8. 여기에 `관리자` 섹션이 추가된다 (§4)
├─ UserApprovalList               ← 신규 (§5). 파라미터 없음
├─ AccountDelete
└─ LegalDocument [모달]
```

- `UserApprovalList` 는 **스택 화면**이다. 탭이 아니고 모달도 아니다 —
  뒤로가기로 설정 화면에 돌아오는 것이 자연스러운 흐름이고, 결정 1이 탭바를 고정했다.
- 상세 시트(§6·§7)는 화면이 아니라 `UserApprovalList` 안에서 열리는 **오버레이**다.
  라우트를 따로 두지 않는다 — 딥링크 대상이 아니고, 목록의 스크롤 위치와 세그먼트 선택이
  시트를 닫은 뒤 그대로 유지되어야 한다.

| 시트 열림 · 기본 단계 | 시트만 닫는다 (화면은 유지) |
| 시트 열림 · 거절 사유 입력 단계 | **기본 단계로 되돌린다.** 시트를 바로 닫지 않는다 — 200자를 쓰다가 백 한 번에 사라지면 안 된다 |
| 시트 열림 · 처리 중 | **이벤트를 소비하고 아무 일도 하지 않는다** (중복 요청·중간 이탈 방지) |

iOS 스와이프 백은 같은 규칙으로 맞춘다. 시트가 열려 있으면 화면 스와이프 백을 끄고
시트의 아래로 스와이프만 살린다.

## 3. 공통 규칙

### 3.1 상속하는 것

색·타이포·간격·라운드·그림자는 `auth §2.1` 의 표를 그대로 쓴다. **신규 색 토큰은 없다** (§8.4).
화면 골격(폭 390, 배경 `background`, 좌우 여백 20)은 `auth §2.2`,
텍스트 입력 공통 동작은 `auth §2.3`, 오류 표현의 3단계는 `auth §2.4` 를 따른다.

### 3.2 토스트와 배너의 역할 분담

`auth §2.4` 가 정한 규칙을 그대로 지킨다 — **토스트는 완료 알림에만, 오류에는 쓰지 않는다.**

| 무엇 | 형태 | 예 |
|---|---|---|
| 처리 완료 | 토스트 2초 | "승인했어요" |
| 처리 실패 (네트워크·서버) | **시트 안 인라인 배너** | §6.7 |
| 경합 상태 (AC-12) | **시트 안 인라인 배너 + 액션 교체** | §6.8 |
| 목록 전체 실패 | 화면 중앙 오류 블록 | §5.9 |
| 되돌릴 수 없거나 사용자에게 즉시 영향 | 시스템 확인 다이얼로그 | §7.3 정지 |

**AC-12(이미 처리된 신청)를 토스트로 하지 않는 이유**: 토스트는 2초 뒤 사라진다.
관리자가 방금 누른 버튼이 왜 무효였는지 되짚을 수단이 없어지고, 목록이 조용히 바뀐 것처럼 보인다.
시트 안에 남기면 **그 항목의 이메일·신청 시각과 함께** 읽을 수 있고, 시트를 닫는 시점에는
목록이 이미 갱신돼 있다.

### 3.3 시각 표기

- 서버는 ISO 8601 UTC 로 내린다 (C-2). 앱은 **표시 직전에 기기 로컬로 변환해 포맷팅만** 한다.
- 목록·시트 공통 형식: **`YYYY. M. D. HH:mm`** (24시간). 예: `2026. 9. 5. 14:20`
- `auth` 는 날짜만 필요해 `YYYY. M. D.` 를 썼다 (auth §7.2). 여기서는 최신순 목록이라
  같은 날 여러 건이 들어오고, 분 단위가 없으면 순서를 눈으로 확인할 수 없다.
- **상대 시각("3분 전")을 쓰지 않는다** (§1.2 f / M-18).

### 3.4 계정 상태 배지 (`Badge/Status` — 신규)

| 상태 값 | 배지 라벨 (서버가 내린다) | 배경 | 테두리 | 텍스트 |
|---|---|---|---|---|
| `PENDING` | "검토 대기" | `brand-light` | 없음 | `brand-dark` |
| `APPROVED` | "승인됨" | `surface` | `success` 1px | `success` |
| `SUSPENDED` | "정지됨" | `surface` | `danger` 1px | `danger` |
| `REJECTED` | "거절됨" | `surface` | `border` 1px | `ink-muted` |

- **라벨 문자열은 서버 응답 값이다** (C-8 / M-18). 앱이 상태 코드로 `switch` 해서 한국어를 만들지 않는다.
  `auth §7.1` 이 상태 안내 화면에서 쓴 것과 같은 분업이다 — **문구는 서버, 색과 모양은 앱**.
- 배지는 Caption / 600, 라운드 999, 패딩 `[2, 8]`, 최소 높이 20.
- **색만으로 구분하지 않는다** (auth §2.5). 배지는 항상 라벨 텍스트를 동반하고, 아이콘만 쓰는 변형을 만들지 않는다.
- 연한 배경색(`success` 의 10% 틴트 같은 것)을 만들지 않는다. 테두리 + 텍스트로 표현해
  **신규 색 토큰이 0개**가 되게 한다 (auth §10.3 과 같은 판단).

### 3.5 접근성 — 이 기능에서 추가되는 것

`auth §2.5` 를 전부 상속하고 아래를 더한다.

- **목록 항목은 한 덩어리로 읽는다.** 카드 안의 이메일·가입 사유·시각을 각각 읽으면
  20개 항목에서 60번 스와이프해야 한다. 카드 전체를 `accessibilityRole="button"` 하나로 묶고
  `accessibilityLabel` 을 다음 순서로 조합한다 — **이메일 → 상태(`처리 완료` 세그먼트에서만) → 시각 → 가입 사유**.
  - 검토 대기: `"name@example.com, 신청 2026년 9월 5일 14시 20분, 가입 사유 {서버가 준 값}"`
  - 처리 완료 (`APPROVED`): `"name@example.com, 승인됨, 승인 2026년 9월 1일 9시 12분"`
  - 처리 완료 (`SUSPENDED`): `"name@example.com, 정지됨, 정지 2026년 9월 6일 18시 3분"`
  - 처리 완료 (`REJECTED`): `"name@example.com, 거절됨, 거절 2026년 9월 2일 11시 40분"`
  - 상태 배지 라벨과 시각 앞 접두어는 **둘 다 서버 값이다** (§3.4 · §5.4). 낭독 문장을 만들 때도
    앱이 상태 코드로 한국어를 고르지 않는다
  - `accessibilityHint`: `"두 번 눌러 상세를 엽니다"`
  - 시각은 낭독용으로 "2026년 9월 5일 14시 20분" 형태로 풀어 읽는다. 화면 표기(`2026. 9. 5. 14:20`)를
    그대로 넘기면 스크린리더가 마침표를 문장 끝으로 읽어 끊긴다.
  - 가입 사유가 긴 경우 낭독에서는 **말줄임하지 않고 전문을 읽는다.** 시각적 2줄 제한(§5.3)은 표현일 뿐이다.
- **바텀시트의 포커스 이동**
  - 시트가 열리면 포커스를 **시트 제목**으로 옮긴다.
  - 배경(목록)은 스크린리더 대상에서 뺀다 — iOS `accessibilityViewIsModal={true}`,
    Android `importantForAccessibility="no-hide-descendants"` (M-20 분기).
  - 시트가 닫히면 포커스를 **시트를 연 목록 행**으로 되돌린다. 목록 맨 위로 튀지 않게 한다.
  - 거절 사유 입력 단계로 전환되면 포커스를 그 단계의 제목으로 옮긴다. 입력란으로 바로 보내지 않는다 —
    사유는 선택 입력이라(AC-17) 관리자가 무엇을 확인하는 단계인지 먼저 들어야 한다.
- **상태 변화 announce** — `shared/lib/a11y` 를 쓴다 (M-20). 화면 코드에 `accessibilityLiveRegion` 을 직접 적지 않는다.

| 사건 | 읽는 문장 |
|---|---|
| 목록 새로고침 완료 (AC-9) | "목록을 새로 고쳤어요" |
| 다음 페이지 로드 완료 (AC-7) | "{서버가 준 추가 건수}건을 더 불러왔어요" |
| 승인 완료 | "승인했어요" |
| 거절 완료 | "거절했어요" |
| 정지 완료 | "이용을 정지했어요" |
| 정지 해제 완료 | "정지를 해제했어요" |
| 거절 취소 완료 (AC-19) | "검토 대기로 되돌렸어요" |
| 처리 실패 · 경합 | 해당 배너의 제목과 부연을 이어서 읽는다 |

- 동적 폰트: 목록 카드와 시트의 높이는 **최소 높이**로 두고 내용에 따라 늘어나게 한다.
  가입 사유 2줄 제한도 줄 수 기준이지 픽셀 고정이 아니다.
- 터치 대상 최소 44×44. 세그먼트 각 칸의 최소 높이 44, 목록 카드의 최소 높이 72.

### 3.6 목록의 네 가지 상태를 세그먼트마다 따로 갖는다

세그먼트를 바꾸면 **다른 목록**이다. `검토 대기` 가 오류여도 `처리 완료` 는 정상일 수 있다.
로딩·비어있음·오류 상태를 세그먼트별로 독립적으로 관리하고, 한쪽의 실패가 다른 쪽을 가리지 않게 한다.
세그먼트 컨트롤 자체는 **어떤 상태에서도 항상 조작 가능**하다 — 목록이 오류여도 다른 탭으로 빠져나갈 수 있어야 한다.

## 4. 화면: 설정 — `관리자` 섹션 (`Screen 17a` · `17b`)

`auth` design.md §8 `SettingsScreen` 에 **섹션 하나를 더한다.** 기존 섹션·행·문구는 하나도 바꾸지 않는다.

### 4.1 진입

마이 탭 → "계정 설정" (기존 경로). 이 기능이 새 진입 경로를 만들지 않는다.

### 4.2 구성 (`Screen 17a`)

```
[ NavBar ]  ‹ 뒤로          설정
   (24)

계정                                     ← 기존
┌────────────────────────────────────┐
│  이메일                 name@ex.com   │
└────────────────────────────────────┘
   (32)

관리자                                   ← 신규 섹션 헤더 Caption / ink-muted
┌────────────────────────────────────┐
│  가입 신청 관리                 3건 › │   ← Layout/ListRow (기존 컴포넌트 그대로)
└────────────────────────────────────┘
   (32)

약관·정책                                 ← 기존
   ...
```

- 섹션 헤더: **"관리자"**
- 행 라벨: **"가입 신청 관리"**, 우측 값 = 대기 건수 **"N건"**, `chevron-right`
- 행 최소 높이 56, `Layout/ListRow` 를 그대로 쓴다. 신규 컴포넌트가 필요 없다.
- 값 자리를 배지(빨간 원)로 만들지 않는다. 설정 화면의 다른 행이 전부 텍스트 값이고,
  여기만 알림 배지를 쓰면 "읽지 않음" 이라는 다른 의미가 섞인다.

### 4.3 렌더 조건 (AC-1 · AC-2)

| 역할 조회 상태 | 섹션 |
|---|---|
| 조회 중 (로딩) | **렌더하지 않는다.** 스켈레톤도 두지 않는다 |
| `ADMIN` | 렌더한다 (`Screen 17a` / `17b`) |
| `USER` | 렌더하지 않는다 — AC-2 |
| 조회 실패 (오류) | **렌더하지 않는다.** 화면의 나머지는 `auth §8.5` 그대로 동작하고, "이메일" 행의 "다시 시도" 로 복구한다 |

**로딩 중에 자리를 비워 두는 이유**: 스켈레톤을 그리면 `USER` 에게도 관리자 섹션이 잠깐 보인다.
AC-2 는 "표시되지 않는다" 를 요구하므로 깜빡임도 위반이다. 반대로 `ADMIN` 에게는 섹션이
조금 늦게 나타날 뿐이고, 그 사이 다른 섹션은 이미 조작 가능하다.

> **판정은 서버가 한다.** 앱이 섹션을 숨기는 것은 편의일 뿐이다 (PRD 제약).
> 실제 차단은 서버 인가이고(AC-3), 앱은 그 응답을 §5.10 으로 받는다.

### 4.4 네 가지 상태

| 상태 | 내용 |
|---|---|
| 로딩 | 섹션 없음 (§4.3). 설정 화면의 나머지는 즉시 렌더 |
| 정상 | `Screen 17a` — "가입 신청 관리" + "N건" |
| 비어있음 | `Screen 17b` — 대기 건수가 0이면 **값 자리를 비우고** `chevron` 만 남긴다. "0건" 을 쓰지 않는다 — 0은 주의를 끌 이유가 없는데 숫자가 있으면 눈이 먼저 간다. 행은 그대로 눌러서 들어갈 수 있다 (AC-6 빈 상태를 보러 갈 수 있어야 한다) |
| 오류 | 섹션 없음 (§4.3) |

### 4.5 건수의 출처 (AC-32)

- 대기 건수는 **서버가 내린 정수**다. 앱이 목록 길이를 세지 않는다 (M-18).
  목록은 20건씩 끊어 오므로(AC-7) 길이를 세면 25건일 때 20이 표시된다.
- AC-32 는 Discord 알림의 건수와 이 화면의 건수가 같을 것을 요구한다.
  **두 값이 같은 서버 계산을 쓰는 것이 그 보장의 방법이다.** 앱은 어느 쪽도 계산하지 않는다.
- 승인·거절 처리 후 이 값은 자동으로 갱신되어야 한다 (§5.11).

### 4.6 접근성

- 행 `accessibilityRole="button"`, `accessibilityLabel` = **"가입 신청 관리, 검토 대기 3건"**
  (`Layout/ListRow` 의 기본 규칙은 "라벨, 값" 이므로 값 문자열을 "검토 대기 3건" 으로 넘긴다).
- 건수가 0이면 **"가입 신청 관리, 검토 대기 없음"**. 값 자리가 비어 있어도 스크린리더에는
  상태를 말해 준다 — 시각적으로는 비움이 정보지만 낭독에서는 침묵이 정보가 되지 못한다.

### 4.7 구현 유의 — 기능 경계 (M-2)

`SettingsScreen` 은 `features/auth/` 소유다. 그 안에서 `features/admin-user-approval/` 을
직접 import 하면 **M-2(기능 간 직접 import 금지) 위반**이다. 조합은 `app/` 레이어에서 한다 —
설정 화면이 "관리자 섹션 슬롯" 을 prop 으로 받고, `app/navigation/MainNavigator.tsx` 가
그 자리에 이 기능의 컴포넌트를 넣는 형태가 M-2 를 만족한다. 구체적 형태는 mobile-developer 가 정한다.
**이 문서가 요구하는 것은 화면 결과이지 배선 방식이 아니다.**

**충족 AC**: AC-1, AC-2, AC-32(건수 출처)

### 5.2 구성

```
[ NavBar ]  ‹ 뒤로       가입 신청 관리

   (16)
```

- 화면 제목: **"가입 신청 관리"** (결정 2)
- 세그먼트 라벨: **"검토 대기 N"** / **"처리 완료"**
  - **"처리됨" 이 아니라 "처리 완료" 다** (2026-09-07 확정 — §1.1.1 Q1). 두 표기를 섞지 않는다.
  - 두 번째 세그먼트에는 **숫자를 붙이지 않는다.** 처리된 계정은 계속 쌓이기만 하고,
    관리자가 확인해야 할 잔여량이 아니다. 숫자는 "할 일이 N개" 라는 뜻으로 읽히므로 대기 쪽에만 둔다.
  - 대기 건수가 1 이상이면 숫자를 붙인다. **0이면 "검토 대기" 만 쓴다** — "검토 대기 0" 은
    한국어로 읽기 어색하고, 0을 굳이 보여줄 이유가 없다는 §4.4 와 같은 판단이다.
  - 숫자는 §4.5 와 **같은 서버 값**이다. 세그먼트와 설정 배지가 다른 수를 보이면 안 된다.
- 기본 선택 세그먼트는 **"검토 대기"** 다. 이 화면에 들어오는 이유가 그것이다.
- 세그먼트 선택은 화면을 떠났다 돌아오면 **초기화된다** (항상 "검토 대기" 로 시작).
  화면이 스택에서 살아 있는 동안(시트를 닫는 등)에는 유지된다.

### 5.3 검토 대기 목록 행 (`Screen 18a` — AC-5 · AC-33)

| 요소 | 값 | 타이포 |
|---|---|---|
| 이메일 | 서버 값 | Title / `ink`, 1줄, 넘치면 말줄임 |
| 가입 사유 | **서버 값 그대로** | BodySmall / `ink-body`, 최대 2줄, 넘치면 말줄임(`…`) |
| 신청 시각 | "신청 " + `YYYY. M. D. HH:mm` | Caption / `ink-muted` |

- 정렬: **신청 시각 최신순** (AC-5). 정렬 옵션을 제공하지 않는다 (PRD Out of scope).
- 카드 패딩 16, 요소 간격 8 / 6, 최소 높이 72. 카드 사이 간격 12.
- **행에 승인·거절 버튼을 두지 않는다** (결정 3). 카드 전체가 하나의 터치 영역이고 시트를 연다.
- 우측 `chevron-right` 를 두지 않는다 — 카드형 목록에서 셰브런은 리스트 행처럼 보이게 만들고,
  버튼이 없다는 사실이 오히려 흐려진다. 대신 카드 전체가 눌리는 것을 pressed 상태(배경 `background`)로 알린다.

#### 가입 사유가 없는 신청 (AC-33) — 앱이 조합하지 않는다

- 서버는 가입 사유가 비어 있으면 **그 자리에 넣을 문자열 "입력하지 않음" 을 완성해서 내린다.**
  (PRD 제약 / C-8 / status.md 2026-08-23 결정)
- **앱은 `null` 검사도, 삼항 연산자도, 기본값 상수도 두지 않는다.** 응답에 실려 온 문자열을
  그대로 렌더한다. `"입력하지 않음"` 이라는 문자열이 **앱 코드 어디에도 나타나지 않아야 한다** —
  §9 문구 목록에도 넣지 않은 이유가 이것이다.
- 시각적으로도 다른 항목과 동일하게 다룬다 (AC-33). 회색으로 흐리거나 이탤릭으로 구분하거나
  줄을 통째로 빼지 않는다. 이메일과 신청 시각의 위치·크기도 그대로다.

### 5.4 처리 완료 목록 행 (`Screen 19a` — AC-19 · AC-20 · AC-21 · AC-24)

| 요소 | 값 | 타이포 |
|---|---|---|
| 이메일 | 서버 값 | Title / `ink`, 1줄 |
| 상태 배지 | §3.4 (`승인됨` / `정지됨` / `거절됨`) | 이메일 오른쪽, 같은 줄 |
| 처리 시각 | **"{서버가 준 접두어} "** + `YYYY. M. D. HH:mm` | Caption / `ink-muted` |

- **담기는 상태는 `APPROVED` · `SUSPENDED` · `REJECTED` 셋 전부다** (2026-09-07 Q1 확정 / §1.2 b).
  세 상태 모두 여기서 시트를 열어 각각 AC-21·AC-24·AC-19 를 수행한다.
- **시각 앞 접두어("승인" / "정지" / "거절")는 서버가 내리는 문자열이다.** 앱이 상태 코드로
  한국어를 고르지 않는다 (C-8 / M-18). 시각 자체는 ISO 8601 UTC 로 받아 앱이 로컬 포맷팅만 한다 (§3.3) —
  그래서 **접두어와 시각을 각각** 받는다. 완성된 문장으로 받으면 UTC → 로컬 변환을 할 수 없다.
- 정렬: **마지막 처리 시각 최신순.** AC-20 은 "승인 시각 최신순" 을 요구하는데, `APPROVED` 항목만
  놓고 보면 마지막 처리 시각이 곧 승인 시각이므로 그 안에서의 상대 순서는 그대로 보존된다.
- 가입 사유를 이 목록에는 표시하지 않는다 — AC-20 이 요구하는 것은 이메일과 승인 시각이고,
  처리가 끝난 뒤에는 사유가 판단 재료가 아니다. 필요하면 시트(§7)에서 본다.
- 이메일이 길어 배지와 겹치면 **이메일을 말줄임하고 배지는 제자리를 지킨다.** 상태가 잘리면 안 된다.
- 상태별로 카드 배경·테두리를 다르게 하지 않는다. 구분은 **배지 하나로만** 한다 —
  세 상태에 카드 스타일을 각각 주면 목록이 얼룩덜룩해지고 훑어보기가 오히려 어려워진다.

### 5.5 당겨서 새로고침 (AC-9)

- 두 세그먼트 모두 지원한다. 표준 `RefreshControl`.
- 당기는 동안 기존 목록은 그대로 보인다. 스켈레톤으로 바꾸지 않는다.
- 완료 시 §3.5 의 announce("목록을 새로 고쳤어요")를 읽는다.
- 새로고침은 **첫 페이지부터 다시 가져온다.** 이미 불러온 2·3페이지는 버린다 —
  최신순 목록에서 앞이 바뀌면 뒤 페이지의 경계가 어긋난다.
- 새로고침이 실패하면 **기존 목록을 유지**하고 화면 상단에 `Feedback/Banner`(danger) 로
  **"새로 고치지 못했어요"** + 부연 **"잠시 후 다시 시도해 주세요."** + 텍스트 버튼 **"다시 시도"**.
  목록을 오류 화면으로 대체하지 않는다 — 이미 보고 있던 내용을 실패가 지우면 안 된다.

### 5.6 페이지네이션 (AC-7 · `Screen 18e`)

- 첫 페이지 **20건**. 목록 끝에 도달하면 다음 페이지를 **자동으로** 불러온다.
  "더 보기" 버튼을 두지 않는다 — 승인 작업은 위에서 아래로 훑는 흐름이고 중간에 탭이 끼면 리듬이 끊긴다.
- 트리거 지점: 마지막 항목이 화면에 들어오기 **한 카드 앞**.
- **목록 푸터가 상태를 말한다.**

| 상황 | 푸터 |
|---|---|
| 다음 페이지 로딩 중 | 24px 스피너 + **"불러오는 중"** (Caption / `ink-muted`, 중앙). `accessibilityLabel="불러오는 중"` |
| 마지막 페이지까지 다 불러옴 | **"모두 확인했어요"** (Caption / `ink-muted`, 중앙, 위아래 여백 24) |
| 다음 페이지 로드 실패 | **"더 불러오지 못했어요"** (Caption / `ink-muted`) + 텍스트 버튼 **"다시 시도"**. **이미 불러온 항목은 그대로 남는다** |
| 한 페이지로 끝남 (20건 미만) | 푸터 없음. "모두 확인했어요" 를 띄우지 않는다 — 애초에 더 있을 거라 기대하지 않은 상태다 |

- 다음 페이지를 자동으로 재시도하지 않는다. 실패하면 위 행을 두고 관리자가 누를 때만 다시 시도한다.
- 페이지 이어붙이기는 react-query 가 한다 — C-8 이 허용하는 조합이다.

### 5.7 로딩 (`Screen 18b`)

- 첫 진입 시 **카드 스켈레톤 3개.** 각 스켈레톤은 실제 카드와 같은 최소 높이(72)를 갖고,
  안에 폭 200/높이 16(이메일), 폭 100%·80%/높이 14 두 줄(사유), 폭 140/높이 12(시각)의 바를 둔다.
- 배경색 `border`, 라운드 4. 펄스 애니메이션은 `Animated` opacity 루프 하나로 한다
  (reanimated 미도입 — `mobile.md` 미확정 항목). "동작 줄이기" 가 켜져 있으면 정지 상태로 둔다.
- 세그먼트 컨트롤과 NavBar 는 **즉시 렌더**한다. 로딩 중에도 세그먼트를 바꿀 수 있다 (§3.6).

### 5.8 비어있음 (`Screen 18c` · `Screen 19b`)

화면 중앙(세그먼트 아래 영역의 세로 중앙)에 배치한다.

```
        [ inbox 아이콘 32, ink-muted ]
                 (12)
        "검토할 신청이 없어요"              ← Title / ink
                 (4)
   "새 신청이 들어오면 여기에 표시돼요."      ← BodySmall / ink-muted, 중앙 정렬
```

| 세그먼트 | 제목 | 부연 | 근거 |
|---|---|---|---|
| 검토 대기 | **"검토할 신청이 없어요"** | **"새 신청이 들어오면 여기에 표시돼요."** | 제목은 AC-6 이 지정한 문구다. 토씨 그대로 쓴다. 부연은 이 문서가 정한다 |
| 처리 완료 | **"아직 처리한 신청이 없어요"** | **"승인하거나 거절한 신청이 여기에 표시돼요."** | **PRD 에 없어 이 문서가 정했다.** AC-20 은 목록이 있는 경우만 말한다. 초안의 "승인된 사용자가 아직 없어요" 는 세그먼트가 `승인됨` 이던 때의 문구라, 라벨이 `처리 완료` 로 바뀌면서 함께 고쳤다 (2026-09-07 Q1) |

- 빈 상태에서도 **당겨서 새로고침이 동작한다** (AC-9). 빈 화면은 스크롤이 없으므로
  `ScrollView` 에 `flexGrow: 1` 을 주어 당길 수 있게 한다.
- 버튼을 두지 않는다. 관리자가 여기서 할 수 있는 행동이 없고, 새로고침은 제스처로 이미 가능하다.

### 5.9 오류 (`Screen 18d` — AC-8)

목록 자체를 못 불러온 경우다. 세그먼트 아래 영역을 아래 블록으로 채운다.

```
        [ 아이콘 32 ]
                 (12)
        제목                              ← Title / ink
                 (4)
        부연                              ← BodySmall / ink-muted, 중앙 정렬
                 (20)
        [ Button/Secondary  "다시 시도" ]   ← 폭은 내용에 맞춤, 중앙
```

| # | 상황 | 아이콘 | 제목 | 부연 | AC |
|---|---|---|---|---|---|
| 1 | 서버 500 | `alert-circle` / `danger` | **"명단을 불러오지 못했어요"** | **"잠시 후 다시 시도해 주세요."** | AC-8 |
| 2 | 네트워크 끊김 | `wifi-off` / `ink-muted` | **"연결을 확인해 주세요"** | **"네트워크에 연결되면 다시 불러올게요."** | AC-8 계열 |

- **"다시 시도" 는 그 세그먼트의 목록만 다시 불러온다** (AC-8). 화면을 리마운트하지 않는다.
- 세그먼트 컨트롤과 NavBar 는 그대로 살아 있다 (§3.6).
- 재시도 중에는 버튼 라벨을 **"불러오는 중…"** 으로 바꾸고 비활성한다.

### 5.10 권한 없음 (AC-3)

역할이 바뀐 뒤 화면이 남아 있는 등의 이유로 서버가 403 을 내린 경우다.
`code` 로 분기한다 (M-13). §5.9 와 같은 블록에 다른 내용을 넣는다.

- 아이콘: `lock` / `ink-muted`
- 제목: **"관리자만 볼 수 있어요"**
- 부연: **"이 화면을 볼 수 있는 권한이 없어요."**
- 버튼: `Button/Primary` **"설정으로 돌아가기"** → `Settings` 로 pop
- "다시 시도" 를 두지 않는다. 다시 눌러도 같은 결과다 (auth §6.8 의 판단과 같다).
- 이 상태에 들어가면 역할 정보를 다시 조회해 §4.3 의 섹션 렌더 조건을 갱신한다 —
  돌아간 설정 화면에 진입점이 남아 있으면 안 된다.

AC-4(미인증)는 이 화면의 책임이 아니다. `auth §2.6` 의 전역 세션 처리가 로그인 화면으로 보낸다.

### 5.11 처리 후 목록 갱신

시트에서 승인·거절·정지·해제가 성공하면 **그 즉시** 아래를 반영한다.

| 처리 | 검토 대기 목록 | 처리 완료 목록 | 대기 건수 (세그먼트 · §4 배지) |
|---|---|---|---|
| 승인 (AC-10) | 항목 제거 | 다음 조회 시 "승인됨" 으로 합류 | −1 |
| 거절 (AC-15) | 항목 제거 | 다음 조회 시 "거절됨" 으로 합류 | −1 |
| 정지 (AC-21) | 변화 없음 | 그 행의 배지가 "정지됨" 으로 | 변화 없음 |
| 정지 해제 (AC-24) | 변화 없음 | 그 행의 배지가 "승인됨" 으로 | 변화 없음 |
| 거절 취소 (AC-19) | 항목 추가 (최신순 자리에) | 항목 제거 | +1 |

- **건수는 앱이 빼고 더하지 않는다.** 서버 값을 다시 받아 반영한다 (M-18 / AC-32).
  "−1" 은 결과의 서술이지 계산 방법이 아니다.
- 항목이 사라지는 애니메이션은 200ms 페이드아웃 + 높이 축소. "동작 줄이기" 에서는 즉시 제거.
- 목록이 이 처리로 비면 §5.8 빈 상태로 전환된다.

## 6. 시트: 신청 상세 (`Screen 20a`~`20e`)

검토 대기 목록의 행을 탭하면 올라온다 (결정 3).

### 6.1 시트의 형태 (`Layout/BottomSheet` — 신규)

- 화면 하단에서 올라오는 오버레이. 배경 스크림 `rgba(0,0,0,0.4)`.
- 시트 배경 `surface`, 상단 모서리만 라운드 20, 좌우 여백 0(화면 폭 전체), 내부 패딩 20.
- 상단에 **핸들 바** — 폭 36 / 높이 4 / 라운드 999 / `border` 색, 상단 여백 8.
- 높이는 **내용에 맞춘다**(wrap). 내용이 화면의 80% 를 넘으면 시트 안에서 스크롤한다.
- 하단 안전영역만큼 아래 패딩을 더한다.
- 닫는 방법 세 가지: 스크림 탭 / 아래로 스와이프 / 안드로이드 하드웨어 백 (§2.4).
  **닫기(×) 버튼을 따로 두지 않는다** — 세 경로로 충분하고, 시트 상단에 버튼을 두면
  핸들 바와 의미가 겹친다. 단 §6.8 처럼 시트가 결과 안내로 바뀌면 명시적 "닫기" 버튼을 둔다.
- **새 애니메이션 라이브러리를 도입하지 않고 성립해야 한다.** RN `Modal` + `Animated` 로
  구현 가능한 범위로 요건을 적었다 (reanimated 미도입 — `mobile.md` 미확정 항목).
  라이브러리 선택은 mobile-developer 가 정하되, 심사에 영향을 주는 SDK 도입은 사람에게 묻는다 (절대 규칙 8).

### 6.2 iOS / Android (M-19 · M-20)

| 지점 | iOS | Android |
|---|---|---|
| 닫기 제스처 | 아래로 스와이프 + 스크림 탭 | 아래로 스와이프 + 스크림 탭 + 하드웨어 백 |
| 시트 뒤 화면 스와이프 백 | **끈다** (시트가 열려 있는 동안) | 해당 없음 |
| 스크린리더 격리 | `accessibilityViewIsModal={true}` | `importantForAccessibility="no-hide-descendants"` |
| 상태바 | 변경하지 않는다 | 변경하지 않는다 (스크림만 덮는다) |
| 키보드 (§6.4 입력 단계) | `KeyboardAvoidingView behavior="padding"` | `behavior="height"` |
| 확인 다이얼로그 (§7.3) | `Alert` — destructive 스타일 | `Alert` — **취소가 항상 왼쪽/아래**가 되도록 배열을 분기 |

`Platform.select` 에는 `android` 또는 `default` 키를 반드시 채운다 (M-20).

### 6.3 기본 단계 (`Screen 20a`)

```
              ▬▬▬                        ← 핸들 바
   (16)
가입 신청                                  ← H2 / ink
   (20)
┌──────────────────────────────────────┐   ← 정보 블록. background 배경, 라운드 12, 패딩 16
│  이메일                                │   ← Caption / ink-muted
│  name@example.com                     │   ← Body / ink, 선택·복사 가능
│   (12)                                │
│  가입 사유                             │   ← Caption / ink-muted
│  여행 중 일정이 자주 바뀌어서 …          │   ← Body / ink-body, 줄 수 제한 없음
│   (12)                                │
│  신청 시각                             │   ← Caption / ink-muted
│  2026. 9. 5. 14:20                    │   ← Body / ink
└──────────────────────────────────────┘
   (24)
[ Button/Primary   "승인" ]
   (12)
[ Button/Secondary "거절" ]                ← 라벨 색 danger (§8.3)
[ 하단 안전영역 ]
```

- 시트 제목: **"가입 신청"**
- 항목 라벨: **"이메일"** / **"가입 사유"** / **"신청 시각"**
- **가입 사유는 시트에서 말줄임하지 않는다.** 목록의 2줄 제한(§5.3)은 훑어보기용이고,
  판단은 여기서 한다. 길면 시트 안에서 스크롤된다.
- 가입 사유가 비어 있을 때도 §5.3 과 같다 — **서버가 내린 문자열을 그대로 렌더**한다 (AC-33).
  이 자리에서 앱이 분기하지 않으므로 AC-34(사유 없는 신청도 동일하게 처리)가 자동으로 성립한다.
- 이메일은 **선택·복사 가능**하게 둔다. 관리자가 다른 경로로 확인할 일이 있다.
- 버튼 순서: **승인이 위, 거절이 아래.** 승인이 압도적으로 잦은 행동이고, 위험한 쪽이
  엄지 기본 위치에서 멀어야 한다. 두 버튼 최소 높이 52, 간격 12 (auth §9.3 과 같은 규칙).
- "거절" 에 `Button/Danger`(배경 빨강)를 쓰지 않는다 — 거절은 되돌릴 수 있고(AC-19)
  계정 삭제와 같은 무게가 아니다. `Button/Secondary` 에 라벨만 `danger` 로 둔다.

### 6.4 거절 사유 입력 단계 (`Screen 20b` — AC-15 · AC-16 · AC-17)

"거절" 을 누르면 **같은 시트 안에서** 내용이 교체된다. 새 시트를 겹쳐 띄우지 않는다.

```
              ▬▬▬
   (16)
이 신청을 거절할까요?                        ← H2 / ink
   (8)
"거절하면 이 사용자는 로그인할 수 없어요.       ← BodySmall / ink-body
 나중에 거절을 취소할 수 있어요."
   (20)
┌──────────────────────────────────────┐   ← background, 라운드 12, 패딩 12
│  name@example.com                     │   ← Body / ink
└──────────────────────────────────────┘
   (20)
거절 사유  [선택]                           ← 라벨 + Badge/Requirement(선택)
   (8)
[ 입력: 멀티라인 ]                          ← Input/TextField (멀티라인)
                            0/200          ← 카운터, 우측 아래
   (8)
"관리자만 볼 수 있어요. 200자까지 쓸 수 있어요."  ← Caption / ink-muted
   (24)
[ Button/Danger    "거절하기" ]
   (12)
[ Button/Secondary "뒤로" ]
```

- 제목: **"이 신청을 거절할까요?"** ← 이 단계 자체가 AC-15 의 확인 단계다 (§1.2 e).
- 본문: **"거절하면 이 사용자는 로그인할 수 없어요. 나중에 거절을 취소할 수 있어요."**
  - "로그인할 수 없어요" 는 `auth §7.3` 의 `REJECTED` 화면과 사실이 일치한다.
  - "나중에 거절을 취소할 수 있어요" 는 AC-19 가 보장하는 사실이다. 되돌릴 수 있다는 것을
    먼저 말해 두면 관리자가 판단을 미루지 않는다.
- 대상 확인 블록: **이메일만** 다시 보여준다. 어느 신청을 거절하는지가 이 단계의 유일한 사실 확인이다.

#### 거절 사유 입력

| 항목 | 값 |
|---|---|
| 라벨 | **"거절 사유"** + 우측에 **"선택"** 배지 (`Badge/Requirement`) |
| 플레이스홀더 | **"왜 거절하는지 남겨두면 나중에 확인할 때 도움이 돼요."** |
| 도움말 | **"관리자만 볼 수 있어요. 200자까지 쓸 수 있어요."** — Caption / `ink-muted` |
| 입력 형태 | 멀티라인, 최소 3줄(약 96), 최대 6줄까지 확장 후 내부 스크롤 |
| 최대 길이 | **200자.** `maxLength=200` 으로 201번째 글자 입력을 차단한다 (AC-16) |
| 카운터 | 입력란 우측 아래 `0/200` → `200/200`. Caption / `ink-muted`, 200 도달 시 `brand-dark` |

- **AC-16 동작**: 200자 상태에서 한 글자를 더 입력하면 **입력이 반영되지 않고 카운터는
  `200/200` 을 유지**한다. 오류 문구를 띄우지 않는다 — 차단 자체가 피드백이다.
  붙여넣기로 200자를 초과하면 앞에서부터 200자만 반영한다. 한글 조합 중(IME)에도
  조합 완료 문자열 기준으로 자른다. iOS·Android 양쪽에서 확인한다 (M-20).
  (`auth §5.3` 의 가입 사유 100자와 **완전히 같은 규칙**이다. 숫자만 다르다)
- **AC-17**: 사유가 비어 있어도 "거절하기" 는 **활성**이다. 선택 입력이므로 버튼 활성 조건이 아니다.
- "관리자만 볼 수 있어요" 는 사실이다 — `auth §7.3` 의 `REJECTED` 화면은 거절 사유를
  표시하지 않고, 사용자에게 가는 알림도 없다 (PRD Out of scope).

#### 버튼

- **"거절하기"** — `Button/Danger`. 이 단계에서는 배경 `danger` 를 쓴다. 실행 버튼이기 때문이다.
- **"뒤로"** — `Button/Secondary`. §6.3 기본 단계로 돌아간다. **입력한 사유는 유지한다**
  (다시 "거절" 을 누르면 쓰던 내용이 그대로 있다). 시트를 완전히 닫으면 버린다.

### 6.5 처리 중 (`Screen 20c`)

| 동작 | 버튼 라벨 |
|---|---|
| 승인 | **"승인 중…"** |
| 거절 | **"거절하는 중…"** |

- 누른 버튼은 배경을 유지한 채 라벨을 위 문구로 바꾸고 좌측에 24px 스피너를 둔다.
- 같은 시트의 **다른 버튼·입력란·핸들 바를 전부 비활성**한다.
- **시트를 닫을 수 없다** — 스크림 탭·스와이프·하드웨어 백 모두 막는다 (§2.4).
  되돌릴 수 없는 처리가 진행 중일 때 화면을 떠나면 결과를 알 수 없게 된다 (auth §9.7 과 같은 판단).
- 목록 쪽은 아무것도 바뀌지 않는다. 성공 응답을 받은 뒤에만 §5.11 을 적용한다 (낙관적 제거를 하지 않는다 —
  AC-14 가 실패 시 항목이 목록에 남을 것을 요구하는데, 미리 지웠다가 되살리면 순서가 흔들린다).

### 6.6 완료

1. 시트를 닫는다.
2. 목록을 §5.11 대로 갱신한다.
3. 토스트를 2초간 표시한다 — 승인 **"승인했어요"** / 거절 **"거절했어요"**.
4. §3.5 의 announce 를 읽는다.
5. 포커스를 목록으로 되돌린다. 처리한 행이 사라졌으므로 **그 자리의 다음 행**으로 보낸다.

### 6.7 처리 실패 (`Screen 20d` — AC-14)

**시트는 열린 채로 남고, 항목은 목록에 그대로 있다** (AC-14 의 핵심 요건).
정보 블록 위에 `Feedback/Banner` 를 넣는다.

| 상황 | 아이콘 | 제목 | 부연 | 액션 |
|---|---|---|---|---|
| 네트워크 끊김 | `wifi-off` / `ink-muted` | **"연결을 확인해 주세요"** | **"아직 처리되지 않았어요. 연결 후 다시 시도해 주세요."** | 배너 우측 텍스트 버튼 **"다시 시도"** |
| 서버 500 | `alert-circle` / `danger` | **"잠시 후 다시 시도해 주세요"** | **"아직 처리되지 않았어요."** | 배너 우측 텍스트 버튼 **"다시 시도"** |

- **"아직 처리되지 않았어요" 를 반드시 붙인다.** 실패한 건지 성공했는데 응답만 못 받은 건지
  모르는 상태가 가장 나쁘다 (auth §9.7 과 같은 원칙).
- "다시 시도" 는 **직전과 같은 요청**을 다시 보낸다. 거절이면 입력한 사유를 그대로 싣는다.
- 버튼과 입력란은 다시 활성된다. 거절 단계였다면 거절 단계에 그대로 머문다.
- 배너는 관리자가 무엇이든 조작하기 시작하면(입력·버튼 탭) 사라진다.
- 이 배너를 토스트로 대체하지 않는다 (§3.2).

### 6.8 이미 처리된 신청 (`Screen 20e` — AC-12)

다른 기기에서 먼저 처리된 신청을 승인·거절한 경우다. `code` 로 분기한다 (M-13).

**시트를 자동으로 닫지 않는다.** 시트의 액션 영역을 아래로 교체한다.

```
┌──────────────────────────────────────┐   ← Feedback/Banner (danger)
│ ⚠  이미 처리된 신청이에요                │   ← Title
│    다른 기기에서 먼저 처리됐어요.          │   ← BodySmall
│    목록을 새로 고쳤어요.                  │
└──────────────────────────────────────┘
   (20)
[ Button/Secondary  "닫기" ]                ← "승인"·"거절" 버튼은 사라진다
```

- 제목: **"이미 처리된 신청이에요"**
- 부연: **"다른 기기에서 먼저 처리됐어요. 목록을 새로 고쳤어요."**
- **승인·거절 버튼을 제거한다.** 남겨 두면 다시 눌러 같은 오류를 받는다.
- 정보 블록(이메일·가입 사유·신청 시각)은 **그대로 둔다** — 어떤 신청이었는지 확인할 수 있어야 한다.
- **배너가 뜨는 즉시 목록을 다시 불러온다** (AC-12 의 "목록이 갱신된다").
  관리자가 "닫기" 를 누르는 시점에는 이미 갱신이 끝나 있다.
- announce: 배너의 제목과 부연을 이어서 읽는다.

### 6.9 네 가지 상태 요약

| 상태 | 내용 |
|---|---|
| 로딩 | §6.5 처리 중 (`Screen 20c`). 시트 열림 자체에는 로딩이 없다 — 표시할 값이 목록 응답에 이미 있다 (C-8 · 상세 조회를 위한 추가 왕복을 만들지 않는다) |
| 정상 | §6.3 기본 (`Screen 20a`), §6.4 거절 사유 입력 (`Screen 20b`) |
| 비어있음 | **가입 사유가 없는 신청** (AC-33) — 서버가 내린 대체 문구가 그 자리에 들어가고 나머지는 §6.3 과 완전히 같다. 앱이 만드는 빈 상태는 없다 |
| 오류 | §6.7 처리 실패 (`Screen 20d`), §6.8 이미 처리됨 (`Screen 20e`) |

## 7. 시트: 사용자 상세 (`Screen 21a`~`21d`)

`처리 완료` 목록의 행을 탭하면 올라온다. 시트의 형태·플랫폼 분기·접근성은 §6.1·§6.2·§3.5 와 같다.

### 7.1 공통 구성

```
              ▬▬▬
   (16)
사용자                                     ← H2 / ink
   (20)
┌──────────────────────────────────────┐
│  이메일                                │
│  name@example.com                     │
│   (12)                                │
│  상태                                  │
│  [ 승인됨 ]                            │   ← Badge/Status (§3.4)
│   (12)                                │
│  승인 시각                             │
│  2026. 9. 1. 09:12                    │
│   (12)                                │
│  정지 시각            ← SUSPENDED 일 때만 │
│  2026. 9. 6. 18:03                    │
│                                       │
│  거절 시각            ← REJECTED 일 때만  │
│  2026. 9. 2. 11:40                    │
└──────────────────────────────────────┘
   (24)
[ 액션 영역 — 상태에 따라 §7.3~§7.6 ]
```

- 시트 제목: **"사용자"**
- 항목 라벨: **"이메일"** / **"상태"** / **"승인 시각"** / **"정지 시각"** / **"거절 시각"**
- 시각 값이 없는 항목은 **행 자체를 렌더하지 않는다.** 빈 값이나 "-" 를 두지 않는다.
- 상태 배지 라벨은 서버 값이다 (§3.4).

#### 7.1.1 처리자·처리 시각을 표시하지 않는다 (AC-13 — 2026-09-07 Q2 확정)

- **"누가 처리했는지" 와 "처리 기록" 을 이 시트에 그리지 않는다.** 기록은 서버에 남지만(AC-13)
  화면에는 내려오지 않는다. PRD Out of scope 의 "감사 로그 열람 화면" 과 같은 판단을
  이미 열려 있는 시트에도 적용한 것이다.
- 위 구성의 "승인 시각" / "정지 시각" / "거절 시각" 은 **상태가 바뀐 시점**이지 처리자 정보가 아니다.
  이 값들은 목록 행(§5.4)에도 이미 나오는 것이라 새 필드가 아니다.
- **따라서 계약에 처리자 필드를 요구할 이유가 없다** (§13-2). 관리자 이메일이 응답에 실리지 않으므로
  그에 딸린 권한·개인정보 검토도 발생하지 않는다.
- 관리자가 여러 명이 되어 "누가" 가 실제로 필요해지면 그때 PRD 에서 다시 연다.

#### 7.1.2 거절 사유를 표시하지 않는다

§6.4 에서 입력받은 거절 사유도 이 시트에 그리지 않는다. §6.4 의 도움말이
**"관리자만 볼 수 있어요"** 라고 약속한 범위는 "서버에 남는다" 까지이고,
그 값을 되읽는 화면은 §7.1.1 과 같은 이유로 이번 범위 밖이다.

### 7.2 액션 결정표

| 상태 | 자기 자신? | 액션 |
|---|---|---|
| `APPROVED` | 아니오 | §7.3 [이용 정지] |
| `APPROVED` | **예** | §7.6 — **정지 동작을 아예 제공하지 않는다** (AC-25) |
| `SUSPENDED` | 아니오 | §7.4 [정지 해제] |
| `SUSPENDED` | 예 | 발생하지 않는다 (자기 자신은 정지될 수 없으므로). 그래도 응답이 그렇게 오면 §7.6 을 적용한다 |
| `REJECTED` | 아니오 | §7.5 [거절 취소] (AC-19). **`처리 완료` 세그먼트에서 도달한다** (2026-09-07 Q1 확정) |
| `REJECTED` | 예 | 발생하지 않는다 (관리자 자신은 `APPROVED` 다). 그래도 응답이 그렇게 오면 §7.6 을 적용한다 |

### 7.3 정지 (`Screen 21a` — AC-21)

- 버튼: `Button/Danger` **"이용 정지"**
- 누르면 **시스템 확인 다이얼로그**를 한 번 띄운다.
  - 제목: **"이용을 정지할까요?"**
  - 본문: **"정지하면 이 사용자는 로그인할 수 없어요. 나중에 정지를 해제할 수 있어요."**
  - 버튼: **"이용 정지"**(destructive) / **"취소"**(cancel)
- **정지 사유를 받지 않는다** (2026-09-07 Q3 확정). 입력란도, 메모 필드도 두지 않는다.
  AC-21 이 사유를 요구하지 않고, 사유를 받으면 그 값이 **사용자에게 보이는 문장이 될지**를
  다시 정해야 한다 — 거절 사유에 대해 §6.4 에서 "관리자만 볼 수 있어요" 라고 약속한 것과
  같은 판단을 정지에도 적용해 애초에 값을 만들지 않는다.
- **거절(§6.4)과 달리 시트 2단계가 아니라 다이얼로그인 이유**: 정지에는 입력할 것이 없다.
  사유를 받지 않으므로 단계를 만들 내용이 없고, 확인만 필요하다.
  거절은 200자 입력이 함께 있어 단계가 필요했다.
- **정지된 사용자가 보는 화면은 `auth` 가 이미 정한 것 그대로다** — `auth §7.4` 의
  **"이용이 정지된 계정이에요"** 와 §7.4.1 의 이의 제기 카드(문의 연락처)다 (AC-22 / `auth` AC-38·AC-39).
  이 기능이 그 화면에 내려보내는 값은 없다.
- 확인 후 §6.5 와 같은 처리 중 상태 — 라벨 **"정지하는 중…"**.
- 완료: 시트 닫힘 + 토스트 **"이용을 정지했어요"** + 그 행의 배지가 "정지됨" 으로 (§5.11).
- 실패·경합 처리는 §6.7·§6.8 과 같다. 부연의 "아직 처리되지 않았어요" 도 그대로 쓴다.

> **AC-23 확인 (사용자 쪽 화면 — `auth` 소유).** 정지된 사용자가 다른 기기에서 쓰고 있었다면,
> `auth` 계약이 `POST /api/v1/auth/token/refresh` 갱신 시점에 계정 상태를 다시 확인해
> `APPROVED` 가 아니면 403 + `account_status` 를 낸다 (`status.md` 2026-08-26).
> 그 응답을 받은 앱은 `auth §2.6`·§1.2 전이표에 따라 로그인 화면으로 이동하고,
> 다시 로그인하면 `auth §7.4` 의 `SUSPENDED` 화면(**"이용이 정지된 계정이에요"**)을 만난다.
> **이 기능이 정의하는 화면과 어긋나는 지점은 없다.** 반영은 액세스 토큰 수명(30분) 안에 일어난다.

### 7.4 정지 해제 (`Screen 21b` — AC-24)

- 버튼: `Button/Primary` **"정지 해제"**
- **확인 다이얼로그를 두지 않는다.** 해제는 사용자에게 이익이 되는 방향이고, 잘못 눌러도
  다시 정지할 수 있다(§7.3). 확인은 손해가 나는 방향에만 둔다.
- 처리 중 라벨: **"해제하는 중…"**
- 완료: 시트 닫힘 + 토스트 **"정지를 해제했어요"** + 배지가 "승인됨" 으로.
- 해제된 사용자는 다시 로그인할 수 있다 (AC-24). 앱 쪽에서 그 사실을 안내하지 않는다 —
  관리자에게는 배지 변화가 결과의 전부다.

### 7.5 거절 취소 (`Screen 21d` — AC-19)

**도달 경로가 확정되었다 (2026-09-07 Q1).** `처리 완료` 세그먼트에서 상태 배지가 "거절됨" 인 행을
탭하면 이 시트가 열린다 (§5.4 · §2.3 전이표). AC-19 는 이 경로로 완성된다.

- 버튼: `Button/Secondary` **"거절 취소"**
- 확인 다이얼로그:
  - 제목: **"거절을 취소할까요?"**
  - 본문: **"이 신청이 다시 검토 대기 목록으로 돌아가요."**
  - 버튼: **"거절 취소"** / **"취소"**(cancel)
  - destructive 스타일을 쓰지 않는다 — 되돌리는 행동이지 파괴적인 행동이 아니다.
- 처리 중 라벨: **"되돌리는 중…"**
- 완료: 시트 닫힘 + 토스트 **"검토 대기로 되돌렸어요"** + §5.11 대로 목록·건수 갱신.
- 정보 블록에는 **"거절 시각"** 행이 추가되고 상태 배지는 "거절됨" 이다.
  **거절 사유(§6.4 에서 입력한 값)는 표시하지 않는다** — §7.1.2 확정.
- 거절 취소로 대기 상태가 된 신청은 §5.3 의 검토 대기 목록에 **신청 시각 기준 자리**로 돌아간다.
  거절 취소 시각이 아니라 원래 신청 시각으로 정렬된다 — AC-19 가 요구하는 것은
  "다시 대기 목록에 나타난다" 이고, 신청 시각이 바뀐 것은 아니기 때문이다.

### 7.6 자기 자신 (`Screen 21c` — AC-25)

관리자가 자기 계정을 열었을 때다.

- **액션 버튼을 렌더하지 않는다.** 비활성 버튼도 두지 않는다.
  AC-25 는 "정지 동작이 제공되지 않는다" 를 요구한다 — 회색 버튼은 "지금은 안 되지만
  언젠가 될 수도 있는 것" 으로 읽히고, 관리자가 눌러보게 만든다.
- 버튼 자리에 한 줄을 둔다 (Caption / `ink-muted`, 중앙 정렬):
  **"내 계정이에요. 스스로 정지할 수 없어요."**
- 정보 블록(이메일·상태·승인 시각)은 다른 사용자와 **완전히 같게** 보여준다.
  자기 계정을 목록에서 숨기지도 않는다 — 목록에 없으면 관리자가 자기 계정의 상태를 확인할 수 없다.
- 이 판정의 근거 값(자기 자신인지)은 **서버가 응답에 담아 내린다.** 앱이 로그인한 계정의
  이메일과 목록 항목의 이메일을 비교하지 않는다 (C-8 / M-18 — 두 응답을 앱에서 이어붙이는 것이 된다).
- 서버는 이 화면과 무관하게 자기 자신 정지 요청을 거부한다. 앱이 버튼을 숨기는 것은 편의다.
  그래도 거부 응답이 오면 §6.7 형식의 배너로 **"내 계정은 정지할 수 없어요"** +
  부연 **"스스로를 정지할 수는 없어요."** + `Button/Secondary` **"닫기"** 를 보인다.

### 7.7 네 가지 상태 요약

| 상태 | 내용 |
|---|---|
| 로딩 | 처리 중 (§7.3·§7.4·§7.5). 시트 열림 자체에는 로딩이 없다 (§6.9 와 같은 이유) |
| 정상 | `Screen 21a` 승인됨 / `Screen 21b` 정지됨 / `Screen 21c` 내 계정 / `Screen 21d` 거절됨 |
| 비어있음 | **해당 없음.** 항목이 고정되어 있고 값이 없는 행은 렌더하지 않는다 (§7.1) |
| 오류 | §6.7 처리 실패 · §6.8 경합 형식을 그대로 쓴다 + §7.6 자기 자신 거부 배너 |

**충족 AC**: AC-19, AC-20, AC-21, AC-24, AC-25

§2.3 전이표 · §3.5 a11y 라벨 · §3.6 · §5.2 세그먼트 · §5.4 목록 행 · §5.8 빈 상태 문구 ·
§5.11 갱신표 · §5.12 · §7 진입 문장 · §7.1 정보 블록 · §7.2 결정표 · §7.5 ·

### Q2. 처리 기록(누가 언제)을 관리자 화면에 보여주는가 — AC-13 · **닫힘 (2026-09-07)**

**결정: A — 표시하지 않는다.** 기록은 서버에 남기되(AC-13) 시트에 처리자·처리 시각을 그리지 않는다.
**따라서 계약에 처리자 필드를 요구할 이유가 없다.**

이유: 관리자가 한두 명인 베타에서 "누가" 는 대부분 자기 자신이고, 화면에 내리는 순간
관리자 이메일이 응답에 실려 계약과 권한 검토가 늘어난다. 관리자가 여러 명이 되면 그때 다시 연다.

**반영된 곳**: §7.1.1(신설) · §7.1.2(신설) · §7.5 · §9.7 · §11 AC-13 · §13-2.

### Q3. 정지에 사유를 남기는가 — **닫힘 (2026-09-07)**

**결정: A — 받지 않는다.** 확인 다이얼로그 한 단계만 거친다(§7.3).
정지된 사용자는 `auth` 가 이미 정한 **"이용이 정지된 계정이에요"** 화면과 문의 연락처를 본다
(AC-22 / `auth` AC-38·AC-39). 이 기능이 그 화면에 내려보내는 값은 없다.

이유: ⑴ AC-21 이 사유를 요구하지 않고, ⑵ 사유를 받으면 관리자가 쓴 메모가 사용자에게 보이는
통보문이 될지를 다시 정해야 하며(거절 사유는 §6.4 에서 "관리자만 볼 수 있어요" 로 약속했다),
⑶ `auth §7.4` 화면·계약·`SUSPENDED` 응답이 모두 바뀐다.

**이 결정이 `auth` design.md §14 항목 6(`SUSPENDED` 정지 사유·기간 표시 여부)도 함께 닫는다.**
`auth` 쪽 문서에 반영을 마쳤다 (§14 참조).

## 13. tech-lead 로 넘기는 사항 (계약 설계 시 참고)

API 스펙은 이 문서가 정하지 않는다. 다만 화면이 성립하려면 다음이 필요하다.

**1. 진입점 판정과 대기 건수를 한 응답에 담는다 (AC-1 · AC-2 · AC-32)**

설정 화면은 이미 계정 정보(이메일)를 한 번 조회한다(`auth §8.5`). 관리자 섹션의
**역할**과 **대기 건수**를 위해 호출을 더 만들면 한 화면의 한 영역에 2회 이상 호출이 되어 **C-8 위반**이다.
같은 응답에 역할과 대기 건수가 함께 실려야 한다. 대기 건수는 **`ADMIN` 에게만** 내린다 —
`USER` 응답에 그 필드가 있으면 앱이 숨겨도 값은 새어 나간다.

**2. 목록 응답은 화면이 필요한 값을 완성해서 내린다 (C-8)**

- 검토 대기: 이메일 · **가입 사유(비어 있으면 "입력하지 않음" 을 서버가 채운 문자열)** · 신청 시각(ISO 8601 UTC)
- 처리 완료: 이메일 · 상태 값 · **상태 배지 라벨 문자열** · **시각 접두어 문자열("승인"/"정지"/"거절")** ·
  마지막 처리 시각(ISO 8601 UTC). 이 목록은 `APPROVED` · `SUSPENDED` · `REJECTED` 를 함께 담는다
  (2026-09-07 Q1). 정렬 기준은 마지막 처리 시각 최신순 (§5.4).
  - **접두어와 시각을 각각 내린다.** 완성된 문장으로 내리면 앱이 UTC → 로컬 변환(C-2)을 할 수 없고,
    앱이 상태로 접두어를 고르면 C-8 위반이다.
- 두 목록 모두 **자기 자신 여부**를 항목에 담는다 (AC-25 / §7.6). 앱이 로그인 계정과 비교하지 않는다.
- **처리자(관리자) 정보는 담지 않는다** (2026-09-07 Q2 / §7.1.1). 화면에 그리지 않으므로 필요 없다.
- **정지 사유 필드는 존재하지 않는다** (2026-09-07 Q3 / §7.3). 입력받지 않으므로 값이 없다.
- 시트는 목록 응답의 값만으로 그려진다 — **상세 조회를 위한 추가 왕복을 만들지 않는다** (§6.9).

**3. 페이지네이션 (AC-7)**

- 페이지 크기 20. 다음 페이지 존재 여부를 응답이 알려줘야 한다 — §5.6 의 "모두 확인했어요" 와
  "불러오는 중" 을 앱이 추측으로 나눌 수 없다.
- 커서 방식이든 오프셋이든 **최신순 정렬 기준(검토 대기 = 신청 시각 / 처리 완료 = 마지막 처리 시각)** 은
  계약이 못 박는다 (§5.3 · §5.4).

**4. 오류 코드 (PRD 열린 질문 5)**

AC 가 화면 분기를 요구하는 상황은 셋이고, 각각 **구분 가능한 `code`** 가 필요하다 (M-13).

| 상황 | 화면 | AC |
|---|---|---|
| 이미 처리된 신청 | §6.8 시트 안 배너 + 목록 갱신 | AC-12 |
| 자기 자신 정지 시도 | §7.6 배너 | AC-25 |
| 관리자 아님 (403) | §5.10 권한 없음 화면 | AC-3 |

AC-12 의 "이미 처리됨" 은 **거절 취소(AC-19)와 정지·해제(AC-21·AC-24)에도 같은 형태로 발생한다** —
다른 기기가 먼저 상태를 바꾼 경우다. 같은 `code` 를 쓰고 화면은 §6.8 형식을 그대로 재사용한다.

카탈로그에 없는 `code` 는 일반 오류로 처리한다 (M-13 — 앱이 죽지 않는다).
가입 사유가 비어 있는 것은 **오류가 아니라 정상 응답**이다 (AC-33).

**5. 처리 결과가 대기 건수를 갱신한다 (§5.11)**

승인·거절·거절 취소 응답에 **갱신된 대기 건수**가 함께 오거나, 앱이 같은 값을 다시 조회할 수 있어야 한다.
앱이 ±1 하지 않는다 (M-18 / AC-32).

**6. 거절 사유 (AC-16 · AC-17)**

- 최대 200자, **선택 입력**(비어 있어도 200 계열 정상 응답).
- 이 값은 **사용자에게 내려가지 않는다.** `auth §7.3` 의 `REJECTED` 화면은 사유를 표시하지 않고,
  §6.4 에서 관리자에게 "관리자만 볼 수 있어요" 라고 약속했다.
- **관리자 화면으로도 되읽지 않는다** (§7.1.2). 저장은 하되 조회 응답에 실을 필요가 없다.

**6-1. 정지에는 사유 입력이 없다 (AC-21 · 2026-09-07 Q3)**

정지 요청 본문에 사유 필드를 두지 않는다. `auth` 의 `SUSPENDED` 응답(`AccountStatusView`)도
현행 그대로이며 이 기능 때문에 바뀌는 것이 없다 — `auth` design.md §14 항목 6 이 이 결정으로 닫혔다.

**7. 정지의 세션 반영 (AC-23)**

이미 확정돼 있다 — `refresh` 갱신 시점에 계정 상태를 재확인해 `APPROVED` 가 아니면
403 + `account_status` (`status.md` 2026-08-26). **이 문서가 요구하는 추가 사항은 없다.**

**8. Discord 알림 (AC-26~AC-32)**

전부 서버 영역이다. 앱 화면과의 유일한 접점은 AC-32(건수 일치)이고,
**두 곳이 같은 서버 계산을 쓰는 것**이 그 보장의 방법이다 (§4.5).

여전히 맞다** (§8.5). 이건 pen 쪽 제약이지 설계 변경이 아니다.

### 15.4 자리표시자 표기

- 목록·시트의 이메일·가입 사유·시각은 전부 **더미 데이터**다. 구현에서 상수로 옮기지 않는다.
- 가입 사유가 없는 항목의 **"입력하지 않음"** 도 더미 데이터다 — 서버가 내리는 값이다 (§9.7).
- 상태 배지 라벨("승인됨" 등)과 시각 앞 접두어("승인" / "정지" / "거절")도 **더미 데이터**다.
  서버가 내리는 값이며 앱 문구 상수가 아니다 (§3.4 / §5.4 / §9.7).
