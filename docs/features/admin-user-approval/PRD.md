# PRD: 관리자 가입 승인

- 기능 슬러그: `admin-user-approval`
- 작성일: 2026-08-23

## 배경 / 문제

Planbee 는 초대·승인제 클로즈드 베타로 운영한다. `auth` 기능이 가입 신청을 `PENDING` 상태로
받아두지만, 그 상태를 `APPROVED` 로 바꿔 줄 사람과 화면이 없으면 **아무도 앱에 들어올 수 없다.**
즉 이 기능이 없으면 `auth` 는 반쪽이다.

승인 처리는 별도의 웹 어드민을 만들지 않고 **앱 안의 관리자 전용 화면**에서 한다.
새 프로젝트·빌드·배포 파이프라인을 늘리지 않고 이미 있는 인증을 그대로 쓰기 위해서다. (2026-08-23 결정)

관리자가 앱을 열어보기 전까지 신청을 모르고 지나치는 문제는 **Discord Incoming Webhook**
으로 해결한다. 도메인도 SMTP 계정도 서드파티 SDK 도 필요 없이 서버에서 HTTP POST 한 번이면 된다.
(메일 발송 인프라를 두지 않기로 한 결정에 따름 — `auth` PRD Out of scope 참조)

## 목표

- 관리자가 앱 안에서 대기 중인 가입 신청을 확인하고 승인하거나 거절할 수 있다.
- 승인된 사용자가 즉시 로그인할 수 있게 된다.
- 관리자가 앱을 열지 않아도 새 신청이 들어온 사실을 알 수 있다.
- 관리자가 이미 승인한 사용자의 이용을 정지하거나 다시 풀 수 있다.
- 누가 언제 어떤 결정을 내렸는지 기록이 남는다.

## Out of scope

- **웹 어드민 콘솔** — 앱 안의 화면으로 대체한다.
- **관리자 지정·해제 UI** — 역할 변경은 앱에서 하지 않는다. 초기 관리자는 시드로 만들고,
  추가가 필요하면 DB 에서 직접 처리한다 (`auth` PRD 열린 질문 2).
- **사용자에게 보내는 승인·거절 알림** — 사용자는 다시 로그인할 때 상태를 확인한다 (`auth` AC-14~16).
- **감사 로그 열람 화면** — 기록은 남기되 화면으로 보여주지 않는다.
- **일괄 승인·일괄 거절**, 검색·필터·정렬 옵션. 베타 규모에서는 최신순 목록으로 충분하다.
- **가입 추이·이용 통계 대시보드**.
- 거절된 사용자의 이의 제기 흐름.

## 유저 스토리와 인수조건

### US-1. 관리자로서 검토할 가입 신청이 있는지 확인하고 싶다

| ID | 인수조건 |
|---|---|
| AC-1 | Given 역할이 `ADMIN` 인 계정으로 로그인했을 때 When 앱을 보면 Then 관리자 화면 진입점이 표시된다 |
| AC-2 | Given 역할이 `USER` 인 계정으로 로그인했을 때 When 앱을 보면 Then 관리자 화면 진입점이 표시되지 않는다 |
| AC-3 | Given 역할이 `USER` 인 계정의 토큰으로 When 관리자 API 를 직접 호출하면 Then 권한 없음으로 거부된다 |
| AC-4 | Given 로그인하지 않은 상태에서 When 관리자 API 를 호출하면 Then 인증 필요로 거부된다 |
| AC-5 | Given 대기 중인 신청이 3건 있고 셋 다 가입 사유를 입력했을 때 When 관리자 화면을 열면 Then 3건이 신청 시각 최신순으로 표시되고 각 항목에 이메일 · 가입 사유 · 신청 시각이 보인다 |
| AC-6 | Given 대기 중인 신청이 0건일 때 When 관리자 화면을 열면 Then "검토할 신청이 없어요" 빈 상태가 표시된다 |
| AC-7 | Given 대기 중인 신청이 25건일 때 When 관리자 화면을 열면 Then 최신 20건이 먼저 표시되고 목록 끝에서 나머지를 불러올 수 있다 |
| AC-8 | Given 서버가 500 을 반환하는 상황에서 When 관리자 화면을 열면 Then 오류 안내와 재시도 버튼이 표시된다 |
| AC-9 | Given 목록을 보고 있을 때 When 아래로 당겨 새로고침하면 Then 최신 목록으로 갱신된다 |

### US-2. 관리자로서 적격한 신청을 승인해 앱을 쓸 수 있게 하고 싶다

| ID | 인수조건 |
|---|---|
| AC-10 | Given 대기 중인 신청을 골랐을 때 When 승인하면 Then 그 항목이 대기 목록에서 사라진다 |
| AC-11 | Given AC-10 으로 승인된 사용자가 When 자기 계정으로 로그인하면 Then 홈 화면으로 들어간다 (`auth` AC-11 과 동일한 결과) |
| AC-12 | Given 이미 승인 처리된 신청일 때 When 다른 기기에서 같은 신청을 다시 승인하면 Then 이미 처리되었다는 안내가 표시되고 목록이 갱신된다 |
| AC-13 | Given 승인이 완료되었을 때 When 그 사용자의 처리 기록을 조회하면 Then 처리한 관리자와 처리 시각이 남아 있다 |
| AC-14 | Given 네트워크가 끊긴 상태에서 When 승인을 누르면 Then 실패 안내가 표시되고 그 항목은 대기 목록에 그대로 남는다 |

### US-3. 관리자로서 부적격한 신청을 거절하고 싶다

| ID | 인수조건 |
|---|---|
| AC-15 | Given 대기 중인 신청을 골랐을 때 When 거절하면 Then 확인 단계를 한 번 거친 뒤 그 항목이 대기 목록에서 사라진다 |
| AC-16 | Given 거절 사유 입력란에 200자를 입력한 상태에서 When 한 글자를 더 입력하면 Then 입력되지 않는다 |
| AC-17 | Given 거절 사유를 비워둔 채로 When 거절하면 Then 거절이 정상 처리된다 (사유는 선택 입력) |
| AC-18 | Given AC-15 로 거절된 사용자가 When 자기 계정으로 로그인하면 Then "가입이 승인되지 않았어요" 화면이 표시된다 (`auth` AC-15) |
| AC-19 | Given 거절 처리된 사용자를 볼 때 When 거절을 취소하면 Then 상태가 대기로 돌아가 다시 대기 목록에 나타난다 |

### US-4. 관리자로서 문제가 있는 사용자의 이용을 정지하고 싶다

| ID | 인수조건 |
|---|---|
| AC-20 | Given 관리자 화면일 때 When 승인된 사용자 목록을 열면 Then 이메일과 승인 시각이 최신순으로 표시된다 |
| AC-21 | Given 승인된 사용자를 골랐을 때 When 이용 정지하면 Then 그 사용자의 상태가 정지로 바뀐다 |
| AC-22 | Given AC-21 로 정지된 사용자가 When 로그인하면 Then "이용이 정지된 계정이에요" 화면이 표시된다 (`auth` AC-16) |
| AC-23 | Given 정지 처리 시점에 그 사용자가 다른 기기에서 로그인 중이었을 때 When 그 기기가 다음 API 를 호출하면 Then 더 이상 이용할 수 없고 로그인 화면으로 이동한다 |
| AC-24 | Given 정지된 사용자를 골랐을 때 When 정지를 해제하면 Then 상태가 승인으로 돌아가고 다시 로그인할 수 있다 |
| AC-25 | Given 관리자 자신의 계정을 볼 때 When 이용 정지를 시도하면 Then 정지 동작이 제공되지 않는다 (스스로를 잠글 수 없다) |

### US-5. 관리자로서 앱을 열지 않아도 새 신청이 온 것을 알고 싶다

| ID | 인수조건 |
|---|---|
| AC-26 | Given Discord Webhook URL 이 설정된 환경일 때 When 새 가입 신청이 접수되면 Then 해당 Discord 채널에 **대기 중인 신청 건수와 관리자 화면에서 확인하라는 안내만** 담긴 메시지가 도착한다 (예: "새 가입 신청이 접수됐어요. 현재 검토 대기 3건 — 앱의 관리자 화면에서 확인해 주세요.") |
| AC-27 | Given Webhook 엔드포인트가 오류를 반환하는 상황일 때 When 가입 신청이 접수되면 Then 가입은 정상적으로 접수된다 (`auth` AC-1 결과가 동일하다) |
| AC-28 | Given AC-27 상황일 때 When 서버 로그를 확인하면 Then Webhook 발송 실패가 경고 수준으로 기록되어 있다 |
| AC-29 | Given Webhook URL 이 설정되지 않은 로컬 환경일 때 When 가입 신청이 접수되면 Then 발송을 건너뛰고 가입은 정상 접수되며 서버는 기동에 실패하지 않는다 |
| AC-30 | Given 가입 트랜잭션이 롤백되는 상황일 때 When 그 신청을 처리하면 Then Webhook 메시지가 발송되지 않는다 (커밋된 신청만 알린다) |
| AC-31 | Given 발송된 Webhook 메시지를 확인할 때 When 메시지 본문을 검사하면 Then 신청자를 식별할 수 있는 값(이메일 · 가입 사유 · 사용자 식별자 · 비밀번호 · 토큰)이 하나도 포함되어 있지 않다 |
| AC-32 | Given 발송 시점의 대기 중 신청이 3건일 때 When 알림 메시지의 건수를 관리자 화면의 대기 목록 건수와 비교하면 Then 두 값이 같다 |

### US-6. 관리자로서 가입 사유를 쓰지 않은 신청도 그대로 검토하고 싶다

가입 사유는 선택 항목이다 (`auth` PRD 제약). 목록의 모든 항목에 값이 있다고 가정할 수 없다.

| ID | 인수조건 |
|---|---|
| AC-33 | Given 가입 사유를 입력하지 않은 신청이 대기 목록에 있을 때 When 관리자 화면을 열면 Then 그 항목의 가입 사유 자리에 "입력하지 않음" 이 표시되고, 이메일과 신청 시각은 다른 항목과 똑같이 보인다 |
| AC-34 | Given AC-33 의 항목을 골랐을 때 When 승인하거나 거절하면 Then 가입 사유가 있는 신청과 동일하게 처리된다 (AC-10 · AC-15 와 같은 결과) |

## 필수 포함 인수조건

| 유형 | AC ID |
|---|---|
| 정상 흐름 | AC-5, AC-10, AC-15, AC-26 |
| 입력 검증 실패 | AC-16 |
| 서버/네트워크 오류 | AC-8, AC-14, AC-27 |
| 데이터가 없는 상태 | AC-6, AC-29, AC-33 |
| 권한 없음 | AC-2, AC-3, AC-4 |

## 제약

- 이 기능은 `auth` 가 정의한 상태(`PENDING`/`APPROVED`/`REJECTED`/`SUSPENDED`)와
  역할(`USER`/`ADMIN`) 위에서 동작한다. 상태·역할의 정의를 여기서 바꾸지 않는다.
- 관리자 화면은 앱 안에 둔다. 별도 웹 프로젝트를 만들지 않는다.
- 관리자 판정은 **서버가 한다.** 앱이 진입점을 숨기는 것(AC-2)은 편의일 뿐이고,
  실제 차단은 서버의 인가로 이뤄진다(AC-3). 앱 쪽 숨김만으로 통과 판정하지 않는다.
- **알림 채널은 Discord 로 확정한다** (2026-08-23). 요청 본문은 Discord Webhook 형식(`content` 필드)을
  따른다. Slack 으로 옮길 일이 생기면 본문 형식만 바꾸면 되도록 발송부를 한 곳에 모은다.
- **Webhook 발송은 가입 트랜잭션 밖에서, 커밋 이후에 비동기로 한다.** 발송 실패가 가입을
  실패시켜서는 안 된다(AC-27). 실패 시 재시도는 1회까지만 하고 그 뒤에는 로그만 남긴다.
- Webhook URL 은 시크릿으로 취급한다. `.env` 로만 주입하고 설정 파일·코드·문서에 값을 쓰지 않는다
  (`docs/conventions/common.md` C-4). `.env.example` 에는 정의만 추가한다.
- **Webhook 메시지에 개인정보를 일절 담지 않는다** (2026-08-23 확정). 이메일·가입 사유·사용자
  식별자·비밀번호·토큰 어느 것도 보내지 않고 **대기 건수와 안내 문구만** 보낸다(AC-26·AC-31).
  이유는 국외 이전 회피다 — Discord 는 미국 사업자라 페이로드에 개인정보를 실으면
  「개인정보 보호법」 제28조의8 의 국외 이전에 해당해 가입 화면에 별도 동의 항목이 하나 더 필요해진다.
  건수만 보내면 그 요건이 성립하지 않는다. `docs/legal/privacy-policy.md` 5항이 이 내용을 이미 반영하고 있다.
- **알림만으로는 누가 신청했는지 알 수 없다.** 이것은 의도한 결과다. 따라서 알림 메시지는 항상
  관리자 화면으로 유도하는 문구를 포함하고, 관리자는 앱에서 실제 내용을 확인한다(AC-1 → AC-5).
  알림에 신청자 정보를 되살리는 어떤 변경도 위 국외 이전 판단을 다시 열게 된다.
- **가입 사유는 선택 항목이다** (`auth` PRD 제약). 목록의 모든 항목에 값이 있다고 가정하지 않는다.
  비어 있을 때 화면에 넣을 대체 문구("입력하지 않음")도 서버가 완성해서 내린다 (C-8, AC-33).
- **관리자 계정의 이메일은 앱 안에서 문의 연락처로 노출된다** (`auth` AC-38~42). 거절·정지·잠금
  사용자가 보는 주소이므로, 관리자 계정은 개인 계정이 아니라 대외 문의용으로 쓸 수 있는
  주소로 만든다. 이 기능이 관리자 계정을 새로 만드는 경로를 제공하지는 않는다(Out of scope).
- 목록 응답은 화면이 필요한 값을 서버가 완성해서 내린다 (C-8). 앱이 여러 엔드포인트를 합치지 않는다.
- 시각은 ISO 8601 UTC, 필드 이름은 `snake_case` (C-2, C-7).
- iOS 우선이되 Android 에서도 동작해야 한다 (M-19·M-20).

## 열린 질문

1. **Discord 채널 Webhook URL 을 누가 발급해 `.env` 에 넣는가.** 채널 설정 → 연동 → 웹후크에서
   만들 수 있다. 값은 시크릿이므로 이 문서나 커밋에 적지 않는다. → 사람 판단
2. **동시에 여러 신청이 들어올 때 메시지를 건별로 보낼 것인가, 일정 시간 묶어 보낼 것인가.**
   현재 PRD 는 건별 즉시 발송을 전제로 썼다(AC-26). 베타 규모에서는 충분하다고 본다.
   메시지가 건수만 담게 되면서(2026-08-23) 묶어 보내도 정보 손실이 없어졌다 — 나중에 바꾸기 쉬운 결정이다.
3. **거절된 계정을 관리자가 대신 삭제하는 경로가 필요한가.** 거절 상태에서는 로그인이 막혀 있어
   `auth` AC-28 의 계정 삭제 경로에 도달할 수 없다. 사용자가 파기를 **요청할** 경로는
   생겼다 — `auth` AC-38 이 거절 화면에 문의 연락처를 표시하고, 그 값은 서버가 `ADMIN` 계정
   이메일로 내려준다(2026-08-23 확정). 남은 것은 그 요청을 받은 관리자가 **앱 안에서** 계정을
   지울 수 있어야 하는가다. 지금은 DB 직접 처리 외에 수단이 없다. → **사람 판단**
4. **정지(AC-23)가 진행 중인 세션에 언제 반영되는가.** 액세스 토큰 수명이 30분이므로
   토큰 만료를 기다리면 최대 30분의 지연이 생긴다. 즉시 차단하려면 매 요청마다 상태를 확인해야 한다.
   지연 허용 여부는 성능과 맞바꾸는 결정이다. → tech-lead
5. **오류 코드 확정.** AC 가 구분을 요구하는 상황: 이미 처리된 신청(AC-12), 자기 자신 정지 시도(AC-25),
   가입 사유가 비어 있을 때의 대체 문구는 오류가 아니라 정상 응답이다(AC-33). → tech-lead
