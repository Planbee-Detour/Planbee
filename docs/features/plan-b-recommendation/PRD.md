# PRD: 실시간 변수 기반 Plan B 추천

- 기능 슬러그: `plan-b-recommendation`
- 작성일: 2026-08-29
- 공모전 주제: `docs/product/competition-theme.md`의 주제 1

## 배경 / 문제

여행 중 비가 오거나 방문 예정 장소가 갑자기 휴무가 되면 사용자는 남은 시간과 다음 일정을
다시 계산하면서 대체 장소를 찾아야 한다. 기존 장소 추천은 비슷한 장소를 보여줄 수는 있지만,
왜 현재 상황에서 실행 가능한 대안인지와 기존 계획이 어떻게 바뀌는지를 설명하지 못한다.

## 목표

- 비 예보와 관광지 휴무가 기존 일정에 미치는 영향을 감지한다.
- 사용자의 실제 일정 진행 상태를 확인해 이미 완료한 일정에 잘못 경고하지 않는다.
- 현재 위치·남은 시간·동선·취향을 반영한 실행 가능한 대체 장소를 제시한다.
- 장소 하나 교체를 기본으로 제공하고, 남은 시간을 다시 구성한 코스를 추가 선택지로 제공한다.
- 추천 결과의 요약, 검증 가능한 근거, 불리한 변경 사항을 구분해서 표시한다.

## Out of scope

- 사용자 확인 없는 자동 일정 변경
- 혼잡도·교통 장애의 실제 감지
- LLM이 근거 없이 장소·운영 상태·거리·시간을 생성하는 방식
- 실제 일정 저장 API와 알림 푸시
- 백그라운드 위치 추적으로 방문 완료를 자동 확정하는 기능

## 유저 스토리와 인수조건

### US-PB-1. 여행자로서 일정에 영향을 주는 변수를 빠르게 알고 싶다

| ID | 인수조건 |
|---|---|
| AC-PB-1 | 상태가 `PLANNED` 또는 `IN_PROGRESS`인 경복궁 일정과 비 예보가 겹치거나 경복궁이 휴무이면 홈에 영향 확정 카드가 표시된다. |
| AC-PB-2 | 영향 확정 카드는 발생 변수, 영향받는 일정 수, "대체 계획 확인하기" 버튼을 표시한다. |
| AC-PB-3 | 사용자가 버튼을 누르기 전에는 기존 일정을 변경하지 않는다. |

### US-PB-1A. 여행자로서 느슨한 일정도 실제 진행 상태에 맞게 판단받고 싶다

| ID | 인수조건 |
|---|---|
| AC-PB-15 | 각 일정은 `FIXED`, `TIME_WINDOW`, `FLEXIBLE` 중 하나의 시간 유형을 가진다. |
| AC-PB-16 | 각 일정의 진행 상태는 `PLANNED`, `IN_PROGRESS`, `COMPLETED`, `SKIPPED`, `CANCELLED`, `UNKNOWN` 중 하나다. |
| AC-PB-17 | `COMPLETED`, `SKIPPED`, `CANCELLED` 일정은 변수 영향 및 Plan B 추천 대상에서 제외한다. |
| AC-PB-18 | 일정 상태가 `UNKNOWN`이거나 시각만으로 진행 상태를 추정한 경우에는 `NEEDS_CONFIRMATION`으로 분류하고, 일정이 영향을 받는다고 단정하지 않는다. |
| AC-PB-19 | `NEEDS_CONFIRMATION`이면 홈에서 "남은 일정 확인하기"를 제공하고, 영향 가능성이 있는 일정별로 "다녀왔어요"와 "아직이에요"를 선택할 수 있다. |
| AC-PB-20 | "다녀왔어요"를 선택하면 해당 일정을 `COMPLETED`로 제외하고, "아직이에요"를 선택하면 `PLANNED`로 확정해 변수와 겹칠 때 `CONFIRMED` 영향으로 전환한다. |
| AC-PB-21 | 확인 결과 영향 가능 일정이 모두 완료되었으면 Plan B 카드를 표시하지 않고 "오늘 야외 일정은 모두 완료했어요"라고 안내한다. |
| AC-PB-22 | 명시적으로 `PLANNED`인 `FIXED`·`TIME_WINDOW` 일정은 아직 유효한 시간 범위에 있고 변수와 겹치면 사용자 재확인 없이 `CONFIRMED`로 분류할 수 있다. |
| AC-PB-23 | `FLEXIBLE` 일정은 현재 몇 번째 일정인지 시각만으로 계산하지 않으며, 확인된 완료 수와 남은 일정만 표시한다. |

### US-PB-2. 여행자로서 실행 가능한 대안을 근거와 함께 확인하고 싶다

| ID | 인수조건 |
|---|---|
| AC-PB-4 | 기본 결과는 경복궁을 대체할 장소 하나를 기존 계획과 비교해 표시한다. |
| AC-PB-5 | 추천은 필수 제약을 통과한 후보만 표시한다. |
| AC-PB-6 | 추천 사유는 요약, 근거 항목, 주의사항으로 나뉜다. |
| AC-PB-7 | 각 근거는 날씨·운영 상태·거리·시간·취향 중 실제 필드에 연결된다. |
| AC-PB-8 | 불리한 변경 사항이 있으면 주의사항으로 숨기지 않고 표시한다. |

### US-PB-3. 여행자로서 남은 시간을 코스로 다시 구성하고 싶다

| ID | 인수조건 |
|---|---|
| AC-PB-9 | "코스로 다시 짜기"를 누르면 2~3개 장소의 시간순 코스를 표시한다. |
| AC-PB-10 | 이동·체류·다음 일정 이동·안전 버퍼 합계가 남은 시간 안에 들어간다. |
| AC-PB-11 | 사용자가 "이 계획으로 변경"을 누른 뒤에만 fixture 일정이 교체된다. |

### US-PB-4. 추천을 만들 수 없는 상황에서도 다음 행동을 알고 싶다

| ID | 인수조건 |
|---|---|
| AC-PB-12 | 추천 생성 중에는 "Planbee가 새로운 계획을 찾고 있어요."를 표시한다. |
| AC-PB-13 | 조건을 만족하는 대안이 없으면 범위를 완화하거나 이전 화면으로 돌아갈 수 있다. |
| AC-PB-14 | 오류가 발생하면 다시 시도하거나 이전 화면으로 돌아갈 수 있다. |

## 제약

- 공모전 MVP는 경복궁 방문 예정 일정을 로컬 fixture로 사용한다.
- 비 예보와 휴무 상태만 실제 감지 대상이며 나머지 변수는 후속 범위다.
- 후보 생성·제약 검증·점수화·근거 사실 생성은 서버 책임이다.
- LLM은 서버가 제공한 근거만 자연어로 정리하며 순위와 숫자를 결정하지 않는다.
- LLM 출력 검증 실패 시 서버 템플릿 문구를 사용한다.
- 시간 유형은 다음 의미로 사용한다.
  - `FIXED`: 예약·열차처럼 시작 시각을 지켜야 하는 일정
  - `TIME_WINDOW`: 오전·오후 또는 운영시간처럼 수행 가능한 시간 범위가 있는 일정
  - `FLEXIBLE`: 날짜만 정해졌고 실행 시각과 순서가 자유로운 일정
- 영향 판정은 `NEEDS_CONFIRMATION`, `CONFIRMED`, `NO_IMPACT`로 구분한다.
  - `NEEDS_CONFIRMATION`: 아직 남았는지 알 수 없어 사용자 확인이 필요함
  - `CONFIRMED`: `PLANNED` 또는 `IN_PROGRESS`임이 확인됐고 실시간 변수와 겹침
  - `NO_IMPACT`: 완료·건너뜀·취소 또는 변수와 겹치지 않아 변경할 필요가 없음
- 일정 종료 시각이 지났다는 이유만으로 `COMPLETED`를 추론하지 않는다.
- 진행률은 배열 위치나 현재 시각이 아니라 명시적으로 확인된 상태를 기준으로 계산한다.

## 열린 질문

- 실제 일정 저장 기능과 API는 후속 계약에서 확정한다.
- 비 예보·휴무 데이터 제공처와 갱신 주기는 tech-lead 단계에서 확정한다.
- 추천 점수 가중치는 MVP 검증 후 조정한다.
